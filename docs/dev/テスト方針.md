# Surtr テスト方針（V9）

> 目的: フェーズ名ベースのテスト管理をやめ、仕様ベースのテスト体系へ移行する。

---

## 1. 基本方針

- テストの主語を「実装フェーズ」ではなく「言語機能」にする
- E2E 偏重を解消し、`unit / fixtures / integration / profile` を温度感で分割する
- エラー検証は文言完全一致を避け、`phase` と重要断片で判定する
- 通常開発は hot / warm を先に回し、merge 前に cold を含む workspace 全体を回す

### 1.1 テスト温度 taxonomy

| 温度 | 配置 | 目的 | 主な実行単位 |
|---|---|---|---|
| hot | crate-local unit tests | parser / resolver / typechecker / codegen / VM の内部契約を高速に固定する | `cargo nextest run -p <crate>` |
| warm | `tests/fixtures/script/{pass,fail}` / `tests/fixtures/modules/{pass,fail}` | Surtr source fixture の成功 / 失敗と module loading を固定する | `cargo nextest run -p rune --test integration ...` |
| cold | `tests/integration/*.rs` | CLI / process / `.eldr` roundtrip / REPL など外部境界を固定する | `cargo nextest run -p rune --test integration ...` |
| manual | `tests/profile/**` | 性能観測・重い compile path の手動確認に使う | CLI や timing env を明示して実行 |

hot は crate 内部 API で完結させ、外部 I/O を持ち込まない。warm は fixture harness を通して compiler pipeline の意味論を固定する。cold は `surtr` process を起動する境界テストに寄せる。manual は CI の通常 gate へ入れず、性能や負荷観測の入力として扱う。

## 3. テスト種別

### 3.1 Hot: crate-local unit tests

- 配置: `crates/**/src/**` の `#[cfg(test)]`、`crates/*/tests/**`
- 対象: parser / resolver / typechecker / codegen / VM の内部契約
- 外部プロセスや file boundary に依存しない
- 例: `cargo nextest run -p spire`, `cargo nextest run -p scar`

### 3.2 Warm: script pass fixtures

- 配置: `tests/fixtures/script/pass/**`
- 形式: `.srt` + `.expected`
- 判定: `compile -> execute -> stdout` 一致
- 命名: `機能_ケース`（phase 番号を含めない）
- Runner: `tests/integration/run_srt.rs` (`run_srt::spec_fixtures_bucket_0..3`)

例:

- `tests/fixtures/script/pass/functions/top_level_const_literal.srt`
- `tests/fixtures/script/pass/strings/triple_quoted_block_string.srt`
- `tests/fixtures/script/pass/stdmod/result_helpers.srt`
- `tests/fixtures/script/pass/usecases/safebind_list_processing.srt`

### 3.3 Warm: script fail fixtures

- 配置: `tests/fixtures/script/fail/**`
- 形式: `.srt` + `.error`
- `.error` には最低 `phase:` と `contains:` を記載
- Runner: `tests/integration/run_srt.rs` (`run_srt::compile_error_fixtures_bucket_0..3`)

例:

```txt
phase: typecheck
contains: expected Int, got String
```

flow / bind 系では少なくとも次を固定する。

- apply 右辺の裸関数参照拒否
- compose 右辺 / 左辺の call 式拒否
- `|*>` に文脈付き関数を渡したケース
- `|>=` / `>*` / `>=>` の Result/List 混在

### 3.4 Warm: module fixtures

- 配置: `tests/fixtures/modules/pass/**/entry.srt` + `entry.expected`
- 配置: `tests/fixtures/modules/fail/**/entry.srt` + `entry.error`
- 同一 case directory 内の `.srt` は definition source として扱う
- `stageN/` directory は module stage 順を明示する
- Runner: `tests/integration/module_import_fixtures.rs`

### 3.5 Cold: integration

- CLI バイナリ経由で入出力契約を検証
- 対象: `run`, `build`, `dump`, `repl`
- `.srt` と `.eldr` 実行のラウンドトリップを含む
- 現在の主な配置: `tests/integration/*.rs`
- REPL は `crates/xldr/tests/repl_core.rs` を core 契約の正本とし、`tests/integration/repl.rs` は process exit code / banner / quiet / version / pipe stdin / ANSI / stderr diagnostic / cwd 依存 bootstrap failure など CLI 境界専用に寄せる
- `repl --script <file>` は strict script policy で `include` を解決して script を一度実行し、その結果の binding / docs を引き継いだ状態で対話を開始することを `xldr` core と CLI integration の両方で固定する

### 3.6 Profile: manual cold/hot measurement

- 配置: `tests/profile/**`
- nextest の通常対象ではない
- 事前コンパイル / cache / heavy compile の手動測定に使う
- `tests/profile/heavy_compile.srt` は compile path の重い構文・型検査・pipeline 形状を観測するための入力とする
- 詳細は `tests/profile/README.md`

### 3.6.1 実行コマンド

全体 gate:

```bash
cargo nextest run --workspace
```

通常開発向け gate:

```bash
cargo nextest run --profile default
```

`profile default` は crate-local unit と warm fixture を主対象にし、`run_eldr` / `build_roundtrip` / `repl` / `test_command` / `tui` の cold CLI/process 境界テストを既定実行から外す。merge 前や CI では cold を含める。

CI / full gate:

```bash
SURTR_TEST_CACHE=1 cargo nextest run --profile ci --workspace
```

`profile ci` は `all()` を対象にし、final `.eldr` fixture cache を明示的に有効化して repeated run の wall-clock を短縮する。cache miss でも正しく通ることを前提にし、cache は correctness の条件にしない。

cold CLI / process 境界:

```bash
cargo nextest run --profile cold -p rune --test integration
```

warm fixture の部分実行:

```bash
cargo nextest run -p rune --test integration run_srt::spec_fixtures_bucket_0
cargo nextest run -p rune --test integration run_srt::compile_error_fixtures_bucket_0
cargo nextest run -p rune --test integration module_import_fixtures::module_spec_fixtures_bucket_0
cargo nextest run -p rune --test integration module_import_fixtures::module_compile_error_fixtures_bucket_0
```

cold CLI / process 境界の部分実行:

```bash
cargo nextest run -p rune --test integration run_eldr
cargo nextest run -p rune --test integration build_roundtrip
cargo nextest run -p rune --test integration repl
cargo nextest run -p rune --test integration test_command
```

cold/hot timing report:

```bash
rm -rf target/test-fixture-cache
RUST_TEST_THREADS=1 SURTR_TEST_TIMING=1 SURTR_TEST_CACHE=1 cargo nextest run -p rune --test integration run_srt --no-capture
RUST_TEST_THREADS=1 SURTR_TEST_TIMING=1 SURTR_TEST_CACHE=1 cargo nextest run -p rune --test integration run_srt --no-capture
RUST_TEST_THREADS=1 SURTR_TEST_TIMING=1 SURTR_TEST_CACHE=1 cargo nextest run -p rune --test integration module_import_fixtures --no-capture
```

`SURTR_TEST_TIMING=1` は `run_srt` と `module_import_fixtures` で fixture count / elapsed time / slow fixture / cache stats の report を stderr に出す。1 回目を cold、同じコマンドの 2 回目を hot として比較し、semantic prefix cache と final `.eldr` fixture cache の影響を見る。report 用の cache stats は test ごとの開始 / 終了 snapshot 差分で出す。測定時は `RUST_TEST_THREADS=1` を付け、bucket 間の wall-clock と stderr 出力を読みやすく保つ。

### 3.6.2 cache strategy

- semantic prefix cache は常時有効にする
- integration support の prefix cache は `target/test-fixture-cache/prefix` に置く
- `rune test` の prefix cache は `target/surtr-test-cache/prefix` に置く
- final `.eldr` fixture cache は opt-in とし、`SURTR_TEST_CACHE=1` のときだけ `target/test-fixture-cache/eldr` を使う
- `SURTR_TEST_CACHE=1` は final `.eldr` fixture cache だけを gate し、semantic prefix cache を無効化しない
- 標準ライブラリ test script の bytecode cache は `target/surtr-test-cache/eldr/*.eldr` に分離する

### 3.7 Unit viewpoint notes

- クレート内部 API を直接検証
- 外部 I/O を使わない
- 重点: 境界ケース、網羅性、opcode 列妥当性、VM 不正状態
- 現在の観点整理メモ: `tests/unit/*/README.md`

パイプ / bind 系で unit に入れる観点は次を含む。

- lexer の longest-match (`|*>`, `|>=`, `>=>`)
- backtick FuncLiteral の tokenization と unsupported body 拒否
- `Result<List<Int>>` と `>>` の字句衝突回避
- left associative parse
- `Bind < Apply=Compose < Logical < Expr` の優先度固定
- `Expr` クラス算術演算子の同列・左結合固定
- backtick infix (`expr \`name\` expr`, `expr \`+\` expr`) の lower 結果固定
- capture placeholder (`&1`, `&Type::method(&1, ...)`)
- pipe slot `_1` は lexer では `Ident("_1")` のまま、pipe RHS 文脈でだけ特別扱いすること
- `user |> User::get_name()` が通常の call 式として parse されること

### 3.8 標準ライブラリ test script

- 標準ライブラリの回帰テスト正本は `lib/tests/*.srt` に置く
- `surtr test <lib-relative-name>` は `lib/tests/<name>.srt` を script rule で compile / run する
- `surtr test --all` は `lib/tests/**/*.srt` を辞書順に実行する。ただし互換 placeholder の `lib/tests/prelude.srt` と、`include` 専用 schema module を置く `lib/tests/schema/**/*.srt` は対象外とする
- `surtr test --quiet <lib-relative-name|--all>` は成功時の pass 行と成功サマリを出力しない。失敗時は fail 行・詳細・失敗サマリを出力する
- test DSL の正本は通常標準定義ソースの `lib/test.srt` に置き、`StyledDoc` の正本は `lib/styled_doc.srt` に置く
- test DSL は `test > describe > it` の階層を持ち、`it` 本文は `Result<()>` を返す
- assertion helper は Bool 判定系と Result 文脈系を分ける
- test DSL の I/O capture (`Test::capture_stdout`, `Test::capture_stderr`) は per-VM バッファを drain する方式とする
- test DSL の I/O capture は標準 I/O handler backend の差し替えとして扱う
- `surtr test` では `it` ごとに stdout / stderr / stdin buffer を分離し、未読 I/O を次の `it` が観測してはならない
- Pure Surtr code から `Test::capture_stdout`, `Test::capture_stderr`, `Test::assert_stdout_eq`, `Test::assert_stderr_eq`, `Test::push_stdin` を使い、Rust 側テストからも同じ buffer backend を観測できることを固定する
- `lib/tests/**` は通常の `lib/**/*.srt` module 探索に含めない
- test bytecode cache は `target/surtr-test-cache/eldr/*.eldr` に分離する

### 3.4.2 Process Runtime 契約テスト

- Process Runtime の正本は `docs/dev/ProcessRuntime_spec.md` とする
- `tests/fixtures/script/pass/process_runtime/**` は process surface と実行結果の成功系を固定する
- `tests/fixtures/script/fail/process_runtime/**` は `meta`, `meta.state`, Lazy 許可範囲, `ProcessInit<T>` 出現制限, handler override, singleton 利用検査, timeout modifier の失敗を固定する
- `unit/spire` は `meta {}`, `meta.state`, `meta.handlers`, `ctx.<slot>`, `supervisor_init`, `defgenserver`, `defsupervisor`, `@timeout` の parse 境界を固定する
- `unit/sigil` / `unit/scar` は singleton required/available 検査、process state 契約一致、handler capability 検査を固定する
- `unit/forge` / `unit/sindr` は `RuntimeProcessSpec` / `RuntimeBootPlan` の encode/decode と deterministic emission を固定する
- `unit/eldr` は Lazy init retry/deadline、Ready 前 call、`Process::sleep`, timeout, handler init/write failure, singleton slot mismatch を固定する
- `integration/run_eldr` / `build_roundtrip` は `.srt -> .eldr -> run` で process metadata と boot plan が落ちないことを固定する
- Process Runtime 変更後は必要に応じて `cargo nextest run -p eldr`, `cargo nextest run -p rune --test integration run_eldr`, `cargo nextest run -p rune --test integration repl`, `cargo nextest run -p rune --test integration test_command` を組み合わせ、merge 前は `cargo nextest run --workspace` を実行する

### 3.5 deferred 回帰メモ

- 将来仕様を先に固定したいケースは、原則として skipped / ignored テストではなく `doc/open-issues.md` に退避する
- open issue には「何待ちで通常テストへ戻すか」と、退避した最小ケースを残す
- 仕様だけ先行し、まだ AST や IR が揃っていないケースは、仕様確定後に `spec` / `compile_errors` / `integration` へ通常テストとして追加する

### 3.6 前方参照ポリシー固定テスト

- `def` / `defextractor` / `@builtin def` / `@builtin defextractor` / `@builtin type` / `defstruct` / `defrecord` / `deferror` / `defenum` / `deftrait` / `impl` の declaration index 収集を `unit/sigil` で固定する
- generic `defstruct` (`Box<$A>`, `Pair<$A, $B>` など) の type parameter 保持、bare 名 annotation 拒否、arity mismatch、field instantiation を `unit/spire` / `unit/sigil` / `unit/scar` / `spec` で固定する
- declaration index が本体解決なしに構築でき、同一 stage の入力順入れ替えでも結果が変わらないことを固定する
- 同一 stage / 前 stage の前方参照成功ケースを `spec` / `integration` で固定する
- later stage 参照や最終未解決が残るケースを `compile_errors` で固定する
- `unique_id` 決定性と user type tag 決定性を `unit/sigil` / `unit/scar` で固定する
- 型循環は `struct` / `record` / `deferror` の拒否、終了 variant 付き recursive enum の許可、全 variant recursive enum の拒否を `unit/scar` / `compile_errors` で固定する
- 重複トップレベル定義の失敗ケースは既存どおり維持する

### 3.7 標準定義ソース境界テスト

- `Bootstrap` / `Kernel` の auto import と、`Result` など `@autoimport` 付き標準 `impl Type` owner helper surface、および `Eq` / `Concat` / `From` / `TryFrom` / `Encode` / `Decode` / `Show` / `Numeric` など `@autoimport` 付き標準 trait helper の auto import を `spec` / `integration` で固定する
- `@autoimport` が `defmod` / `deftrait` / `impl Type` に付いたときの受理範囲を `unit/spire` で固定し、標準 prelude へ auto import されるのは `defmod`, `deftrait`, `impl Type` に由来する標準 surface に限ることを `unit/sigil` で固定する
- `Bootstrap -> [SpecialTypes, Function, Kernel, Add, Sub, Mul, Eq, Neq, Compare, Concat, Numeric, Show, Ordering, Tuple, From, TryFrom, Encode, Decode, Functor, Chainable, PipeApply, Compose, Composable, LiftComposable, KleisliComposable, Int, String, Regex, Boolean, Error, List, Option, Generator, HashMap, Result, Duration, Process, Facet, Float, Json, Config, Project, Random, File, FS, IO, Shell, StyledDoc] -> [Test] -> ユーザ拡張` のロード順を `integration` で固定する
- 同一 stage 内 import が file 読み込み順に依存せず成功し、later stage import が失敗することを `unit/sigil` / `spec/modules` / `compile_errors/modules` で固定する
- `Script` / `ReplChunk` の top-level `def` が暗黙擬似モジュール所属として扱われることを `integration` / `rune` で固定する
- `Script` では `include` / `import` / `const` / top-level `def` / `namespace` / 型定義 / trait 定義 / `impl` を受理し、explicit top-level `defmod` を拒否することを `unit/spire` / `unit/scar` で固定する
- `Script` の `include` 先頭固定と、最初の top-level expr 以降に宣言を置けないことを `unit/spire` / `compile_errors` で固定する
- 同一 script の top-level expr と top-level `def` body では bare call を維持しつつ、`namespace` / `impl` / include module file / 他 module からは script helper の canonical path で参照することを `unit/sigil` / `spec` で固定する
- `repl --module` と `repl --script` の preload mode は CLI 引数で確定し、追加 file の token sniffing で切り替えないことを `integration/repl` で固定する
- `ReplChunk` では top-level `def` / `import` だけを許可し、`const`、型定義、`impl`、`defmod` を拒否することを `unit/spire` / `integration/repl` で固定する
- `defmod` ネスト禁止と、`defmod` / `impl` / `impl Trait for Type` body で `import` と許可された member 宣言のみを受理することを `unit/spire` / `unit/sigil` / `compile_errors` で固定する
- `impl Type` を型専用の module-like namespace として扱い、`Self` / `self` / `Type::method` / `Type::new` sugar が崩れないことを `unit/sigil` / `spec` で固定する
- 明示 `import` が auto-import 名を shadow できることと、明示 import 同士 / auto-import 同士の同名衝突が失敗することを `unit/sigil` / `compile_errors` で固定する
- 同一 file での module/member 重複 import を `compile_errors` で固定する
- user module / user extension での `@builtin` 利用禁止を `compile_errors` で固定する
- std module での `@builtin type` 受理と、通常 module での拒否を `unit/spire` と `integration` で固定する
- `Bootstrap` source に置いた汎用 error が `Result` / `match` / `eprint` で従来どおり使えることを `spec` で固定する
- operator trait と `Numeric` trait の `Int` / `Float` 実装、`Numeric::safe_div`、bounded generic specialization、`impl Trait` parameter、`-> impl Trait` / `where` の staged error を `unit` / `spec` / `compile_errors` で固定する
- step compile の bytecode 完全一致と、将来の並列 compile 向け bytecode 集合同値観点を `unit` の観点として残す
- 各対応 `lib/*.srt` のトップレベルに canonical builtin type doc が並ぶことと、各 type 標準定義ソースに module-level `@doc` と最低 1 つの定義があることを fixture で固定する
- `List` の公開 surface は `defmod List` 配下の `cons` / `first` / `last` / `at` / `len` / `append` / `concat` / `reverse` / `reduce` / `reduce_while` / `each` / `map` / `flat_map` / `filter` / `find` / `find_map` / `any` / `all` / `count` / `sum` / `take` / `drop` / `partition` / `group_count` / `zip` に固定し、トップレベル関数定義へ戻らないことを `spec` / `integration` / `unit` で守る
- `unit/sindr` では `ListHandle` の runtime 不変条件として、`head_value()` / `tail_handle()` と `len` が空 / 1 要素 / 複数要素で整合することを固定する
- `HashMap` の公開 surface は `defmod HashMap` 配下の `empty` / `from_entries` / `len` / `contains_key` / `get` / `insert` / `remove` / `keys` / `values` に固定し、`HashMap("k" => v)` 表示契約と insertion-order 契約を `spec` / `unit/eldr` / `unit/sindr` で守る
- `re"..."` / `re'...'` が `Regex::compile(...)` に lower されることを `unit/spire` で固定する
- `Regex` wrapper API (`compile` / `captures` / `find` / `replace_all` など) の成功系と失敗系（`RegexCompileError`, `NoneError`）を `unit/eldr` と `integration` で固定する

### 3.7.1 Json / Encode / Decode 契約テスト

- `Encode` / `Decode` は `@autoimport` trait としてロードされ、`encode(...)` / `decode(...)` helper が user code で unqualified に解決できることを `unit/sigil` と `unit/scar` で固定する
- `decode(text, JsonFormat, JsonValue)` と `text |> decode(JsonFormat, JsonValue)` の `TypeRef` witness lowering を `unit/sigil` で固定する
- `encode(value, JsonFormat)` と `value |> encode(JsonFormat)` の `TypeRef` witness lowering を `unit/sigil` で固定する
- `Json::parse` は `null`, boolean, string, integer, decimal, exponent, array, object を `unit/eldr` と `spec/json` で固定する
- `Json::stringify` は object key order が deterministic であることを `unit/eldr` と `spec/json` で固定する
- malformed JSON は `Err(JsonParseError(...))` として観測できることを固定する
- type mismatch は `Err(JsonDecodeError(...))` として観測できることを固定する
- custom `impl Decode<JsonFormat, Config> for JsonValue` が `Json::get(...) |>= decode(JsonFormat, T)` と `=?` で書けることを `spec/json` で固定する
- `Facet::over` / `Facet::set` は decode 後の typed value に適用する例を `spec/json` で固定し、`Decode` の引数に `Facet` を渡す API は追加しない

### 3.8 `@doc` / `.eldr` metadata テスト

- `@doc """..."""` が `defmod` / `def` / `defstruct` / `defrecord` / `deferror` / `@builtin type` / `@builtin def` / `impl Trait for Type` に付くことを `unit/spire` で固定する
- `impl Type` block head では `@doc` / `@hidden` が parse error になることを `unit/spire` で固定する
- `@doc` の dangling case を parse error として固定する
- 同一 declaration / impl member に対する duplicate annotation kind（少なくとも `@doc`, `@autoimport`）を parse error として固定する
- `:doc Ty` が impl helper namespace ではなく canonical type doc を返すことを `unit/xldr` / `integration/repl` で固定する
- `:doc name` が定義 lookup、`:doc $name` が binding lookup であることと、binding doc を暗黙 fallback しないことを `unit/xldr` / `integration/repl` で固定する
- closure を保持する callable binding に対する `:doc $binding` が `Closure` type doc の後に binding 付属 `@doc` 本文を表示し、下段の補足は signature / captures / provenance の最小限にとどまることを `unit/xldr` / `integration/repl` で固定する
- `build -> dump --format json` で `Docs` chunk と `summary.doc_count` が出ることを `integration` で固定する
- 旧 `.eldr` が `Docs` chunk なしでも decode できることを `unit/sindr` で固定する

### 3.9 Deferred 回帰メモの扱い

- 未実装・未確定の将来仕様は、原則として skipped / ignored テストではなく `doc/open-issues.md` に退避する
- 仕様が確定し、実装に着手する段階で `spec` / `compile_errors` / `integration` へ通常テストとして追加する
- `Float` の非有限値や表示規則などの未確定論点は `doc/float.md` に集約する

### 3.10 パイプ / SafeBind の UseCase テスト

- `Result` の段階的検証と表示整形を `>=>`, `>*`, `|>=`, `|*>` の組み合わせで固定する
- `List` の展開と表示整形を `cons`, `|>=`, `|*>` と `List::map` / `List::find_map` で固定する
- `List::cons + List::reverse` ベースの構築スタイルと、`ReduceStep` による early-exit surface を docs に近い usecase で固定する
- `SafeBind.LHS` が MatchBlock として解釈されることを固定する
- `SafeBind` と `Result<List<_>>` の組み合わせを固定する
- docs のサンプルに近い利用例を `spec/usecases` へ置き、構文と実行結果の両方を守る

### 3.11 Facet / private visibility 契約テスト

- `Facet::chain` と `/` の両方を Facet 合成 surface として固定し、`join` 記述を残さない
- `Facet::view` の文脈依存返り型（plain / `Result`）を `unit/scar` と `spec` で固定する
- `Facet::set` / `Facet::over` / `Facet::over_result` の成功・失敗（source `Err`, variant mismatch, `update_fun` 失敗）を `unit/forge` と `spec` で固定する
- Facet path class（field / tuple / list index / map key / required enum / optional enum）と API（`view` / `preview` / `put` / `set` / `over` / `over_result` / `case_set` / `case_over`）の有効・無効組み合わせを `unit/scar`, `unit/forge`, `spec`, `compile_errors` で固定する
- `~source.path` shorthand の expand を `unit/spire`, `unit/scar`, `lib/tests`, `spec`, `compile_errors` で固定する
- shorthand は source 付き Facet API の第1引数でのみ受理し、それ以外では専用 misuse error になることを固定する
- shorthand の API 適格性は expand 後の既存 Facet 規則で判定されることを固定する
- readonly Facet 境界を固定する
- `readonly field` 越しの `Facet::view` は成功
- `readonly field` 越しの `Facet::set` / `Facet::over` / `Facet::over_result` は失敗
- owner による readonly field そのものの置換は成功
- owner であっても readonly field の先への深い mutable traversal は失敗
- `@readonly defstruct` root からの mutable Facet operation は owner を含めて失敗
- Facet の同一スコープ使用規約（関数引数・戻り値・closure capture・container 格納禁止）を `unit/scar` と `compile_errors` で固定する
- `view` 後の plain 値 / `Result` 値は関数境界で受け渡せることを `spec` で固定する
- tuple index `_N` は path segment 専用として固定する
- `value._N` と `Tuple._N`（型文脈あり）は成功、`_N` 単体は失敗、`Tuple._N` のローカル deferred binding は成功として固定する
- `:doc Tuple` が tuple shape、`Tuple._N` FacetPath、`t._1` の値アクセス説明を返すことを `unit/xldr` / `integration/repl` で固定する
- `:sig Tuple` は無効であることを `integration/repl` で固定する
- `:sig Facet::view(...)` / `:sig Facet::set(...)` / `:sig Facet::over(...)` / `:sig Facet::over_result(...)` / `:sig Facet::chain(...)` が command query で許可された引数 surface の範囲で defined / specialized 表示を返すことを `integration/repl` で固定する
- `:facet <FacetPath>` と `:facet $<facet-binding>` が canonical path、segment 一覧、停止点を返すことを `unit/xldr` / `integration/repl` で固定する
- `:facet user.address.name` や `:sig pair._1` のような値 access / 任意式 surface が command query では無効であることを `integration/repl` で固定する
- `:doc` / `:sig` の bare symbol 解決が current scope 準拠であり、auto-import されない helper は import 前に bare 名では見えないことを `unit/xldr` / `integration/repl` で固定する
- command query が literal、任意式、generic type variable を受けず、binding 強制は `$name`、capture は `&to_string` / `&add(Int, &1)` のような restricted surface のみを受けることを `unit/xldr` / `integration/repl` で固定する
- private capability 境界を固定する
- `User.password`（type-root capability）は拒否
- `user.password`（value access）も owner の `impl User` / `impl Trait for User` 外では拒否
- closure 内 private access（例: `{|| user.password}`）も field access と同じ規則で拒否
- `return user.password` も owner 外では拒否、owner 内では plain value return として許可

## 7. クレート別テスト観点

### 7.1 sindr

- 観点: `Bytecode` 互換（encode/decode）、新チャンク集合（`Code` / `Cnst` / `Func` / `Type` / `ErrT` / `CInf` / `LblT` / `ImpT` / `ExpT` / `LitT` / `Line` / `SpnT` / `SrcP` / `PcSp`）の往復、`FunctionEntry` metadata（`qualified_name` / `end_pc` / flags / span）互換、`BuiltinMeta` 整合、`Value` 表示規則、`Int=BigInt` の直列化
- CriticalCase: 必須チャンク欠落、重複 tag、未知 tag、`LblT` / `Func` の範囲外 pc、`ImpT` / `ExpT` の無効参照、`LitT` と `Cnst` の不整合、tag と user `Int` の混線

### 7.2 spire

- 観点: 優先順位/結合規則、複数行 Incomplete、補間文字列トークナイズ、named args 構文境界、超大整数 tokenization、`parse_with_context_diagnostic` の expected token / cursor span / LSP range 変換
- CriticalCase: ネスト式の優先順位、補間内構文エラー span、EOF 直前 Incomplete、`BigInt` 化後の負数パターン、LSP 診断の line/column オフセットずれ

### 7.3 sigil

- 観点: shadowing、自由変数 capture、declaration index 収集、トップレベル宣言事前登録（`def` / `defextractor` / `@builtin def` / `@builtin defextractor` / `@builtin type` / `defstruct` / `defrecord` / `deferror` / `defenum` / `deftrait` / `impl`）、`if` 専用ノード化、file 単位 import 状態
- CriticalCase: ネスト closure の capture 解決、`@builtin` 未定義検出、constructor / extractor 衝突、構造体名と `new` の非 import、明示 import による auto-import shadowing、明示 import 同士 / auto-import 同士の衝突、module/member 重複 import、declaration index 決定性、`unique_id` 決定性、同一 stage / 前 stage 前方参照、later stage 参照拒否

### 7.4 scar

- 観点: 型互換、型名/コンストラクタ名/Extractor 名のシグネチャ先行登録、型 predeclare と user type tag 決定性、型循環検出、`match` 網羅性、`=?` 文脈制約、Extractor 専用 `MatchResult<$Value, Error>` / tuple payload 契約、補間の `Result` 禁止
- CriticalCase: Bool/Result/Int/String の非網羅、`SafeBind.LHS` / `matchArm.LHS` の MatchBlock 解釈、`=?` の不正 RHS、`Option` の SafeBind 非対象、Extractor の返り値契約違反、Extractor 外 `MatchResult` 禁止、`Seq` 型拒否、tuple arity mismatch、関数戻り値不一致、前方参照での型注釈とコンストラクタ呼び出し、`struct` / `record` / `deferror` 型循環拒否、recursive enum 許可/拒否境界

### 7.5 forge

- 観点: TypedNode -> Opcode 列、`fun_idx == index` 不変条件、`lexical_captures` 順序、未解決 label の hard failure、`match` mismatch failure の明示化、Extractor の `Success / NoMatch / Err` lowering
- CriticalCase: 呼び出し arity、`CaptureClosure` 順序、`Return` 配置、未解決 jump label、最終 arm 不一致時の `PatternMismatch`、Extractor error の即時伝播

### 7.6 eldr

- 観点: CallFrame 規約、fail-fast、`fun_idx` 直参照、jump/local/tag 異常系、`Return` 規約
- CriticalCase: top-level `Return`、`LoadLocal` 範囲外、invalid jump、unknown function index、`CallClosure` arity mismatch

### 7.7 rune

- 観点: CLI 契約（run/build/dump/repl）、`.srt/.eldr` roundtrip、dump JSON 互換、REPL 状態継続、標準定義ソースロード契約
- CriticalCase: build デフォルト出力、dump スキーマ、module 定義関数の `qualified_name` 表示、REPL エラー後状態保持、`:v` 再表示、標準定義ソースロード順序崩れ、script の include 順序違反、script の expr 後宣言拒否、REPL での `const` / 型定義拒否
- REPL core 契約は `xldr` で直接検証し、Rune integration では banner / quiet / version / pipe stdin / prompt 出力 / ANSI / stderr diagnostic / cwd 依存 bootstrap failure のような CLI 境界を優先する

- `tests/integration/run_srt.rs`
  - script front-end の fixture ランナーとして扱い、single-file `.srt` の script 制約を固定する
- `tests/integration/module_import_fixtures.rs`
  - module loading / staging / multi-source fixture の基盤ランナーとして扱い、script entry と definition source を分離したケースを固定する

## 9. デグレ事前予防ルール

- バグ修正時は再発ケースを同一 PR に追加する
- 仕様差分は `tests/fixtures/script`、`tests/fixtures/modules`、または crate-local unit に必ず反映する
- VM/bytecode 変更時は `eldr` 単体と `rune` integration の両方を実行する
- エラー系検証は全文一致ではなく `phase + contains` を使う
- 標準定義ソース定義（現行実装: `bootstrap.srt` / `kernel.srt`）と実装の整合チェックを CI で常時実行する
- 前方参照ポリシー変更時は、成功系（同一 stage / 前 stage で解決可能）と失敗系（later stage 参照 / 最終未解決）を必ず対で更新する
- 並列化導入後も、ID/tag と診断内容が実行スケジュール非依存であることを回帰テストで保証する
