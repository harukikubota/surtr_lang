# Surtr テスト方針

> 目的: フェーズ名ベースのテスト管理をやめ、仕様ベースのテスト体系へ移行する。

---

## 1. 基本方針

- テストの主語を「実装フェーズ」ではなく「言語機能」にする
- E2E 偏重を解消し、`unit / fixtures / integration / profile` を温度感で分割する
- エラー検証は文言完全一致を避け、`phase` と重要断片で判定する
- 通常開発は hot / warm を先に回し、merge 前に cold を含む workspace 全体を回す
- nextest は `rtk cargo nextest` 経由で実行する。`surtr test` は自身の `--quiet` で成功出力を抑え、`rtk proxy` 経由で診断と終了コードをそのまま保持する

通常ソースの名前解決・型検査・実行テストは共通の標準環境を前提とする。autoimport の切替引数や標準なしの通常実行経路は設けない。owner / scope など内部構造そのもののテストは、その契約を直接検証してよい。標準 source inventory は `crates/sindr/src/stdlib.rs` を共有し、テストごとに標準関数を仮定義しない。

### 1.1 テスト温度 taxonomy

| 温度 | 配置 | 目的 | 主な実行単位 |
|---|---|---|---|
| hot | crate-local unit tests | parser / resolver / typechecker / codegen / VM の内部契約を高速に固定する | `rtk cargo nextest run -p <crate>` |
| warm | `tests/fixtures/script/{pass,fail}` / `tests/fixtures/modules/{pass,fail}` | Surtr source fixture の成功 / 失敗と module loading を固定する | `rtk cargo nextest run -p rune --test integration ...` |
| cold | `tests/integration/*.rs` | CLI / process / `.eldr` roundtrip / REPL など外部境界を固定する | `rtk cargo nextest run -p rune --test integration ...` |
| manual | `tests/profile/**` | 性能観測・重い compile path の手動確認に使う | CLI や timing env を明示して実行 |

hot は crate 内部 API で完結させ、外部 I/O を持ち込まない。warm は fixture harness を通して compiler pipeline の意味論を固定する。cold は `surtr` process を起動する境界テストに寄せる。manual は CI の通常 gate へ入れず、性能や負荷観測の入力として扱う。

## 3. テスト種別

### 3.1 Hot: crate-local unit tests

- 配置: `crates/**/src/**` の `#[cfg(test)]`、`crates/*/tests/**`
- 対象: parser / resolver / typechecker / codegen / VM の内部契約
- 外部プロセスや file boundary に依存しない
- 例: `rtk cargo nextest run -p spire`, `rtk cargo nextest run -p scar`
- Scar の stdlib-backed surface case は process-local prelude を共有する case registry へ登録し、8 bucket から実行する。registry 外の個別 `#[test]` に戻さず、`dead_code` deny と inventory test で登録漏れ・重複を拒否する
- `structured_diagnostics` など小さい stdlib-backed test target は case suite に集約し、assertion 本体は関数として保つ
- Forgeの標準prefixを使う19ケースは、既存の4 bucketから実行する。arity上限、特殊enum capture、trait opcode、Facet captureのケースも同じregistryへ登録し、入力とassertionを保持する
- `type_constructor_carriers`、`return_type_arguments`、`default_trait_methods`、`trait_method_type_lists`、`nominal_constructor_parameters`の通常ケースも、各8 bucketのregistryで標準prefixを共有する。`support/case_registry.rs`が登録漏れ・名前と関数の重複・個別テストとの併用を検査する。標準定義を置き換える`default_trait_methods`の4ケースは、独立した全体検査として個別に実行する

### 3.2 Warm: script pass fixtures

- 配置: `tests/fixtures/script/pass/**`
- 形式: `.srt` + `.expected`
- 判定: `compile -> execute -> stdout` 一致
- 命名: `機能_ケース`（phase 番号を含めない）
- Runner: `tests/integration/run_srt.rs` (`run_srt::spec_fixtures_bucket_0..7`)

例:

- `tests/fixtures/script/pass/functions/top_level_const_literal.srt`
- `tests/fixtures/script/pass/strings/triple_quoted_block_string.srt`
- `tests/fixtures/script/pass/stdmod/result_helpers.srt`
- `tests/fixtures/script/pass/usecases/safebind_list_processing.srt`

### 3.3 Warm: script fail fixtures

- 配置: `tests/fixtures/script/fail/**`
- 形式: `.srt` + `.error`
- `.error` には `phase:`、内容のある `contains:`、`json:` のいずれかの検証条件を1つ以上記載する。失敗フェーズと原因を固定する場合は `phase:` と `contains:` を併記する。空ファイル、コメントのみ、空の `contains:` は拒否する
- Runner: `tests/integration/run_srt.rs` (`run_srt::compile_error_fixtures_bucket_0..15`)

例:

```txt
phase: typecheck
contains: expected Int, got String
```

構造化診断は `.error` に `json: /JSON/pointer = JSON値` を追加し、Scar の実エラーから生成した JSON を照合する。
`reason` / `origin` / `data` / `related` の必要なフィールドを指定する。`null` は key の存在も検証し、key 欠落とは区別する。

```txt
phase: typecheck
json: /reason = "ArgumentTypeMismatch"
json: /origin/kind = "Call"
json: /data/expected_type = "Int"
json: /data/actual_type = "String"
```

### 3.4 Facet / Hole contract

- `Facet<K, S, A, T, B>` の arity は常に 5 とし、旧 2-slot annotation は失敗 fixture で固定する
- Facet の deferred update slot は `_, _` の組だけを許可し、`Hole` の直接表記は reserved-type error にする
- `set` は focus と完全一致する replacement だけを受け入れる。Result focus への暗黙 `Ok` wrap は失敗 fixture で固定する

flow / bind 系では少なくとも次を固定する。

- `_` input callable を `|*>` / `|>=` に渡すケース。grouped生成Callと関数値束縛の両方を検証し、空・非空carrierで生成式の評価が一度であることを確認する
- groupingを介した通常引数・注釈・返り値・分岐の期待関数型伝播。入力型・返り型・引数数の不一致は拒否する
- apply 右辺の裸関数参照拒否
- 合成の左右で、型契約に合う関数値を返す関数呼出しを受理し、関数値を返さない呼出しと引数不足の呼出しを拒否する。合成では引数を注入しない
- `|*>` に文脈付き関数を渡したケース
- `|>=` / `>*` / `>=>` の Result/List 混在

### 3.4 Warm: module fixtures

- 配置: `tests/fixtures/modules/pass/**/entry.srt` + `entry.expected`
- 配置: `tests/fixtures/modules/fail/**/entry.srt` + `entry.error`
- 同一 case directory 内の `.srt` は definition source として扱う
- `stageN/` directory は module stage 順を明示する
- Runner: `tests/integration/module_import_fixtures.rs`

### 3.5 Cold: integration

- CLI バイナリ経由で入出力契約を検証
- 対象: `run`, `build`, `dump`, `repl`
- `.srt` と `.eldr` 実行のラウンドトリップを含む
- 現在の主な配置: `tests/integration/*.rs`
- REPL は `crates/xldr/tests/repl_core.rs` を core 契約の正本とし、`tests/integration/repl.rs` は process exit code / banner / quiet / version / pipe stdin / ANSI / stderr diagnostic / cwd 依存 bootstrap failure など CLI 境界専用に寄せる
- Xldr REPL core は semantic case を source order の stable table に 1 回ずつ登録し、`index % 8` の 8 bucket と name / function 重複を検出する inventory test 1 本で実行する。default REPL bootstrap state を process 内で 1 回だけ構築し、各 engine へ独立した VM / session state を復元する現行経路では、schema 12 の `std.semantic` を実ヒットさせた `profile ci` 実測で 9/9 成功、全体 7.180s であることを確認した
- `repl --script <file>` は strict script policy で `include` を解決して script を一度実行し、その結果の binding / docs を引き継いだ状態で対話を開始することを `xldr` core と CLI integration の両方で固定する

### 3.5.1 継続実行と予算の契約テスト

- `unit/eldr` は builtin / callback の開始・再開・完了・失敗、quantum 0 / 1 / 複数 step、子から親への復帰を固定する。callback の opcode と builtin の状態遷移で予算を共有し、戻り値・副作用を一度だけ配送する。
- CPU の yield と Future 待機を別々に検証する。Runnable の再登録、Waiting の wakeup、queue の重複防止と、別の runnable task が未完了の処理の途中で進むことを確認する。
- direct / closure / tail closure / partial / inject / compose、recover wrapper、file wrapper、Task / process handler を共通 driver で実行する。file は中断中の生存と完了・失敗後の flush / close、process は state 更新と reply 配送を確認する。
- 通常の batch / REPL / Task / process 入口から予算切れ・待機・再開を確認する。テスト専用 scheduler 呼出しだけでは入口の検証を代用しない。
- REPL checkpoint / rollback は中断状態を独立に保存し、保存位置から再開することを確認する。callback の再呼出し、未完了状態の結果への露出、待機後の trace 欠落を拒否する。
- 仮想操作数は決定的な入力で数える。実時間、allocator、要素の clone / drop、RSS に閾値を設けず、未分割の外部呼出しを公平性の保証範囲に含めない。

### 3.5.2 List の表現と構築操作

- `unit/sindr` は Empty / Cons / Packed / 混在 List の長さ、head、tail、論理順の equality・Debug・表示を固定する。buffer の所有権移動と tail の共有は pointer と開始位置で確認し、実時間を測らない。
- `unit/eldr` は flat_map の入力訪問・callback・出力追加を数える。singleton、空結果、巨大な mapper 結果、三段の直積、多段 singleton を使い、旧 `2E` Cons と新 `E` Builder 追加を比較する。多段に残る `kM` も検証する。
- List の opcode、Facet、JSON などの consumer は、内部 field を読まず ListHandle API を使う。表現追加のために opcode や bytecode schema を増やさない。
- 標準 List / do テストは混在 List の代数則、mapper の順序と回数、partial pattern・SafeBind・guard、Transformer の既存契約を検証する。
- Forge / script / REPL / build roundtrip は通常の `CallBuiltin`、capture、template、pipe、Kleisli、checkpoint の入口を固定する。中断中の Builder が結果へ出ないこと、rollback 後も一度だけ再開することを確認する。

### 3.6 Profile: manual cold/hot measurement

- 配置: `tests/profile/**`
- nextest の通常対象ではない
- 事前コンパイル / cache / heavy compile の手動測定に使う
- `tests/profile/heavy_compile.srt` は compile path の重い構文・型検査・pipeline 形状を観測するための入力とする
- 詳細は `tests/profile/README.md`

### 3.6.1 実行コマンド

全体 gate:

```bash
rtk cargo nextest run --workspace
```

通常開発向け gate:

```bash
rtk cargo nextest run --profile default
```

`profile default` は crate-local unit と warm fixture を主対象にし、`run_eldr` / `build_roundtrip` / `repl` / `test_command` / `tui` の cold CLI/process 境界テストを既定実行から外す。merge 前や CI では cold を含める。

CI / full gate:

```bash
SURTR_TEST_CACHE=1 rtk cargo nextest run --profile ci --workspace
```

`profile ci` は `all()` を対象にし、final `.eldr` fixture cache を明示的に有効化して repeated run の wall-clock を短縮する。cache miss でも正しく通ることを前提にし、cache は correctness の条件にしない。

`profile ci` と `profile cold` は test binary の build / list 後、test process 開始前に `scripts/ci-stdlib-prewarm.sh` を workspace root で 1 回実行する。script は `tests/profile/stdlib_prewarm.srt` を `surtr check` し、default stdlib variant の content-addressed semantic snapshot `std.semantic` と Scar テスト用の標準 prefix を準備する。test-enabled variant の `std.test.semantic` と final `.eldr` fixture cache は準備しない。後者は上記コマンドの `SURTR_TEST_CACHE=1` を明示したときだけ有効になる。

cold CLI / process 境界:

```bash
rtk cargo nextest run --profile cold -p rune --test integration
```

Scar 専用の setup は設けない。`ci` / `cold` の全体用 `scripts/ci-stdlib-prewarm.sh` に Scar の準備もまとめる。`default` は全体・部分実行とも setup を行わず、テスト側がキャッシュを読み、miss 時だけ排他制御して構築する。標準定義の名前解決と型検査を先に済ませ、各 test process は checkpoint と名前解決の再開位置を読み込む。AST の parse と宣言の収集は各 process で行い、個別の test 名と失敗の分離を維持する。標準定義を差し替える契約テストは、この共通 prefix を利用せず差し替えた source を検査する。

事前準備は通常の debug build を使う。`--release`、独自の Cargo profile、異なる Rust flags で Scar を検証すると、準備側と test 側の指紋が異なる場合は load error になる。同じ build 条件で直接 `cargo test -p scar` を実行する場合は、各 process が cache を読み、miss 時だけ process 間排他で準備する。

warm fixture の部分実行:

```bash
rtk cargo nextest run -p rune --test integration run_srt::spec_fixtures_bucket_0
rtk cargo nextest run -p rune --test integration run_srt::compile_error_fixtures_bucket_0
rtk cargo nextest run -p rune --test integration module_import_fixtures::module_spec_fixtures_bucket_0
rtk cargo nextest run -p rune --test integration module_import_fixtures::module_compile_error_fixtures_bucket_0
```

cold CLI / process 境界の部分実行:

```bash
rtk cargo nextest run -p rune --test integration run_eldr
rtk cargo nextest run -p rune --test integration build_roundtrip
rtk cargo nextest run -p rune --test integration repl
rtk cargo nextest run -p rune --test integration test_command
```

cold/hot timing report:

```bash
rm -rf target/test-fixture-cache
RUST_TEST_THREADS=1 SURTR_TEST_TIMING=1 SURTR_TEST_CACHE=1 rtk cargo nextest run -p rune --test integration run_srt --no-capture
RUST_TEST_THREADS=1 SURTR_TEST_TIMING=1 SURTR_TEST_CACHE=1 rtk cargo nextest run -p rune --test integration module_import_fixtures --no-capture
```

`SURTR_TEST_TIMING=1` は `run_srt` と `module_import_fixtures` で fixture count / elapsed time / slow fixture / cache stats の report を stderr に出す。1 回目を cold、同じコマンドの 2 回目を hot として比較し、semantic prefix cache と final `.eldr` fixture cache の影響を見る。report 用の cache stats は test ごとの開始 / 終了 snapshot 差分で出す。測定時は `RUST_TEST_THREADS=1` を付け、bucket 間の wall-clock と stderr 出力を読みやすく保つ。

### 3.6.2 cache strategy

- semantic prefix cache は常時有効にする
- integration support の prefix cache は `target/test-fixture-cache/prefix` に置く
- `rune test` の prefix cache は `target/surtr-test-cache/prefix` に置く
- final `.eldr` fixture cache は opt-in とし、`SURTR_TEST_CACHE=1` のときだけ `target/test-fixture-cache/eldr` を使う
- `SURTR_TEST_CACHE=1` は final `.eldr` fixture cache だけを gate し、semantic prefix cache を無効化しない
- 標準ライブラリ test script の bytecode cache は `target/surtr-test-cache/eldr/*.eldr` に分離する
- `profile ci` / `profile cold` の stdlib setup は default stdlib semantic snapshot だけを test process より先に作成する。cache key は stdlib source と semantic schema / metadata から導出し、file がない場合、key が異なる場合、または壊れている場合は通常の stdlib compile を行うため、cache hit は correctness 条件ではない
- stdlib semantic snapshot と test-related semantic prefix の miss は cache path ごとの `.lock` file で process 間排他し、lock 取得後に同じ key を再読込する。再読込も miss の process だけが build / store を行う。lock file を作成または lock できない環境では cache を correctness 条件にせず通常 compile を行う
- Scar の test-only prefix は `target/scar-test-cache/<key>.prefix` に置く。key は test-only の `scar-test-cache-key` crate の build 時に生成し、Scar と上流 compiler crate の source、manifest / Cargo.lock、標準定義、test support、target / host、Cargo profile / debug / optimization 設定、Rust flags と rustc identity を含める。変更後の source を古い binary の実行時に読む方式は使わない
- Scar の cache miss は file lock 取得後に再読込し、miss が残る process だけが標準 prefix を構築する。一時 file から rename して公開する。各 case は checkpoint を clone して session を復元し、binding や型検査の変更を他の case と共有しない
- Scarの永続definition、trait宣言・実装、canonical callable signature、型定義とenum metadataは、不変の間だけcheckpoint・session・子checker間で共有する。関数indexの書換え、trait義務と継承slot、型定義の署名・field policy・span、enum一覧の更新は、変更する値だけを複製する。変数binding・fresh ID・scope undoは独立した所有値に保つ。呼出しごとの型変数生成とsignature具象化は独立した所有値を作る。保持checkpointと兄弟sessionへの変更漏れ、拒否後の独立session、rollback、serialize往復をcrate-localで検証し、実時間に閾値を設けない
- Scar の prefix は schema / key / payload checksum を検証する。壊れた file、読込・lock・保存の失敗、setup が指名した file の不存在は明示的に失敗させる。破損を通常 compile へ fallback して隠さない。破損時は診断に出た cache file を削除してから再実行する
- Xldr の default REPL bootstrap state は semantic snapshot から source / scope / Scar checkpoint / bytecode metadata を process 内で 1 回だけ構築する。各 `ReplEngine` は bytecode から VM を新規生成して runtime boot を実行し、Sigil / Scar session state を clone するため、binding・runtime state を engine 間で共有しない。`.eldr` scope restore では snapshot の stage layout と stdlib の function / type / callable / process prefix を検証し、不一致時は source bootstrap へ fallback せず load error にする

### 3.7 Unit viewpoint notes

- クレート内部 API を直接検証
- 外部 I/O を使わない
- 重点: 境界ケース、網羅性、opcode 列妥当性、VM 不正状態
- 現在の観点整理メモ: `tests/unit/*/README.md`

パイプ / bind 系で unit に入れる観点は次を含む。

- lexer の longest-match (`|*>`, `|>=`, `>=>`)
- backtick FuncLiteral の tokenization と unsupported body 拒否
- `Result<List<Int>>` と `>>` の字句衝突回避
- left associative parse
- `Bind < Apply=Compose < Logical < Expr` の優先度固定
- `Expr` クラス算術演算子の同列・左結合固定
- backtick infix (`expr \`name\` expr`, `expr \`+\` expr`) の lower 結果固定
- capture placeholder (`&1`, `&Type::method(&1, ...)`)
- data constructor capture (`&User`, `&User(&1, ...)`, `&Enum::Variant`, generic Enum owner)
- pipe slot `_1` は lexer では `Ident("_1")` のまま、pipe RHS 文脈でだけ特別扱いすること
- `user |> User::get_name()` が通常の call 式として parse されること

### 3.8 標準ライブラリ test script

- 標準SRTテストは公開APIと言語契約を主語にし、`basic_types`・`monads`・`traits`・`modules`・`language_features` に分類する
- `rtk cargo build -p rune` 後、`rtk proxy ./target/debug/surtr test --quiet <file-path|--all>` で実行する
- 単体の相対パスは起動時CWD、絶対パスは指定ファイルを読む。親ディレクトリ・symlinkも通常のファイル指定とし、trim・区切り変換・拡張子補完・lib/testsへの付け替えをしない
- 開発用debugビルドのallは `lib/tests/*/*.srt` の相対2成分の入口を辞書順に列挙する。root直下・3成分以上のsupportは実行せず、カテゴリallowlist・再帰・basename除外は設けない。切れたsymlinkとdirectory symlinkも読み取り時に異常として報告する
- 各入口を単体と同じ読み込み・include・fingerprint・コンパイル経路へ渡し、独立したVMで順次実行する。対象0件は終了コード1、ファイル異常は集計して後続へ進む
- quietは成功出力を省略し、失敗・異常を保持する。all discoveryとIO分離のCLI契約はRust境界で直接検証する
- 補助定義は複数入口で必要な最小宣言だけsupportに置く。値・枝・種別は目的別アサーション、表示とIOはその専用観測で検証する。setup/cleanupとアサーションのResultをケース結果へ接続する
- 標準SRTテストの各 `it` 本文は、準備からアサーションまでを一つの `do { ... }` にまとめる。carrierは本文の `Result<()>` から推論させ、指定しない。準備とアサーションは空行で区切り、`do` を区切りとして増やさない
- Resultを検証対象として保持する束縛は `=`、成功値を取り出して後続へ進む束縛は `<-` を基本とする。通常の束縛、Resultを返す処理、アサーションは同じ `do` 内に記述する
- 分割が必要な計算、`do` 自体を検証する計算、失敗時にもcleanupを行うため結果を保持する計算は、ファイル内のフィクスチャ関数へ分ける。検証対象のcarrier指定やSafeBindはその関数内に保持する
- リリースビルドにおけるallの対象・振る舞いは未確定とし、開発用の標準テスト契約から推定しない
- API追加・仕様変更時は成功、空値・端点、拒否、短絡、評価回数のうち必要な条件を更新する
- 型の標準trait実装はその型の入口、独自型へのimpl・既定メソッド・型コンストラクタ制約はtraitsで検証する。Functor・Applicative・Monad・MonadTの法則は両辺の観測可能な結果を比較する
- 標準関数を呼ぶだけのwrapper、業務ロジック、複数APIを束ねる独自trait、旧schema・総合Spec・互換入口は置かない。短い入力mapper/predicateはケース内closureを基本とし、独自型・implや検証対象のdo計算、cleanupを保つフィクスチャ関数など必要な宣言だけファイル先頭または共有supportに置く
- Eqがない値の比較用にEq/Showを追加しない。関数は呼出結果、Reader/State/Generatorはrun/next等の公開APIの結果を検証する
- 無関係な結果をTuple/Listへまとめて比較しない。自然なTuple戻り値も一度評価して要素別に検証する。Tuple自体の構造、Listを返すAPI、出力entry列は直接比較してよい
- Errorの種別・cause・messageはそれぞれ明示して検証する。ResultのErr同士のEqは先頭種別だけを比較し、causeとmessageの代用にしない
- inspectは表示自体・エスケープ・opaque値の非評価など表示契約だけに使う。出力entryは呼出し単位で比較し、未読出力を無目的に捨てたり物理行へ独自分割したりしない。入力はpush_stdinで供給する
- setupや外部副作用はit内に置く。File/FSはケース固有のパスと初期状態を使い、検証Resultを保持して失敗時もcleanup・cwd復元を実行する。setup/cleanupの失敗もケース結果へ反映する
- Testのアサーション自体、CLIの終了コード・集計・フィルター・一覧・IO分離は既存Rustテストで検証する。構文・型の拒否は各phaseの直接テストまたは拒否fixtureへ置き、SRTの公開APIケースへ重複させない
- test DSL の正本は通常標準定義ソースの `lib/test.srt` に置き、`StyledDoc` の正本は `lib/styled_doc.srt` に置く
- test DSL は `test > describe > it` の階層を持ち、`it` 本文は `Result<()>` を返す
- 各 `it` は本文の Result を一件の成否として記録する。アサーションを個別に集計せず、テストは直列に実行する
- 標準SRTテストでは単一アサーションも `do` 内に置く。最初の Err を本文から返し、その `it` の後続処理を実行しない。`it` は記録後に `Ok(())` を返して次の `it` へ進む。VM の実行異常を回復する契約ではない
- 期待する Err の検証対象は通常の束縛か直接引数で保持し、検証前に伝播しない。これらの記述方針は `lib/tests` に適用し、言語構文やtest DSLへ新しい拒否規則を追加しない
- 文末 `?` は成功型の終端が Unit の Result に使い、文自体の型は Unit とする。Result を返す関数・closure の末尾では、通常の型不一致として拒否する境界を固定する。途中の Unit を使えるブロックまで構文で禁止しない。構文・型の拒否境界は Spire / Scar、失敗後の短絡、次の `it` と I/O 分離は script / test CLI の直接テストで固定する
- 未使用の非 Unit 値をユーザーへ警告する機能は別改修とする。文末 `?` は明示的に成功値を捨てる Unit 文なので、未使用の Result 値として扱わない
- assertion helper は Bool 判定系と Result 文脈系を分ける
- test DSL の I/O capture (`Test::capture_stdout`, `Test::capture_stderr`) は per-VM バッファを drain する方式とする
- test DSL の I/O capture は標準 I/O handler backend の差し替えとして扱う
- `surtr test` では `it` ごとに stdout / stderr / stdin buffer を分離し、未読 I/O を次の `it` が観測してはならない
- Pure Surtr code から `Test::capture_stdout`, `Test::capture_stderr`, `Test::assert_stdout_eq`, `Test::assert_stderr_eq`, `Test::push_stdin` を使い、Rust 側テストからも同じ buffer backend を観測できることを固定する
- `lib/tests/**` は通常の `lib/**/*.srt` module 探索に含めない
- test bytecode cache は `target/surtr-test-cache/eldr/*.eldr` に分離する

### 3.4.2 Process Runtime 契約テスト

- Process Runtime の正本は `docs/dev/ProcessRuntime_spec.md` とする
- `tests/fixtures/script/pass/process_runtime/**` は process surface と実行結果の成功系を固定する

### 3.6.1 Trait coherence / call-site 型推論テスト

実装上の identity、solver lifecycle、phase boundary は [`Trait_system_spec.md`](./Trait_system_spec.md) を正本とし、この節は test matrix と fixture 配置を定める。

- `CanonicalUnifier` の単項入れ子型は深さ 32 / 64 / 128 / 256 で比較し、入力構築を除いた割当回数を crate-local テストで固定する。一致・末端不一致・末端変数・constructor identity の Hole を含め、時間は参考計測として出力する。rigid、間接 occurs check、ignored input の判定時点も同じ層で検証する
- impl pattern の alpha-normalization と recursive unification は `unit/scar` で固定する。generic は任意の型 pattern と一致し、tuple/function/nominal type application の各構成要素を再帰照合する
- `$A` 対 `Int`、`List<$A>` 対 `List<Int>`、`Pair<$A, Int>` 対 `Pair<String, $B>`、trait argument 側の generic 対 nested concrete を `compile_errors` で固定する
- overlapping impl は各 pair の宣言順を逆にした fixture も置き、同じ typecheck phase/error kind で失敗することを固定する
- 同じ nominal target の `List<Int>` 対 `List<String>` のように recursive unification 不能な pattern は成功系とし、full impl identity のまま Forge まで到達することを固定する
- 異なる `where` constraint を持つ overlapping pattern も V1 では拒否し、impl-level `where` obligation を満たさない concrete dispatch は typecheck で拒否する
- trait solver は unit test で deferred obligation の具体化時再検査、rigid generic の未宣言 bound、child `where` assumption による parent coverage、generic argument を保つ有限再帰 obligation を確認する。surface fixture は各診断と利用者向け挙動を固定する
- normal `where` bound は `$T: Trait` の成功と、`$T: Trait<...>` の parser failure を trait definition / impl / function / trait method の全位置で固定する。special `Self` LHS でも `Self: Parent<$Tag>` は parser failure とし、`Self: Type<...>` だけを shape RHS として残す。trait / impl head と expression call の `TryConvert<$To>` / `try_to::<$To>(...)` は成功系に残す
- `Self: Type<$A>` は trait-definition where の `Self` だけで成功し、他 LHS・function / impl / method where では失敗させる。Trait-head parameterを持つTypeConstructor traitは`deftrait T<$P> where ...`として成功し、`deftrait T<$P: Bound>`は`where $P: Bound`へのhelp付きで失敗させる。`Trait.$Slot` は独立 slot-map RHS として成功／通常 trait での失敗を固定する
- constructor application は通常関数／trait method signature の direct parameter・return、または対応する`where` constraintを持つnominal field/payloadで成功し、local / non-nominal field / nested / closure signatureの不正位置は parser failure にする。call-site TypeCtorTrait RTAではconstructor head、完全・部分型application、`_`を受理し、外側constructor variableだけを拒否する。parameter witness は位置ごとに独立、return witness は fresh concrete result とし、分岐 constructor 不一致・未確定 return を TypeError にする
- bare capability は trait call、operator lowering、generic call への proof 引渡しで消費される成功を固定し、unused capability（function、trait / impl method、impl block）を `UnusedTraitConstraint` TypeError にする。parent / shape / slot map は未使用判定の対象外とする
- obligation の失敗 fixture は `phase = typecheck` と目的の error kind/message を確認し、impl head / expression call の exact trait argument と mismatch を対にする。full `(trait_id, trait_args, receiver)` obligation は specialization 後も保持し、Scar-before-Forge audit が branch、match arm、closure、aggregate の pending dispatch を拒否することを固定する
- overlap は Scar の impl predeclare で検出し、Forge の duplicate function index/CodegenError へ進まないことを `integration` で固定する
- `Convert` / `TryConvert` の排他は generic 名だけを変えた alpha-equivalent pair、generic/concrete pair、nested pair、宣言逆順を `compile_errors` で固定し、構造的に disjoint な pair は成功系で固定する
- `defmod` / inherent `impl` / trait `impl` の同名 callable、および `def` と `defp` の同名衝突を `unit/sigil` / `compile_errors` で固定する。signature や visibility の違いによる overload も拒否する
- 未具体化 closure / capture / ExtractorClosure の変数束縛を拒否し、concrete callable 注釈付き束縛を受理することを `unit/scar` / `compile_errors` で固定する
- capture した外部型と外側 signature の rigid generic は保持しつつ、新しい local callable scheme を generalize しないことを `unit/scar` で固定する
- 未束縛 generic へ closure / capture / ExtractorClosure、scalar literal、tuple、non-empty list、constructor result を直接渡し、expected type から具体化する成功系を `unit/scar` / `spec` で固定する
- named / builtin Extractor の裸 generic target と Trait `where` 一般化を拒否し、`List<$T>` / `Result<$T>` の concrete head を受理する。List / String の `uncons` は各適用で concrete な静的契約を持つことを固定する
- ordinary call、constructor、trait helper、`|>`、`>>`、`>*`、`>=>` は同じ actual expression で同じ型を得る対称 fixture を置く
- list element、tuple slot、`if` の全 branch、`match` の全 arm へ expected type が伝播することを固定し、最初の branch/arm の順序を逆にしたケースも同じ結果にする
- expected type のない空 list/hash や shape だけでは確定しない closure は inference error とし、numeric literal の `Int` から `Float` への暗黙 coercionを追加しない

### 3.7 標準定義ソース境界テスト

- `Bootstrap` / `Kernel` の auto import と、`Result` など `@autoimport` 付き標準 `impl Type` owner helper surface、および `Eq` / `Concat` / `Convert` / `TryConvert` / `Show` / `Functor` / `Applicative` / `Monad` など `@autoimport` 付き標準 trait helper の auto import を `spec` / `integration` で固定する。少なくとも `fmap`, `pure`, `ap`, `return`, `bind` の bare call を成功系で固定し、`Encode` / `Decode` は auto import 対象外として固定する
- constructor trait application の static capability を `unit/scar` と `compile_errors` で固定する。`Functor<$A>` は `fmap`、`Applicative<$A>` は `fmap` / `ap`、`Monad<$A>` は `fmap` / `ap` / `bind` を利用でき、親から子への逆方向利用は失敗しなければならない
- constructor trait の引数へ `Option<$A>` / `List<$A>` / `Result<$A>` などの具象値を渡せることと、callee 本体では宣言された trait capability に制限されることを別々に検証する。具象型として解決された call-site では、具象型が実装する trait helper を利用できることも成功系で固定する
- constructor application の witness は direct parameter position ごとに独立し、return は fresh result witness とする。入力値または expected type なしの unresolved result witness を拒否する
- constructor application の宣言側許可位置を direct parameter / return と対応する nominal field/payload に限定し、local annotation、non-nominal field、tuple / container、closure signature 内の不正な利用を失敗させる。call-site RTAの applied carrier はこの制限の対象外として成功させる
- constructor trait method の ReturnTypeArguments と通常引数型による型変数導入規則、二重導入、return type のみに現れる型変数を `unit/scar` / `compile_errors` で固定する。通常Trait methodのbare generic targetは、user-defined型でもimpl source/targetの共有変数から全引数が解ける成功、完全型指定の成功、共有されないcaptured引数のambiguity、通常関数では拒否、を対にする
- Trait-head binder、RTA内の`_`/applied carrier、nominal annotationの`Hole`境界、constructor head推論、`Alternative::empty`をScarの直接テストへ対応付ける。`do` RTAのapplied carrierは`lib/tests/language_features/do.srt`でpipelineと実行比較する
- [do intrinsic契約](./Do_intrinsic_spec.md)のsurface、scope、carrier、failure targetはSindr / Spire / Sigil / Scarの直接テストで固定する。全carrierのpipeline比較、MonadFail優先とguardのAlternative、Transformerのbase failureは`lib/tests/language_features/do.srt`で観測する。Alternative不足、SafeBind末尾のresult span、生成closure内Facet消費はScar surface、human/JSONの同じsource factsはRune binaryの直接比較テストへ置く
- 多段block / closureのcompiler stack回帰はSigilの名前解決とScarの型検査で固定する。テスト環境の`RUST_MIN_STACK=32 MiB`がCLIでの失敗を隠さないよう、局所回帰は8 MiBのthreadで実行する。通常のCLI processによるコンパイル試験も`build_roundtrip`に置き、正常終了を確認する。productionのstack設定は変更しない。
- 関数シグネチャ alias の展開、未使用 parameter、arity mismatch、alias cycle、canonical type name 衝突を `unit/scar` / `compile_errors` で固定する。alias が runtime type や TypeRegistry entry を生成しないことを `unit/forge` で確認する
- `Alternative` の `<|>` は `Option` / `List` の成功系、eager evaluation、左結合、改行拒否、identity / associativity law を `spec` / `integration` で固定する
- `Monoid` の identity / associativity law、`List::reduce` / `fold` / `fold_map` / `reduce_with` の空入力・順序・単位元を `spec` で固定する
- `@autoimport` が `defmod` / `deftrait` / `impl Type` に付いたときの受理範囲を `unit/spire` で固定し、標準 prelude へ auto import されるのは `defmod`, `deftrait`, `impl Type` に由来する標準 surface に限ることを `unit/sigil` で固定する
- `STDLIB_MODULE_SPECS` が定める標準モジュールの順序、`Bootstrap` と shared standard stage の境界、および variant 有効時に `TestExtension` が同じ shared standard stage へ加わることを `integration` で固定する
- 同一 stage 内 import が file 読み込み順に依存せず成功し、later stage import が失敗することを `unit/sigil` / `spec/modules` / `compile_errors/modules` で固定する
- `Script` / `ReplChunk` の top-level `def` が暗黙擬似モジュール所属として扱われることを `integration` / `rune` で固定する
- `Script` では `include` / `import` / `const` / top-level `def` / `namespace` / 型定義 / trait 定義 / `impl` を受理し、explicit top-level `defmod` を拒否することを `unit/spire` / `unit/scar` で固定する
- `Script` の `include` 先頭固定と、最初の top-level expr 以降に宣言を置けないことを `unit/spire` / `compile_errors` で固定する
- 同一 script の top-level expr と top-level `def` body では bare call を維持しつつ、`namespace` / `impl` / include module file / 他 module からは script helper の canonical path で参照することを `unit/sigil` / `spec` で固定する
- `repl --module` と `repl --script` の preload mode は CLI 引数で確定し、追加 file の token sniffing で切り替えないことを `integration/repl` で固定する
- `ReplChunk` では top-level `def` / `import` だけを許可し、`const`、型定義、`impl`、`defmod` を拒否することを `unit/spire` / `integration/repl` で固定する
- `defmod` ネスト禁止と、`defmod` / `impl` / `impl Trait for Type` body で `import` と許可された member 宣言のみを受理することを `unit/spire` / `unit/sigil` / `compile_errors` で固定する
- `impl Type` を型専用の module-like namespace として扱い、`Self` / `self` / `Type::method` / `Type::new` sugar が崩れないことを `unit/sigil` / `spec` で固定する

### 3.11 Facet / private visibility 契約テスト

- `bulk_update(value) { ... }` と `bulk_update(value, { ... })` が同じ専用 AST になり、`bulk_update value { ... }` を拒否することを parser で固定する。既存の `Facet::bulk_update(value) { ... }` を維持し、bare `bulk_update` の宣言・束縛・シャドーイングを拒否する
- `Facet::bulk_update` は Spire が専用構文として解析し、Sigil が外側の通常 callable identity を要求せず、初期の `Ok(source)` と各 Facet 呼出しへ展開する設計を維持する。生成した呼出しの解決・型検査エラーを値生成へ置き換えず、実行時の更新失敗を伝播する。通常の関数値として `bulk_update` を要求する経路を追加しない
- `match value { ... }`、`match(value) { ... }`、`match(value, { ... })` の同等性と、`cond { ... }`、`cond({ ... })` の同等性を parser で固定する。括弧内のブロックも専用文法で解析し、通常のブロック値へ変換しない。評価順序、guard、網羅性、Facet 更新の失敗伝播は既存の実行テストで検証する

- `Facet::compose` と `->` の両方を Facet 合成 surface として固定し、旧 `/` 合成経路を残さない
- `->` の左結合、通常 Expr より強い結合、ドットと呼び出しのオペランド内結合、capture 境界、bulk_update の相対 path 合成を parser と型検査の直接テストで固定する
- 式位置の `->` は Facet path に限定し、型位置の関数型・戻り値型の `->` と do / bulk_update の `<-` が維持されることを固定する
- `Facet::view` の文脈依存返り型（plain / `Result`）を `unit/scar` と `spec` で固定する
- `Facet::set` / `Facet::over` / `Facet::over_result` の成功・失敗（source `Err`, variant mismatch, `update_fun` 失敗）を `unit/forge` と `spec` で固定する
- Facet path class（field / tuple / list index / map key / required enum）と API（`view` / `preview` / `put` / `set` / `over` / `over_result` / `case_set` / `case_over`）の有効・無効組み合わせ、および optional enum selector の拒否を `unit/scar`, `unit/forge`, `spec`, `compile_errors` で固定する
- `~source.path` shorthand の expand を `unit/spire`, `unit/scar`, `lib/tests`, `spec`, `compile_errors` で固定する
- shorthand は source 付き Facet API の第1引数でのみ受理し、それ以外では専用 misuse error になることを固定する
- shorthand の API 適格性は expand 後の既存 Facet 規則で判定されることを固定する
- readonly Facet 境界を固定する
- `readonly field` 越しの `Facet::view` は成功
- `readonly field` 越しの `Facet::set` / `Facet::over` / `Facet::over_result` は失敗
- owner による readonly field そのものの置換は成功
- owner であっても readonly field の先への深い mutable traversal は失敗
- `@readonly defstruct` root からの mutable Facet operation は owner を含めて失敗
- Facet の同一スコープ使用規約（関数引数・戻り値・closure capture・container 格納禁止）を `unit/scar` と `compile_errors` で固定する
- `view` 後の plain 値 / `Result` 値は関数境界で受け渡せることを `spec` で固定する
- tuple index `_N` は path segment 専用として固定する
- `value._N` と `Tuple._N`（型文脈あり）は成功、`_N` 単体は失敗、`Tuple._N` のローカル deferred binding は成功として固定する
- `:doc Ty` が canonical type doc、`:doc Facet.Ty` が PathConstructable root doc を返し、`:doc Ty.prop` が `:info Ty` / `:facet Ty.prop` へ誘導することを `unit/xldr` / `integration/repl` で固定する
- `:info Ty` が `facet root: public | readonly` と private を含む field policy table を返すことを `unit/xldr` / `integration/repl` で固定する
- `:doc Tuple` が tuple shape、`:doc Facet.Tuple` が `Tuple._N` FacetPath、`t._1` の値 access 説明を返すことを `unit/xldr` / `integration/repl` で固定する
- `:sig Tuple` は tuple literal pattern signature を返すことを `integration/repl` で固定する
- `:sig Facet::view(...)` / `:sig Facet::set(...)` / `:sig Facet::over(...)` / `:sig Facet::over_result(...)` / `:sig Facet::compose(...)` が command query で許可された引数 surface の範囲で defined / specialized 表示を返すことを `integration/repl` で固定する
- `:facet <FacetPath>`、`:facet <facet-binding>`、および `:facet <Facet API call>` が canonical path、5 slot、kind、API eligibility、operation result、segment 一覧、停止点を返すことを `unit/xldr` / `integration/repl` で固定する。root/segment policy、readonly による API unavailable reason、current scope availability も含める
- `:info FacetPathKind` / `:info ReadablePath` は declaration と atomic members を表示し、`:sig ReadablePath` は constructor signature がないことを説明して `:info` へ誘導することを固定する
- `:facet User.private_field` が structurally valid な private Path を inspection でき、外側 REPL scope での availability を明示することを `unit/xldr` / `integration/repl` で固定する。通常 source と `Facet::*` API 引数の private capability rejection は維持する
- `:sig pair._1` のような任意式 surface が command query では無効であることを `integration/repl` で固定する
- `:doc` / `:sig` の bare symbol 解決が current scope 準拠であり、auto-import されない helper は import 前に bare 名では見えないことを `unit/xldr` / `integration/repl` で固定する
- command query が literal、任意式、generic type variable、`$name`、capture query を受けないことを `unit/xldr` / `integration/repl` で固定する
- private capability 境界を固定する
- `User.password`（type-root capability）は拒否
- `user.password`（value access）も 所有者の `impl User` 外では拒否し、`impl Trait for User` も外側として扱う
- closure 内 private access（例: `{|| user.password}`）も field access と同じ規則で拒否
- `return user.password` も owner 外では拒否、owner 内では plain value return として許可
- Trait impl 内の private 直接アクセスと Facet 導出は拒否し、所有者の公開関数への委譲は成功する
- inspect は全 private・混在・入れ子の構造体を定義順に表示し、String の引用を維持する。Show 不在でも成功し、to_string は Show 不在を拒否する。手書き Show からの明示的な inspect 呼び出しは成功する

2. `forge` の `fun_idx == index` と opcode 非退行
3. `sindr` の bytecode 互換（旧 decode）
4. `scar` の網羅性と `=?` 制約
5. `sigil` の capture / `unique_id` 決定性
6. `rune` の roundtrip と REPL 回帰

## 9. デグレ事前予防ルール

- バグ修正時は再発ケースを同一 PR に追加する
- 仕様差分は `tests/fixtures/script`、`tests/fixtures/modules`、または crate-local unit に必ず反映する
- VM/bytecode 変更時は `eldr` 単体と `rune` integration の両方を実行する
- エラー系検証は全文一致ではなく `phase + contains` を使う
- 標準定義ソース定義（現行実装: `bootstrap.srt` / `kernel.srt`）と実装の整合チェックを CI で常時実行する
- 前方参照ポリシー変更時は、成功系（同一 stage / 前 stage で解決可能）と失敗系（later stage 参照 / 最終未解決）を必ず対で更新する
- 並列化導入後も、ID/tag と診断内容が実行スケジュール非依存であることを回帰テストで保証する

## Pattern consumer 拡張の受入

`apply_pattern` は projection の0 / 1 / 複数・番号順・型注釈・alias / tail、Result input 全体、元 Error / cause、既存 list failure kind、単一評価・短絡・内部 binding 非公開を標準 SRT で固定する。index 範囲・欠番・重複・許可位置・予約名・OR・pipe の拒否は fixture、canonical consumer / Regex 通常 call の分離は parser / resolver の契約、REPL の chunk 間 capture・署名・doc target は Xldr で固定する。標準 @doc の本文・存在そのものはテスト契約にせず、サンプルの実行と解決 target / signature を検証する。

## Test モジュールの検証

- Rune の typed options は1,024通りの組み合わせ、値形式、順序、`--`、重複と欠落を unit test で固定する。JSON の usage error も同じトークン化で形式を選ぶ。
- Eldr は種類付きスコープのフィルター全8集合、宣言の検証順、実行／非実行、IO の分離、時間の有無を直接検証する。
- `tests/integration/test_command.rs` は単一／all × 実行／一覧 × human／JSON の8境界、quiet とポリシー、走査異常、all の続行を検証する。
- Test モジュール自体は Rust のテストで検証する。Surtr の入力コードを Rust 側に置き、終了コード・ケースの成否・診断・IO を Rust の assertion で直接比較する。Test のアサーションを別の Test アサーションだけで判定する SRT テストは置かない。失敗時は入力とケース名を出力し、原因を追跡できるようにする。
- 追加アサーションと canonical ErrorKind、cause chain の成功・失敗は `tests/integration/test_command.rs` に置く。Eq 不足、非 deferror marker、動的な種類列、型の逃がしも CLI のコンパイル境界で拒否する。
- inspect 比較は表示・payload message を検査する場合に使う。枝、値、種別、cause の構造の検証には目的に合う Test API を使う。
- cases の詳細を quiet で省略しても summary は全件を保持する。`discovered = selected + filtered`、実行時 `selected = passed + failed + skipped + pending`、一覧時 `selected = runnable + skipped + pending` を検証する。
- ScopeFailed、ファイル異常、ポリシー違反をケース failed に混ぜない。実行異常で中断した active case だけは Failed として確定し、ファイル異常も別に記録する。

### アサーションの契約と利用箇所

- `assert` の message 保持、`assert_satisfies` の predicate の単一評価と失敗時だけの診断構築を検証する。message は通常の String 引数として評価し、空文字列も保持する。
- 比較4種は成功・失敗・等しい境界を検証し、Compare 不足や異なる型の組は拒否する。prefix/suffix は一致・不一致・空文字列、`assert_some` は Some・None と Eq を持たない payload を検証する。
- `assert_err_message_eq` は message の一致・不一致と予期せぬ Ok を検証する。kind・cause・位置を比較に含めず、必要な契約は対応するアサーションで別に検証する。
- 通常関数の名前付き引数・関数値・キャプチャ、最初の Err によるケース内の短絡と次の `it` の実行、明示的な `;` による discard を検証する。失敗表示は標準 Test の正規名で外側の公開アサーションを指し、同じ短名の利用者関数は特別扱いしない。
- 標準関数を検証する SRT テストでは、検証対象の式を残す。たとえば Compare の関数・演算子、String の prefix/suffix helper、`Option::is_some`、`Eq::eq` 自体の検査を、同等のアサーションへの置換で消さない。
- アサーションを順に検査する場合は `do` の bare Result 式、文末 `?`、SafeBind で失敗を伝播する。通常の束縛や Unit を返す処理、明示的な discard の検証と区別する。

### Random の検証分担

`lib/tests/modules/random.srt` では、同じ seed と操作列から10回分の値列を作って等価性を検査する。
各 draw の返却生成器を次へ渡し、元の生成器を再利用しても最初の値が変わらないこと、
値の範囲、空・逆順範囲の Error kind と message を検証する。
生成器の状態進行は `crates/eldr/src/builtin.rs` で直接検証する。
不透明な生成器の表示文字列や隣接する乱数値の不一致では状態進行を判定せず、実装依存の具体的な生成列も固定しない。
