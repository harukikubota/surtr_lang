# Surtr 要件定義書 V9

> V9 の目的は、Phase2 までの実装を言語仕様として確定し、フェーズ3の土台を整えることである。
> 本書は言語仕様と処理系の外部契約を扱い、Rust 実装の詳細はソースコードを正とする。

---

## 1. 言語思想

Surtr は静的型付き関数型言語である。

- コンパイラとランタイムをシンプルに保つ
- 構文の表現力で記述力を高める
- 失敗を型で表現し、曖昧さを早期に排除する

---

## 2. 型システム

### 2.1 基本型

- `Int`
- `Float`（finite-only の `f64` ラッパー）
- `String`
- `Boolean`
- `Unit`
- `Duration`（非負ミリ秒値を表す opaque struct。`100ms` literal、`Duration(Int)` / `try_from(Int, Duration)`、比較、加算、失敗可能減算を持つ）

### 2.2 合成型

- `List<T>`
- `HashMap<T>`（key は `String` 固定、value のみ generic）
- tuple `(T1, T2, ...)`（arity 2 以上）
- `Result<T>` (`Ok(T)` / `Err(Error)`)
- `Option<T>` (`Option::Some(T)` / `Option::None`)
- `Facet<K, S, A, T, B>`（compiler-managed な型変更可能 path capability。同一スコープ内でのみ使用可能）
- `Workers<T>`（runtime-managed な worker 集合 handle）
- `WorkerLease<T>`（`Workers<T>` から得る reservation capability）
- `Duration`（runtime sleep 用の opaque struct value。field は private で、`100ms` literal だけが特別な syntax sugar。pattern 位置の `Duration(ms)` は attached extractor による millisecond 分解、`100ms` は literal value 検査として扱う）
- `Result<T>` をコード上の主表記とし、関数戻り値シグネチャでは `Result<T, E>` を補助的に記述できる
- 関数型 `(T1, T2, ... -> R)`
- ユーザ定義型 (`defstruct`, `defrecord`, `deferror`, `defenum`)

### 2.2.1 TypeIdentity

Surtr は top-level 名を次の TypeIdentity で区別する。

- `Type`
  - 標準 type owner。`Int`, `Float`, `String`, `Boolean`, `Unit`, `Error`, `Result`, `List`, `HashMap`, `Generator`, `Regex`, `RegexCaptures`, `RegexMatch`, `RandomGenerator`, `Facet` を含む
- `Struct`
  - `defstruct Name { ... }`
- `Record`
  - `defrecord Name(...)`
- `Enum`
  - `defenum Name { ... }`
- `ConcreteError`
  - `deferror Name { ... }`
- `Mod`
  - `defmod Name { ... }`
- `Const`
  - `const APP_NAME = "surtr"` / `private const DEFAULT_PORT = 8080`

同一可視圏では、ある top-level 名は `Type` / `Struct` / `Record` / `Enum` / `ConcreteError` / `Mod` / `Const` のいずれか 1 つにだけ属してよい。

- canonical builtin type 名は `Type` identity として compiler が予約し、他 identity での再定義を許可しない
- `deferror Name` は abstract `Error` とは別の `ConcreteError` identity を導入する。ただし型検査上の失敗値は abstract `Error` へ収束する
- `Option<$T>` は標準 enum として `Enum` identity に属する
- Extractor は `Option<$T>` を返す。`Some(payload)` は成功、`None` は MatchBlock の no-match を表す
- `Result<$T>` は builtin-special enum とし、surface では `@builtin defenum Result<$T> { Ok($T), Err(Error) }` を正本とする
- `Boolean` は builtin-special enum とし、surface では `@builtin defenum Boolean { True, False }` を正本とする
- `Ok` / `Err` / `True` / `False` の bare constructor は builtin-special enum 限定の sugar とし、正規形は `Result::Ok` / `Result::Err` / `Boolean::True` / `Boolean::False` とする
- `Ok` / `Err` / `True` / `False` は `TypeIdentity` ではなく builtin-special enum variant sugar の予約 surface 名として扱い、`defmod Ok` / `defenum True` のような owner 名には使えない。この制約は `sindr` の owner surface name constraint を正本とする
- `Boolean::True` / `Boolean::False` の match pattern と網羅性チェックは通常 enum variant metadata を通す。内部表現や lowering は必要に応じて `Bool` / `BoolLit` を使ってよい
- `Boolean.True` / `Boolean.False` のような Facet selector は通常 enum selector と同じ扱いにし、compiler / runtime は Boolean 専用の FacetPath 意味論を持たない
- `TypeRef`, `Hole`, `Closure`, `MatchArms`, `CondClauses`, `Self` は compiler-special type identity とし、通常の top-level type 定義ではない
- `Tuple` は REPL / ドキュメント上では tuple shape 説明用の表示名として扱う
- コード上の `Tuple` は `Tuple._N` を作る Facet path root として扱う
- `Tuple` は nominal builtin type ではなく、tuple shape と FacetPath root の説明を束ねる補助的 surface とする
- `Script` / `ReplChunk` は暗黙 compile unit 名に使う reserved pseudo-module 名であり、ユーザ定義を禁止する

### 2.3 `Option` の扱い

Surtr は標準 enum として `Option<T>` を持つが、失敗伝播の主軸にはしない。

- `Option<T>` は `Option::Some(T)` / `Option::None` を持つ user-facing な補助型である
- `T?` は `Option<T>` へ lower される optional sugar とする
- 標準定義ソースの欠損・失敗 API は引き続き `Result<T>` / `Err(NoneError)` を返す
- `Option` は `SafeBind` (`=?`) の対象ではない
- `Option` は `Functor` / `Chainable` の標準実装を持ち、`|*>` / `|>=` を `Option` 文脈で使える
- `Option` は `LiftComposable` / `KleisliComposable` の標準実装を持ち、`>*` / `>=>` も `Option` 文脈で使える
- `Option` と `Result` / `List` の間で演算子文脈を混在させてはならない
- `Option` の基本 helper は `impl Option` の `Option::is_some` / `Option::is_none` / `Option::wrap` とし、`Result` との変換は `From` trait の `from(value, Result)` / `from(value, Option)` で明示的に行う
- `From` / `TryFrom` などの trait impl は `impl From<Result<$T>> for Option<$T>` のような generic target を受理し、ユーザ定義 generic 型にも同じ dispatch 規則を適用する
- 暗黙的な `Option` / `Result` 変換は行わない

### 2.4 エラー型

- `Error` は抽象的な失敗値の型であり、直接構築しない
- `deferror` は `Error` として扱える具象エラー値を定義する
- ユーザー定義関数の引数型には、裸の `Error` および `List<Error>` / `Result<Error>` / `(Error -> A)` など Error 値を外側へ持ち出す型を書けない。`Error` は `Err(Error)` の内部で保持し、`match` の `Err(...)` arm で取り出した範囲でのみ標準 builtin に渡して観測する
- `Error` を引数に取る closure / capture / composition は、`Result::tap_err` など標準 Error 観測 API の non-escaping 引数としてのみ許可する。型注釈で `(Error -> A)` を書くこと、通常値として再束縛・返却・格納すること、直接呼び出すことはできない
- `Result<T, E>` の `E` には `deferror` により定義された型のみを書ける
- `Err(term)` / `Result::Err(term)` の `term` には具象エラー値のみを入れ、抽象 `Error` を直接 surface で構築しない。compiler は `Result::Err(...)` の引数位置でだけ具象 error surface を abstract `Error` へ昇格できる
- `match` は `Result` の `Ok(...)` / `Err(...)` を見る。`Err(...)` 内では具象 `deferror` 名による kind 部分チェックを提供するが、payload 分解は提供しない
- `RichError` の確定フィールドは `kind`, `message`, `location`, `cause`
- `cause` チェーンは runtime が管理する線形 chain とする
- parallel error は持たない
- `Result::cause(result, err)` は special form とし、`err: Lazy<Error>` は concrete `deferror` type / constructor surface に加え、`Err(e)` などで既に得た `Error` 値も受けられる。`Err(old)` に対してだけ `err` を評価し、新しい domain error head にして既存 chain をその末尾へ付ける
- `Result::chain(head, tail)` は `(Result<T>, Result<()>) -> Result<T>` を取り、両方が `Err` のときは右の chain 末尾へ左の chain 全体を連結する
- `Result::map_err(result, err)` は special form とし、`err: Lazy<Error>` は concrete `deferror` type / constructor surface に加え、`Err(e)` などで既に得た `Error` 値も受けられる。`Err(_)` のときだけ `err` を評価して `Err(err)` に置き換え、既存 chain は保持しない
- `Result::recover(result, handler)` は純粋な標準ライブラリ関数とし、具象 error kind を見ず、任意の `Err(Error)` のときだけ 0 引数 `handler()` を評価する
- `Result::recover_kind(result, marker, handler)` は special form とし、`marker: Lazy<Error>` は concrete `deferror` type / constructor を直接書く surface として扱う。括弧なしの `marker` payload は resolve/typecheck するが runtime では評価せず、具象 `deferror` kind marker としてだけ使う。`(marker)` は explicit eager boundary として判定前に一度評価するが、kind 判定には同じ constructor marker を使う。一致する `Err(Error)` のときだけ `handler(Error)` を評価する
- `assert` / `ensure` の error branch も `Lazy<Error>` 契約であり、新しい `deferror` を構築しても、既に得た `Error` 値をそのまま返してもよい。すべての `Lazy<T>` 引数で、通常の `expr` は callee が必要時に評価し、`(expr)` は callee の選択判定より前に一度だけ評価する eager boundary とする。括弧は closure 値を暗黙呼び出ししない
- `Error::kind(Error) -> String` / `Error::message(Error) -> String` / `Error::format(Error) -> String` を持つ。`format` は `eprint` と同じ人間向け複数行表示を `String` として返す

bootstrap には少なくとも次が含まれる。

```surtr
deferror NoneError { "None Value." }
deferror ZeroDivisionError { "division by zero" }
deferror VariantMismatch(detail: String) { detail }
```

### 2.4.1 Json / Encode / Decode

- `JsonValue` は JSON AST を表す source enum とする。`Json` は type ではなく qualified operation namespace とする
- `JsonValue` の shape は `Null`, `Bool(Boolean)`, `Int(Int)`, `Float(Float)`, `String(String)`, `Array(List<JsonValue>)`, `Object(HashMap<JsonValue>)` で固定する
- `JsonValue::Object` は `HashMap<JsonValue>` を使うため、object key は `String` 固定、表示と stringify の順序は `HashMap` の deterministic key order に従う
- JSON integer literal は `JsonValue::Int(Int)` として読む
- JSON decimal / exponent literal は `JsonValue::Float(Float)` として読む。`Float` は finite-only の `f64` ラッパーとして扱う
- `Json::parse(text)` と `Json::stringify(value)` は Rust library backed builtin とし、VM では `CallBuiltin` で到達する。専用 opcode は追加しない
- `Json::decode(text)` は `String -> JsonValue` の public wrapper、`Json::encode(value)` は `JsonValue -> String` の public wrapper とする
- malformed user JSON は `RuntimeError` ではなく `Err(JsonParseError(...))` を返す
- stringify 不能な runtime value は `RuntimeError` ではなく `Err(JsonEncodeError(...))` を返す。ただし VM 内部不整合は `RuntimeError` のままでよい
- `Encode<$To>` と `Decode<$To>` は target-oriented trait とし、標準 prelude には auto import しない
- `JsonValue::decode(value, Target)` は `Decode<Target> for JsonValue` への helper surface とし、`Target` を `TypeRef` witness slot として解釈する
- `JsonValue::encode(value)` は標準ライブラリ上の source alias として `Encode::encode(value, JsonValue)` を呼び、`Encode<JsonValue> for typeof(value)` へ dispatch する
- `value |> JsonValue::decode(Target)` と `value |> JsonValue::encode()` は pipeline partial call により同じ surface を使う
- `TypeRef` は引き続き trait method signature / trait impl method signature の parameter 型でのみ許可する。通常 `def` の parameter / return / field / local annotation では使えない
- `Decode` は `Facet` を受け取らない。`Facet` は decode 前の `JsonValue` inspection、または decode 後の typed value update の周辺で使う

```surtr
deftrait Encode<$To> {
  def encode(self: Self, to: TypeRef<$To>) -> Result<$To, Error>
}

deftrait Decode<$To> {
  def decode(self: Self, to: TypeRef<$To>) -> Result<$To, Error>
}
```

### 2.5 文字列

- 文字列リテラルは二重引用符文字列と単一引用符文字列を持つ
- 複数行文字列は `@doc` と同じ raw triple-quoted string `"""..."""` を関数ブロック内の式として利用できる。本文インデントは開始行の行頭インデントを起点に判定する
- 二重引用符文字列と triple-quoted string では式埋め込み `"#{expr}"` / `"""#{expr}"""` をサポートする
- 埋め込み式は `String` 化可能な式に限る

| クォート | 式埋め込み | 転義シーケンス |
|---|---|---|
| `"..."` | あり | `\\`, `\"`, `\'`, `\n`, `\t` |
| `'...'` | なし | `\\`, `\"`, `\'`, `\n`, `\t` |
| `"""..."""` | あり | raw |

- `@doc` は同じ raw triple-quoted string `"""..."""` を doc string として使う
- `@doc` 内の本文は interpolation しない。unescaped `#{...}` は parse error とする

### 2.6 Trait System V1

Surtr V1 は compile-time only の trait system を持つ。

- trait 宣言は `deftrait Name { def method(...) -> ... }` で書く
- trait 宣言は `deftrait Name<$T, ...> { ... }` のように型引数を取ってよい
- trait 実装は `impl Trait for Type { def method(...) -> ... { ... } }` で書く
- trait 実装は `impl Trait<ConcreteTy, ...> for Type { ... }` のように trait 側の型引数を concrete に束縛してよい
- trait dispatch は runtime trait object や hidden dictionary を持たず、型検査時に concrete な opcode / builtin / user function へ確定する
- trait は method のみを持つ
- associated types / associated consts / default method body / trait inheritance / multi-trait bounds は V1 範囲外とする
- `impl Trait` 糖衣は parameter 位置でのみ許可する
- return 位置の `impl Trait` は不許可とし、同じ型を戻す場合は `def f<$T: Trait>(x: $T) -> $T` のように明示 bound を使う
- 関数ブロック内の local binding / closure parameter / pattern annotation では、外側の `def` / extractor / method signature で束縛済みの型引数 `$T` を参照してよい
- 関数ブロック内の型注釈は新しい型引数を導入しない。参照できる `$T` は外側シグネチャで既に束縛済みのものに限る
- `where` clause は staged とし、まだ実装しない
- `@builtin type TypeRef<$T>` を compiler-reserved な type witness として持つ
- `TypeRef<$T>` は通常の user code の型としては使えず、trait head で宣言された型引数 `$T` に対応する witness parameter としてのみ trait method signature に現れてよい
- `TypeRef<$T>` は trait method / trait impl method の parameter 型としてのみ許可する
- `TypeRef<$T>` は return type、通常の `def` parameter、field type、local binding type annotation、tuple / function type の要素としては不許可とする
- `TypeRef<$T>` の値を生成・束縛・返却する surface 構文は持たない
- `@builtin type Hole` を compiler-reserved な ignored-input callable marker として持つ
- `Hole` の user-facing surface は `_` とする
- `Hole` / `_` は plain data wildcard ではなく、callable input marker としてのみ使う
- callable を値へ適用する位置では、入力型が `_` なら任意の具象型・call-site で具体化された generic・推論変数を受理する。`_` 自体をそれらの型へ単一化したり、通常の型互換性や暗黙変換へ持ち込んではならない
- `_` は変数の callable type annotation と、関数戻り値に現れる callable type の中でのみ許可する
- `_` は通常関数の引数型、field type、container 要素、tuple 要素、plain value annotation、return hole 単体には使えない
- `Hole` の値を生成・束縛・返却する surface 構文は持たない
- `@builtin type Closure` を REPL / inspect / doc surface 用の compiler-reserved callable category として持つ
- `Closure` は user program の通常の nominal data type ではなく、関数リテラルや capture で生成される callable 値を説明するための補助名である
- callable 値の実体的な表記は引き続き `(A, B -> R)` のような関数型シグネチャであり、`Closure` はその置き換えではない
- `Closure` は `Tuple` 表記と同様に、REPL とドキュメントで混乱を減らすための補助的な surface 名として扱う

target type を明示して変換する trait の例:

```surtr
deftrait From<$To> {
  def from(self: Self, to: TypeRef<$To>) -> $To
}

deftrait TryFrom<$To> {
  def try_from(self: Self, to: TypeRef<$To>) -> Result<$To, Error>
}
```

演算子は compile-time only trait dispatch として扱う。

- `+`, `-`, `*` はそれぞれ `Add::add`, `Sub::sub`, `Mul::mul` の surface sugar として扱う
- `==`, `!=`, `++` はそれぞれ `Eq`, `Neq`, `Concat` の method に対応する
- `<`, `<=`, `>`, `>=` は ordered-comparison surface として扱い、`Compare` を満たす型に対して使える
- `|>`, `/`, `>>`, `>*`, `>=>` はそれぞれ `PipeApply::pipe_apply`, `Compose::compose`, `Composable::compose`, `LiftComposable::lift_compose`, `KleisliComposable::kleisli_compose` の surface sugar として扱う
- `|*>`, `|>=` はそれぞれ `Functor::map`, `Chainable::chain` の surface sugar として扱う
- 数値 helper は共通 trait にせず、`Int::safe_div` / `Float::safe_div` / `Int::abs` / `Float::abs` のように concrete type owner surface として提供する
- comparison 演算子と `safe_mod` は数値 helper trait ではなく、`Compare` / `Int` owner helper として扱う
- comparison capability として `Compare` を標準提供する
- `Compare` は必須 method `compare(self: Self, rhs: Self) -> Ordering` を持ち、三値比較結果を返す
- `Compare` は default helper として `lt`, `lte`, `gt`, `gte` を持ち、impl 側で任意 override できる
- `Ordering` は `Less | Equal | Greater` の 3 variant を持つ標準 enum とする
- `Int` と `Float` は operator traits / `Compare` 実装も持つ
- `Float` は finite-only の `f64` ラッパーとして concrete helper / operator traits / `Compare` を提供する

## 3. 文法

### 3.0 モジュール的名前空間

Surtr では、関数はすべて明示または暗黙のモジュール的名前空間に属し、型は `Global` または 1 段の user namespace に属する。

- `defmod Name { ... }` は通常の module 名前空間を導入する
- `namespace N { ... }` は 1 段の user namespace を導入し、その body 内の型定義・trait 定義・`impl` target・`defmod` head を `N::...` へ lower する
- `defmod N::M { ... }` は namespace block を使わずに namespace 配下 module を定義する sugar である
- `defmod` head は definition source の primary module path を導入する正本であり、module path は token 列ではなく parse 後 AST と namespace lowering 結果から決定する
- `defmod N::M { ... }` と `namespace N { defmod M { ... } }` は同じ canonical module path `N::M` に lower される
- internal canonical owner/module path は常に 2 セグメントで、bare global owner は `Global::Name`、namespace 配下 owner は `Namespace::Name` とする
- `Global` は compiler-reserved root namespace であり、user code では `Global::Type` / `Global::Kernel` のような明示記法を禁止する。user-facing 表示では `Global::` を省略する
- namespace 名と owner 名は同じ一意表で管理し、`namespace A` が存在する可視圏では `defmod A` / `defstruct A` / process owner `A` などを禁止する
- コメントや空行の配置は canonical module path 導出に影響しない
- `impl Type { ... }` は型 owner 専用のモジュール的名前空間を導入する。これは「`self` / `Self` が使える type-owned namespace」であり、標準 `Type` と user-defined `Struct` / `Enum` が同じ surface を共有する
- `deftrait Name { ... }` は trait 名前空間に method 契約を置く。ここでは本体を持たない
- `impl Trait for Type { ... }` は trait 実装用のモジュール的名前空間に concrete な method 本体を置く
- `Script` / `ReplChunk` の top-level `def` は暗黙の擬似モジュールに属する
- `Script` の bare top-level `def` は暗黙の擬似モジュール配下へ canonicalize する。内部名は実装都合で保持してよい
- `defstruct` / `defrecord` / `deferror` / `defenum` / `@builtin type` は canonical type owner を導入する
- 型名構文は bare identifier / qualified identifier / generic (`Type`, `N::Type`, `Type<...>`, `N::Type<...>`) を受理する
- bare 型名は `Global::Type` を指す。`Global::Type` と `Type` は同値である
- 型 import は持たない。型はどの file からも root-qualified path で直接参照できる
- canonical type key は `Global::Type` または `Namespace::Type` とする
- 同一 canonical type key の重複は compile error とする。`A::User` と `B::User` は共存できる
- canonical builtin type 名と同じ `Global::Type` の再定義は compile error とする
- 関数名解決は file 単位で行い、`&fun_name` が一意に決まることを優先する
- local 変数束縛と、その file 自身の module 関数定義は外側の関数名を shadow してよい
- import は関数のみを対象にし、型名解決には影響しない
- `defagent` / `defgenserver` / `defsupervisor` などの process declaration でも、public callable surface は通常の module 関数と同じ import 規則で扱う
- process runtime の待機系 surface では `@timeout(...)` を runtime-managed call の後方 modifier として扱う。`Task::async` は handle を返し、待機は `Task::await(task)` 側で行う。
- process declaration では annotation により公開された concrete 関数名だけが import 対象になる。annotation なし `def` は `defp` 相当として import できない
- compiler-managed hidden process surface (`pid`, `spawn`, hidden owner helper, hidden lower 名) は import 対象外であり、user code から直接参照できない
- `const` は module/import 名前空間に属さず、`public const` は compile unit 全体の global const namespace へ、`private const` は定義 file 内だけへ入る
- 明示 `import` は同じ file 内の auto-import 名を明示的に shadow してよい
- 明示 `import` 同士、および auto-import 同士の同じ unqualified 関数名衝突は compile error とする

### 3.1 束縛と式

- 束縛は `name = expr`
- 型注釈付き束縛は `name: Ty = expr`
- エラーバインドは `name =? expr`
- tuple 束縛は `(x, y, ...) = expr`
- 正規表現生成リテラルは `re"pattern"` / `re'pattern'` とし、`Regex::compile("pattern")` へ lower する
- セミコロン終端式は `Unit` として扱う
- TCO における末尾位置は、現在の関数 / closure / Extractor / process handler の返り値そのものになる式位置とする
- TCO 対象は user function への direct call、相互再帰、module-qualified call、target が user function の callable call に限る
- 算術・連結・constructor・container 構築・call 引数評価中の再帰、`=?` の早期 return 制御、effectful builtin / process runtime builtin は user-function TCO 保証の対象外とする

### 3.1.1 `const`

- `const` は file top-level にのみ書ける
- surface は `const NAME = expr`, `const NAME: Ty = expr`, `private const ...`, `public const ...`
- visibility 未指定は `public`
- `const` 名は `CAP_PATTERN` (`[A-Z][A-Z0-9_]*`) 必須で、先頭/末尾 `_` と `__` は禁止する
- `CAP_PATTERN` は `const` 専用 identifier class とし、関数名・引数名・ローカル束縛名では使えない
- V1 の RHS は primitive literal または type-root Facet path alias のみ許可する
- `public const` は compile unit 全体で一意でなければならず、`import` なしで unqualified 参照できる
- `public const` は他の top-level 宣言と同じく `Namespace::NAME` でも参照できる
- `private const` は定義 file のみから参照できる
- process runtime の標準 surface は `lib/process.srt` を正本とし、REPL / project compile の両方で同じルートからロードする
- hidden lowering surface として `Agent` / `GenServer` / `Supervisor` module を `process.srt` に置いてよいが、user code からの直接呼び出しは `@hidden` 共通診断で拒否する
- process owner の compiler-managed surface 名 `pid` / `spawn` / `adopt` / `status` / `workers` は kind を問わず予約し、同名 user 定義を禁止する

`=` は Bind であり、`pattern = expr` 形式の language-level binding form として扱う。

- `=` は RHS を 1 回だけ評価し、total な MatchBlock pattern にだけ束縛できる
- `=` 自体の結果型は `Unit` であり、trait dispatch 演算子ではない

`=?` は SafeBind であり、「失敗しうる入力を受けて失敗を伝播する束縛糖衣」として扱う。

- `=?` 自体の結果型は `Unit` であり、trait dispatch 演算子ではない
- `=?` は `Result<T>` を返す関数内でのみ使える。REPL top-level ではエラーメッセージを表示してセッションを継続する
- closure body も `=?` の関数 body として扱い、早期 return 先は最も近い enclosing callable body とする
- closure 内の `=?` は外側の `def` / method / closure を飛び越えず、その closure の戻り値が `Result<_, E>` として期待される場合だけ使える

- `SafeBind.LHS` は MatchBlock として解釈する
- `match` の各 arm 左辺も MatchBlock として解釈する

- `pattern =? Result<T, E>` の場合:
  - `Ok(value)` のときは `value` を左辺へ束縛して続行する
  - `Err(error)` のときは現在の評価を中断し、失敗をそのまま伝播する
- `pattern =? expr` の場合:
  - `expr` が SafeBind 対象の失敗しうるパターン入力なら、それを左辺 MatchBlock へ照合する
  - RHS 側で `Err(Error)` が観測されたら、そのまま早期 return する
  - `MatchBlock::NoMatch` は error 化して早期 return する
- `Option<T>` は SafeBind 対象ではない。必要なら `from(value, Result)` で明示変換してから `=?` を使う
- `num: Int =? Option::Some(1)` は compile error とする
- `SafeBind.LHS` では `uncons`、list/string 分解、literal match などの構造パターンマッチを許可する
- `SafeBind.LHS` では Extractor を許可する
- MatchBlock と Extractor は再帰的に書け、必要になった部分だけ段階的に評価される
- 上記がすべて `Ok(...)` / successful match で通ったときだけ、束縛変数を導入して評価を継続する
- トップレベル実行では、その失敗は診断表示の対象になる

`Result<T, E>` は関数戻り値シグネチャでのみ許可し、変数注釈・関数引数・field・関数型内部では `Result<T>` を用いる。
`defextractor` / `@builtin defextractor` は `Option<T>` を戻り値にし、`Some` の payload shape が pattern 側の束縛数を決める。

### 3.2 データ定義

- `defstruct Name { field: Ty, ... }`
- `defstruct Name<$A, ...> { field: $A, ... }`
- `defrecord Name(field: Ty, ...)`
- `deferror Name(field: Ty, ...) { "message template" }`
- `defenum Name { Variant, Variant(Ty), Variant = Int, ... }`
- `@builtin type Facet<$K, $S, $A, $T, $B>`
  - `$K` は compiler-derived な path kind、`$S/$A` は更新前、`$T/$B` は更新後の source/focus を表す
  - update slot は `_, _`（API 消費ごとに導出）または両方 concrete type の組だけを許可する
  - `Hole` はユーザー型名として予約し、`_` は callable 入力型と Facet deferred slot でのみ使える
- `deftrait Name<$T, ...> { def method(self: Self, ...) -> ... }`
- `impl Type { def method(...) -> ... { ... } }`
  - `Type` target は標準 `Type` owner または user-defined `Struct` / `Enum` のいずれかに一意解決できなければならない
  - `Record` / `ConcreteError` は `impl Type` target にできない
  - `defstruct` の constructor surface `Struct(...)` は `impl Struct { def new(...) -> Self { ... } }` または `impl Struct { def new(...) -> Result<Self, E> { ... } }` によって定義される
  - `defstruct` の `new` は direct initializer / validated initializer 専用であり、`Option<Self>` や他の wrapper / 別型を返す general-purpose factory hook にはできない
  - `defstruct` は declaration type parameter を持てる。例: `defstruct Box<$A> { value: $A }`, `defstruct Pair<$A, $B> { left: $A, right: $B }`
  - generic `defstruct` の plain `impl` head は引き続き owner 名だけを受理し、`impl Box<$A> { ... }` のような trait-style type argument 付き target は不許可とする
- `impl Trait<$T, ...> for Type { def method(self: Self, ...) -> ... { ... } }`
  - `Type` target は canonical type key 上で一意解決できなければならず、標準 `Type` と user-defined `Struct` / `Record` / `Enum` / `ConcreteError` を対象にしてよい

`defenum` の外部契約は次。

- discriminant はデフォルト `0` 起点で自動採番し、明示値の次はその値 + 1 とする
- discriminant は内部管理値であり、surface から直接参照する field accessor は提供しない
- enum に対する `match` は網羅必須
- 循環判定は `scar` の型 predeclare 後に実行する
  - `struct` / `record` / `deferror` の field 型循環は拒否する
  - `enum` は「全バリアント共通で参照される型」を循環 edge として扱う
  - 終了 variant を持つ recursive enum は許可する
  - 禁止時の主診断文言は `Cyclic type definition detected` とする
  - 最小 cycle 表示の完全性は契約化しない
- constructor surface は引き続き `Enum::Variant(...)` を使う
- Facet selector surface は `Enum.Variant` を使う（PascalCase 固定）

Facet / path の外部契約は概要として次で固定する。

- `Type.segment` は compiler-managed な Facet path を表す
- `value.segment` は対応する Facet path を `value` に適用した sugar として扱う
- 公開 API は `Facet::view`, `Facet::preview`, `Facet::put`, `Facet::set`, `Facet::over`, `Facet::over_result`, `Facet::chain` とする
- 合成 API 名は `chain` に固定し、`join` は導入しない
- operator 形式では `left / right` を `Facet` path chain sugar として許可する
- `Facet::view` の返り型は文脈依存とする
  - source が `Result<T>` なら `Result` 文脈で開始する
  - field/tuple segment は文脈を維持する
  - variant segment を含むと `Result` 文脈へ昇格する
  - 最終返り値は `Plain` 文脈なら `A`、`Result` 文脈なら `Result<A>`
- `Facet::preview` は variant segment を含む Facet 専用 API とし、struct field / tuple segment のみの structural path は compile error とする
- `Option.Some` / `Option.None` は通常 enum variant として `preview` 対象になる
- `Boolean.True` / `Boolean.False` は通常 enum variant selector と同じ経路で `preview` / variant 専用 Facet API の対象になる。特別扱いは bare constructor sugar の `True` / `False` に限定する
- `Result.Ok` / `Result.Err` は variant Facet として扱わず、`Result<T>` source の実行文脈として扱う
- `~source.path` は compiler-managed shorthand とし、source 実体と structural value path の expand のみを責務にする
  - source expression はちょうど 1 回だけ評価する
  - shorthand 自体は first-class `Facet` 値ではない
  - shorthand は `Facet::view`, `Facet::preview`, `Facet::put`, `Facet::set`, `Facet::over`, `Facet::over_result` の第1引数位置でのみ受理する
  - shorthand の path 部分は field / tuple の structural value path 由来に限る
  - shorthand の API 適格性（plain source 必須、variant 専用、readonly 制約など）は expand 後に各 `Facet::*` API が既存規則で判定する
- `Facet::put(facet, source, value)` は plain source + structural path 専用 API とし、返り値は `S` とする
- `Facet::put` は `Result<S>` source を受理しない
- `Facet::put` は variant segment を含む Facet を受理しない
- `Facet::set(facet, source, value)` / `Facet::over(facet, source, update_fun)` / `Facet::over_result(facet, source, update_fun)` の返り値は常に `Result<T>` とする
- `Facet::bulk_update(source) { ... }` は Facet update を source order で適用する special form とし、返り値は `Result<S>` とする
- `Facet::bulk_update` block は通常 block ではなく、`match` 同様の dedicated surface として扱う
- `Facet::bulk_update` entry は改行区切りで、`,` 区切りは受理しない
- `Facet::bulk_update` entry は `path <- set(value)` / `path <- over(update_fun)` / `path <- over_result(update_fun)` / `path { ... }` のみを受理する
- `Facet::bulk_update` の nested block は path prefix を積む sugar とし、`address.country <- ...` と `address { country <- ... }` は同じ path へ lower される
- `Facet::bulk_update` は whole-state updater `$S -> Result<$S>` を block 内で受理しない。必要な場合は通常関数として block 外で `|>=` 合成する
- focus が `Result<A>` のとき、`Facet::set` は replacement focus をそのまま受け、`A` の暗黙 `Ok(A)` wrap は行わない
- `Facet::over` は成功値 update 用 API とする
  - plain focus `A` では `update_fun: (A -> Result<A>)`
  - `Result<A>` focus では `Ok(value)` の payload にだけ `update_fun: (A -> Result<A>)` を適用し、`Err(err)` は updater を呼ばずそのまま保持する
- `Facet::over_result` は `Result<A>` focus 全体の update 用 API とし、`update_fun: (Result<A> -> Result<Result<A>>)` を要求する
- `readonly` は Facet path 自体の妥当性ではなく mutating Facet operation の妥当性として扱う
  - `Facet::view` は readonly boundary をまたいでもよい
  - `readonly field` は `defstruct` field modifier `readonly profile: Profile` で表し、その field をまたぐ writable traversal を禁止する
  - owner の `impl Type` 本体では readonly field そのものの置換だけを許可し、その先への深い writable traversal は禁止する
  - `@readonly defstruct Profile { ... }` は readonly root として扱い、その struct を root にした writable Facet operation を owner を含めて禁止する
- tuple access は `._0`, `._1`, ... に統一する（`.0`, `.1` は不許可）
- tuple index `_N` は path segment 専用とする
  - `value._N` は許可
- `Tuple._N` は型文脈で `Facet<K, (...), A, T, B>` が期待される位置で直接使える
  - `Tuple._N` はローカル束縛して deferred FacetPath として保持してよい
  - `_N` 単体は不許可
- enum variant selector が現在値に一致しないときは `Err(VariantMismatch(...))` を返す
- Facet は同一スコープ内でのみ使用可能な capability とする
  - 同一スコープ内での一時束縛（例: `facet = User.name`, `facet = Tuple._1`）は許可
  - 関数引数/戻り値/container 格納/closure capture は不許可
  - 関数境界で受け渡すのは `Facet` ではなく `view` 済み値（`A` または `Result<A>`）とする
- private capability 境界は次で固定する
  - `Type.private_field` は `impl Type` / `impl Trait for Type` の本体内でのみ許可
  - `value.private_field` も同じ可視性規則に従い、`impl Type` / `impl Trait for Type` の本体内でのみ許可
  - private 判定は FacetPath 生成時に行い、closure 内でも特別扱いしない
- Facet root の inspection policy は `public` / `readonly` の二値で表示する。これは値の
  可変性ではなく、root を含む mutating Facet operation の可否を表す。`@readonly defstruct`
  は `readonly`、それ以外の PathConstructable type は `public` である
- field inspection policy は `public` / `readonly` / `private` / `private readonly` とする。
  `readonly` は当該 segment の深い mutable traversal を止め、private は通常 source 上の
  capability 可視性を制限する
- `:info Ty` は definition inspection であり、外側 scope でも private field を含む型 metadata を
  表示してよい。runtime `inspect` と通常 source の visibility はこの例外に含まれない
- `:facet Path` は Path inspection であり、private segment を含む Path も型定義上正当なら表示する。
  REPL の外側 scope で実行・binding・Facet API 消費ができるかは、Path validity と分けて
  availability として表示する

トップレベル宣言の解決規則は以下とする。

- `def` / `defextractor` / `@builtin def` / `@builtin defextractor` / `@builtin type` / `defstruct` / `defrecord` / `deferror` / `defenum` / `deftrait` / `impl` は同一コンパイル単位で事前登録対象とする
- `sigil` は通常の本体解決前に declaration index を収集し、`module_path` / `name` / `fq_name` / `kind` / `stage_index` / import 可否 / visibility を保持する
- declaration index の決定順は `sigil::resolver::declarations::DeclarationOrdering` を実装正本とし、`stage_index -> fq_name` の昇順で固定する
- 参照が定義より前に現れても、同一 stage または前 stage の declaration index で解決できれば成功とする
- later stage の宣言は参照不可とし、最終未解決は通常の resolve / typecheck 診断として fail-fast に確定する
- 現行 V1 は明示的な依存グラフ、再評価用 queue、保留参照集合、固定点診断集約を public contract に含めない
- `unique_id` は declaration index から `stage_index -> fq_name` の決定順で割り当てる
- user type tag は `scar` の型 predeclare 順で予約し、`Ok = 0`, `Err = 1`, user-defined type は `2` 以降とする
- `impl Type` target は同一 compile stage 内で一意に解決できなければならない。同一 file に定義があることは要求しない
- `impl` の owner namespace は記述した module path ではなく target type 名へ属する。`impl User` の method は常に `User::method` として解決する
- `impl` は型ごとに 1 ブロックのみ許可する（後付け拡張禁止）
- `impl Trait for Type` は `(Trait, Type)` ごとに 1 ブロックのみ許可する
- user-defined `Struct` に対する `impl` は `new` の実装を必須とする
- `defmod` はネストできない
- `defmod` の直下には関数形宣言のみ置ける。型定義・trait 定義・`impl`・`defmod` の入れ子は不許可とする
- `User(...)` は構造体 head の sugar として扱い、ExprBlock では `User::new(...)` に割り当てる
- MatchBlock では同じ `User(...)` を attached extractor head とみなし、`impl User { defextractor deconstruct(...) ... }` に割り当てる
- `User { ... }` 構造体リテラルは `impl User` の同型メソッド本体内でのみ許可する
- 構造体リテラルの field は `field: expr` に加え shorthand の `field` を許可し、`field: field` の sugar として扱う
- shorthand は field 単位で判定し、`User { name, age: next_age }` のような mixed form を許可する
- shorthand の名前解決は通常のローカル / 引数 / `self` 参照規則に従い、型検査では最終的に各 field を expected type に照らして個別に検証する
- この shorthand は `User { ... }` struct literal 専用であり、constructor call `User(...)` や constructor pattern `User(...)` には適用しない
- `new` は import 対象外とする
- 構造体名そのものも import 対象外とする。`import User` は無効で、構造体 head `User` は宣言名としてそのまま解決する
- `defstruct` / `defrecord` / `deferror` の field は `private name: Ty` と書ける
- private field は `Type.private_field` / `value.private_field` を問わず、`impl Type` / `impl Trait for Type` 本体内からのみ参照を許可する
- private 判定は field access が FacetPath segment を形成する時点で行い、closure 専用の別ルールは設けない
- `inspect` / `to_string` の named-field 表示は外側 surface を優先し、`Struct` / `Record` とも `Type(field: value, ...)` を使う
- private field を含む named-field 値の `inspect` / `to_string` は hidden field を `..private` で要約し、完全な round-trip code は保証しない

### 3.3 関数

- `def name(args...) -> Ty { ... }`
- `defp name(args...) -> Ty { ... }`
- `def name<$T: Trait>(args...) -> Ty { ... }`
- `defextractor name(self: Ty?) -> Option<$Value> { ... }`
- `@builtin def name(args...) -> Ty`
- `@builtin defextractor name(self: Ty?) -> Option<$Value>`
- `defextractor` / `@builtin defextractor` は module / impl の下でのみ宣言できる
- Extractor は LHS / MatchBlock 専用であり、通常の式・RHS・引数位置では呼び出せない
- Extractor の `Option::Some` は payload を pattern へ渡し、`Option::None` は no-match として扱う
- `defp` は private helper を宣言し、定義された module / impl の内部からのみ参照できる
- private helper は `import` 対象外であり、外部 module から qualified path でも参照できない
- `@builtin type Name`
- `@doc """..."""` は public declaration にのみ付けられる
- `@doc """..."""` は `defmod` / `def` / `deftrait` / `impl Trait for Type` / `defstruct` / `defrecord` / `defextractor` / `deferror` / `defenum` / `@builtin type` / `@builtin def` / `@builtin defextractor` の直前に置ける
- `defp` や process declaration 内の annotation なし helper のような private declaration に `@doc` を付けた場合は parse error とする
- `impl Type { ... }` の block head には `@doc` を付けられない。型全体の説明は type declaration 側に書き、owner helper の説明は impl member ごとに書く
- `@autoimport` は `defmod` / `deftrait` / `impl Type` の直前に置ける
- `@hidden` は declaration / impl member 単位の属性であり、`impl Type` の block head には付けられない
- declaration annotation は種類ごとに一意でなければならない
- 同一 declaration または impl member の直前に同じ annotation kind を複数回書いた場合は parse error とする
- クロージャは `{|x| expr}` / `{|| expr}` / `{ expr }`
- クロージャ引数型注釈は任意で、`{|x: Int| expr}` 形式を許可する
- `{ expr }` はゼロ引数クロージャ `(-> T)` を作る。即時評価されるブロック式は言語機能として持たない
- 複文の `{ stmt; expr }` もゼロ引数クロージャであり、即時評価したい場合は `block = { ... }` のように束縛して `block()` で呼ぶ
- `match expr { pattern => expr, ... }` と `cond { cond => expr, ... }` の `{ ... }` は `=>` を持つ専用コンテナであり、ブロックリテラルではない
- parser は実装上の防御境界として構文・型・pattern の最大ネスト深度を 32 に制限し、超過時は parse error とする
- capture は `&f`, `&Type::method`, `&Module::func`, `&Type::method(args...)` を許可する
- `&f(args...)` は capture placeholder を含む full call shape のときだけ有効とする
- capture は callable 値を作る式として確定し、後続 `()` によって通常 call や別の parse 形へ変化しない
- capture placeholder は `&1`, `&2`, ... とし、outermost capture scope にのみ属する
- prefix partial capture (`&f(10)`) は導入しない
- pipe slot `_1` は lexer では `Ident("_1")` のまま扱い、pipe RHS の最外 call の direct argument でだけ特別扱いする
- `|>` / `|*>` / `|>=` は explicit `_1`、implicit first-argument injection、trait helper / partial call を含めて `Lazy<T>` parameter へ値を注入してはならない。型解決後に `TypeError` とし、明示 binding または closure で評価順序を固定する
- FuncLiteral は backtick 付きの parser-only 補助構文とし、`expr \`name\` expr` / `expr \`operator\` expr` を許可する
- FuncLiteral は値ではなく、単独出現・束縛・引数受け渡し・戻り値化・型位置への記述を許可しない
- V1 の FuncLiteral は unqualified name と symbolic operator のみを対象とし、qualified path (`\`Type::method\``) は未対応とする
- V1 では capture 側の operator FuncLiteral (`&\`+\``) は未実装とし、受理しない
- `type` は予約語とする
- `Self` は `impl` 内の型位置でのみ許可し、対象型へ解決する
- `self` は `impl` メソッドの第一引数専用で、再束縛は禁止する
- trait method 宣言は `deftrait` の中で body を持たない
- trait head の型引数は trait method signature から参照してよい
- `TypeRef<$T>` は trait method signature / trait impl method signature の parameter 型としてのみ許可する
- このとき `$T` は対応する trait head で宣言された型引数でなければならない
- `TypeRef<$T>` を trait 以外の通常関数 signature に書くことはできない
- `TypeRef<$T>` を return type や local binding に書くことはできない
- parameter 位置の `impl Trait` は anonymous bounded type parameter として扱う
- 返り値や複数位置で同じ bound 型を使うときは named type parameter を使う
- `where` clause は staged とし、parse error にする

tuple / extractor の外部契約は次で固定する。

- tuple 値は `(expr1, expr2, ...)` で書き、arity 2 以上のみ許可する
- `(expr)` は引き続き parenthesized expression であり、1-tuple は導入しない
- tuple 型は `(T1, T2, ...)` で書き、arity 2 以上のみ許可する
- `()` は引き続き `Unit` であり、空 tuple は導入しない
- tuple 要素アクセスは `._0`, `._1`, ... の positional access とする
- `defextractor` の成功値は単一値なら `Option<T>`、複数値なら `Option<(T1, T2, ...)>` を使う
- `Seq` は現時点では surface 型として導入しない
- `Option::None` は Extractor / MatchBlock 評価の no-match を表し、通常の失敗 API は `Result` を使う

関数値の扱いは次で固定する。

- 裸の関数参照は許可しない
- 関数値として保持できるのは capture / closure / `Ty::Func` を持つ変数・式のみ
- `fun_name()` や `Type::method()` は通常は関数呼び出しであり、apply 系演算子の右辺では第一引数注入として解釈する
- ただし `(fun_name())` のように括弧で囲んだ call 式を演算子に渡す場合は、call の返り値を関数値として評価する
- Phase 1 の call 構文は `name(args)` / `Module::func(args)` / `Type::method(args)` のような identifier / qualified path 起点に限定する
- `&add(&1, 10)(4)`, `({|x| x + 1})(4)`, `(make())(4)` のような匿名 callable 式への即時 call は不許可とし、一度 `fn = expr` のように束縛してから `fn(args)` で呼ぶ
- call 式の最終引数がゼロ引数クロージャなら、`f(arg1, ..., { ... })` を `f(arg1, ...) { ... }` と書いてよい
- この trailing block sugar は通常の関数呼び出しでのみ許可し、constructor call では許可しない
- trailing block は常に最終 positional 引数として解釈し、named 引数にはできない
- `>>` / `>*` / `>=>` は関数値を要求し、括弧なし call 式は受けない
- pure callable combinator は `Function` auto-import module に置き、`id`, `always`, `noop`, `on`, `flip`, `apply`, `both`, `both3`, `both4`, `both5`, `both6`, `both7`, `both8`, `dup`, `first`, `second`, `curry`, `uncurry` を公開する
- closure / capture 内の trait helper 呼び出しは、代入注釈・引数注釈・高階関数引数などの期待 callable 型境界まで解決を遅延できる
- 期待 callable 型から引数型が一意に確定した時点で trait helper dispatch を concrete 化する
- 期待型境界を抜けても concrete 化できない callable 値は束縛できない
- standalone の trait helper 参照は引き続き不許可とし、遅延解決の対象にしない

`@builtin` の利用境界は次で固定する。

- `@builtin def` / `@builtin type` は標準定義ソース（`SourceKind::StdDefinitionSource`）でのみ許可する
- user script / project module / REPL chunk では `@builtin` を書けない
- builtin の追加・変更の正本は共有メタデータテーブルであり、Surtr source 側の `@builtin` 宣言はその宣言層としてのみ扱う
- `@builtin` は inline (`@builtin def ...`) と standalone (`@builtin` の次行に宣言) の両形式を許容する
- builtin type の canonical head は compiler が固定で持ち、標準定義ソースでは次と完全一致しなければならない
  - `Int`
  - `Float`
  - `String`
  - `Boolean`
  - `Unit`
  - `Error`
  - `List<$A>`
  - `HashMap<$V>`
  - `Result<$T>`
  - `RandomGenerator`
  - `Facet<$K, $S, $A, $T, $B>`

### 3.4 制御構造

- `if_then(flag, (-> Unit)) -> Unit` / `if(flag, (-> A), (-> A)) -> A`
- `if_let(value, pattern, then, else) -> A`
- `if_let_then(value, pattern, then) -> Unit`
- `is_match(value, pattern) -> Boolean`
- `cond { cond1 => expr1, ..., True => exprN }`
- `match expr { pattern (`|` pattern)* (`when` expr)? => expr, ... }`
- `match` は網羅必須
- `Err(Timeout | ConnectionReset @ e: Error)` のように、`Result<T>` の `Err(...)` 内で複数の concrete error kind を部分チェックできる。`@ e: Error` は実際の `Error` 値を束縛する

`if` / `if_then` の branch 型が関数型で書かれるのは、選択されなかった branch を
評価しない special form であることを外部契約として明示するためである。
ただし source 上の通常記法では closure を明示する必要はなく、
`if(flag, "ok", err_reason)` や `if_then(flag, print("ok"))` のように
通常の式として書ける。

`if_let` / `if_let_then` も pattern 特化の special form として扱う。
`if_let` は値を返す 2 分岐、`if_let_then` は成功時のみ実行して `Unit` を返す。

`assert` / `ensure` も guard 用の special form として扱う。

`and` / `or` も `Kernel` の special form として扱うが、外部契約の型は
通常の 2 引数関数として見せる。

- `if_let(A, Pattern, (-> B), (-> B)) -> B`
- `if_let_then(A, Pattern, (-> Unit)) -> Unit`
- `is_match(A, Pattern) -> Boolean`
- `assert(Boolean, Error) -> Result<Unit>`
- `ensure(A, (A -> Boolean), Error) -> Result<A>`
- `recover(Result<A>, (-> Result<A>)) -> Result<A>`
- `recover_kind(Result<A>, Lazy<Error>, (Error -> Result<A>)) -> Result<A>`
- `and(Boolean, Boolean) -> Boolean`
- `or(Boolean, Boolean) -> Boolean`
- `from(A, TypeRef<B>) -> B`
- `try_from(A, TypeRef<B>) -> Result<B, Error>`
- `encode(A, TypeRef<Format>) -> Result<String, Error>`
- `decode(A, TypeRef<Format>, TypeRef<B>) -> Result<B, Error>`
- `compare(A, A) -> Ordering`
- `lt(A, A) -> Boolean`
- `lte(A, A) -> Boolean`
- `gt(A, A) -> Boolean`
- `gte(A, A) -> Boolean`
- `eq(A, A) -> Boolean`
- `neq(A, A) -> Boolean`
- `concat(String, String) -> String`

外部契約は次で固定する。

- `assert` は条件が `True` のとき `Ok(())` を返し、`False` のときだけ error 引数を評価して `Err(error)` を返す
- `ensure` は値を 1 回だけ評価し、その値を predicate へ渡す
- `ensure` の predicate は unary callable value を要求し、call 式は受けない
- `ensure(value, &pred, err)` と `ensure(value, {|x| ... }, err)` は許可する
- `ensure(value, pred(), err)` のような call 式は不許可とする
- `assert` / `ensure` の error 引数は失敗時にのみ評価する
- `if_let` / `if_let_then` は第1引数の値を 1 回だけ評価する
- `if_let` は `match(value) { pattern => then, _ => else }` と同値な振る舞いを持ち、`else` は必須
- `if_let_then` は `match(value) { pattern => { then; () }, _ => () }` と同値な振る舞いを持つ
- `if_let` / `if_let_then` の束縛は成功 branch 内でのみ有効
- `is_match` はパターン合致の真偽だけを返し、束縛を生成しない
- `is_match` の pattern では binding variable pattern を禁止し、必要なときは `if_let` / `match` を使う
- `and(left, right)` は左辺が `True` のときだけ右辺を評価し、`False` なら右辺を評価せず `False` を返す
- `or(left, right)` は左辺が `False` のときだけ右辺を評価し、`True` なら右辺を評価せず `True` を返す
- `and` / `or` は source 上で closure を要求しない
- `from(value, TargetTy)` / `try_from(value, TargetTy)` の第2引数 `TargetTy` は通常の Expr ではなく型指定スロットとして解釈する
- `encode(value, FormatTy)` の第2引数 `FormatTy`、および `decode(value, FormatTy, TargetTy)` の第2・第3引数は通常の Expr ではなく型指定スロットとして解釈する
- `TargetTy` は bare type syntax で書き、内部では `TypeRef<TargetTy>` witness として扱う
- `FormatTy` / `TargetTy` は bare type syntax で書き、内部では `TypeRef<...>` witness として扱う
- `from` / `try_from` / `encode` / `decode` の witness slot 以外で bare type syntax を値引数として渡すことはできない
- `from` / `try_from` / `encode` / `decode` は target type や format marker を式単位で固定するための special form surface を持つ
- `compare` は ordered comparison の公開 helper であり、`Compare::compare` に対応する
- `lt` / `lte` / `gt` / `gte` は ordered comparison の公開 helper であり、`Compare` の default helper method に対応する
- `<` / `<=` / `>` / `>=` は `Compare` を満たす型に対してのみ使え、それぞれ `Compare::lt` / `Compare::lte` / `Compare::gt` / `Compare::gte` に対応する ordered-comparison surface として扱う
- `eq` / `neq` は call-style helper であり、それぞれ `==` / `!=` に lower する
- `eq` / `neq` の比較可能型は `==` / `!=` と同一とする
- `concat` は call-style helper であり `++` に lower する
- `concat` は `String` 同士のみを許可する

`cond` は上から順に条件を評価し、最初に `True` になった clause の右辺値を返す。
外部契約は次で固定する。

- 各非終端 clause の左辺は `Boolean` を返す式でなければならない
- 最終 clause は必ずリテラル `True` でなければならない
- `True` clause は最後に 1 回だけ書ける
- すべての clause の右辺型は一致しなければならない
- 選ばれなかった clause の右辺は評価しない

### 3.5 パターン（V9 確定範囲）

- `True`, `False`
- `Ok(x)`, `Err(e)`
- `_`
- `Int` / `String` リテラルパターン
- tuple pattern `(p1, p2, ...)`
- binding / as-pattern / list pattern / type annotation を `match` arm 左辺でも許可する
- or-pattern `p1 | p2 | ...` を許可する（同一 arm body を共有）
- guard `pattern when cond` を許可する（`cond` は `Boolean` 必須）
- guard が `False` の arm は不一致として次 arm へ進む
- 網羅性判定は guard なし arm を基準に行う

`match` は `Result` の成功 / 失敗構造を扱う。具象エラー型での分解は行わない。

`defenum` 導入後の拡張として、`Enum::Variant(...)` 形式の constructor pattern も許可する。

### 3.6 演算子

- 算術: `+ - *`
- 比較: `< <= > >= == !=`
- 文字列結合: `++`
- パイプ / bind:
  - `|>` : 値 apply
  - `|*>` : `Result` / `List` / `Option` の map apply
  - `|>=` : `Result` / `List` / `Option` の bind apply
  - `>>` : 通常関数合成
  - `>*` : `Result` / `List` / `Option` の lifted 合成
  - `>=>` : `Result` / `List` / `Option` の Kleisli 合成

パイプ / bind 系の外部契約は次で固定する。

- `|>`, `|*>`, `|>=` は apply 系であり、右辺が call 式なら左辺値を第一引数へ注入する
- `x |> f(1, 2)` は `f(x, 1, 2)` と等価
- `user |> User::get_name()` は `User::get_name(user)` と等価
- `x |> (make_closure(1))` は `make_closure(1)` の返す関数値へ `x` を渡す
- `|>` の右辺は function value / call 式を受ける
- `|*>` の右辺は plain function を表す function value / call 式を受ける
- `|>=` の右辺は同一文脈 (`Result`、`List`、または `Option`) を返す function value / call 式を受ける
- `|*>` / `|>=` を含む flow operator は、RHS callable の入力が `_` なら LHS payload を渡せる。`_` は payload 型を制約・変換しない ignored-input marker とする
- `>>`, `>*`, `>=>` は compose 系であり、左右とも function value でなければならない
- `>*` は左辺に同一文脈 (`Result`、`List`、または `Option`) を返す関数、右辺に plain function を要求する
- `>=>` は左右とも同一文脈 (`Result`、`List`、または `Option`) を返す関数を要求する
- flow operator の callable operand では、closure / capture / inferred facet capture / grouped callable-producing expression に対して operand class に応じた期待 callable 型を伝播してよい
- `|>=` と `>=>` の `Result` 文脈では、対象 callable operand に `A -> Result<B, E>` の戻り値期待を与え、closure-local `=?` の nearest-callable 境界を確定する
- `|*>` と `>*` の plain RHS では、全体の期待型が明示的に nested `Result` などを要求する場合を除き、contextual return を推測しない
- `parse() >=> validate()` や `parse() >* render()` や `f() >> g()` のような括弧なし call 式 compose は不許可
- `|*>`, `|>=`, `>*`, `>=>` は `Result` と `List` を混在させない
- `|>`, `|*>`, `|>=`, `>>`, `>*`, `>=>`, `=?` は同一優先度・左結合で扱う
- `=` は同じ token class に見えても expression operator ではなく、束縛構文として別扱いする
- `|*>`, `|>=`, `>=>` は最長一致でトークナイズする
- flow 系演算子 (`|>`, `|*>`, `|>=`, `>>`, `>*`, `>=>`) のみ、演算子の直前または直後で改行してよい
- 演算子の結合優先度は `Bind < StdOn < Apply=Compose < AndOr < Compare < Expr` とする
- prefix `!expr` は `Boolean::not(expr)` に lower し、`Expr` / `Compare` / `AndOr` / flow 系より強く結合する
- `Expr` クラスの算術演算子 (`+`, `-`, `*`, `++`) は同列・左結合で扱う
- comparison 系 (`==`, `!=`, `<`, `>`, `<=`, `>=`) は `Compare` クラスとし、左結合で扱う
- `and` / `or` / `&&` / `||` は `AndOr` クラスとし、左結合で扱う
- `&&` / `||` は `Boolean` 専用の short-circuit 演算子であり、`and(left, right)` / `or(left, right)` と同じ意味論を持つ
- `and` / `or` / `&&` / `||` は operator trait dispatch に載せない。eager evaluation では short-circuit 契約を満たせないため、special form として扱う
- 記号演算子 `&&` / `||` の dispatch target と precedence は parser 固定契約とし、local 定義や import による `and` / `or` の shadowing では retarget しない
- bare call surface の `and(...)` / `or(...)` は通常の callable 解決に従い、local 定義や import による shadowing を受けうる
- FuncLiteral の operator 形式は対応する operator のクラスに従う
- FuncLiteral body は `ident | qualified_path | operator` を受理する
- FuncLiteral の name 形式のうち `and`, `or`, `eq`, `neq` は `Compare` / `AndOr` クラスとして扱う
- unqualified FuncLiteral `` `on` `` は parser 固定の std target として `StdOn` クラスに置き、常に `Function::on(left, right)` へ lower する
- qualified FuncLiteral `` `Function::on` `` も `StdOn` クラスとして扱う
- `StdOn` は flow 系より低優先度とし、``left `on` key >> next`` は `Function::on(left, key >> next)` として parse する
- `Other::on` のようなそれ以外の qualified_path FuncLiteral は std target に含めず、`Expr` クラスのままとする
- std fixed infix target の precedence は parser 契約であり、後段の scope 解決や shadowing では変化しない
- 上記以外の FuncLiteral name / qualified_path 形式は `Expr` クラスで扱う
- `left \`Type::method\` right` は `Type::method(left, right)` に lower する
- `&\`name\`` と `&\`Type::method\`` はそれぞれ `&name`, `&Type::method` と同義にする
- `&\`op\`` は 2 引数 closure `{|lhs, rhs| lhs op rhs}` 相当に lower する
- `&\`op\`(args...)` は placeholder capture 規約 (`&1` から連番、named args 禁止) を使って lower する
- 記号演算子は Scar で対応する operator trait dispatch に resolve し、Forge では concrete dispatch target へ lower する

演算子診断の表示方針は次で固定する。

- open operator (`+`, `-`, `*`, `++`, `/`, `==`, `!=`, `<`, `<=`, `>`, `>=`, `|*>`, `|>=`, `>*`, `>=>`, `from`, `try_from`) は user-defined impl を前提にし、「同型が必要」「現在の型では未定義」「現在見えている実装対象」を中心に案内する
- close operator (`|>`, `>>`, `!`, `&&`, `||`) は標準定義の固定契約として案内し、user-defined impl 前提の拡張案内は出さない
- `OP rule:` 表示では `where` clause を出さない。たとえば `A + A -> A`、`A == A -> Boolean` のような surface rule のみを示す
- `/` は基本的に `Compose` family として扱うが、`Facet<K, S, A, _, _> / Facet<L, A, B, _, _> -> Facet<K, S, B, _, _>` を満たす `Facet` compose ではその具体的契約を優先して表示する
- `=`, `=?`, `match`, `cond` のような special form は `OP rule:` へ無理に寄せず、`Bind rule` / `SafeBind rule` / `Match rule` / `Cond rule` の専用見出しを使う

### 3.7 引数規約

- 名前付き引数は関数・コンストラクタ呼び出しで使用できる
- 位置引数と名前付き引数の混在は禁止する
- `Type::method(...)` をメソッド呼び出しの正規形とする
- `Type(...)` は `impl struct` の `Type::new(...)` 糖衣としてのみ許可する

- `bit_not(Int) -> Int`
- `test_bit(Int, Int) -> Result<Boolean, NegativeBitIndex>`
- `set_bit(Int, Int) -> Result<Int, NegativeBitIndex>`
- `clear_bit(Int, Int) -> Result<Int, NegativeBitIndex>`
- `toggle_bit(Int, Int) -> Result<Int, NegativeBitIndex>`
- `shl(Int, Int) -> Result<Int, NegativeShiftCount>`
- `shr(Int, Int) -> Result<Int, NegativeShiftCount>`

- `Error::kind(Error) -> String`
- `Error::message(Error) -> String`
- `Error::format(Error) -> String`
- `set_exit_code(Int) -> Unit`

- `recover_kind(Result<A>, Lazy<Error>, (Error -> Result<A>)) -> Result<A>`

- `or(Boolean, Boolean) -> Boolean`

`safe_div` / `safe_mod` はゼロ除算時に `Err(ZeroDivisionError)` を返す。
`shl` / `shr` は負 shift count に対して `Err(NegativeShiftCount)` を返す。
`set_exit_code` は `main` 内でのみ使用可能で、評価を継続したままプロセス終了コードを更新する。
`safe_div` は `Int::safe_div` / `Float::safe_div` の concrete runtime builtin target として使う。
`to_string` の surface は `Show::to_string` helper として source 側に現れ、runtime builtin テーブルはその concrete execution target を共有する。
`assert` / `ensure` は `Kernel` の special form であり、runtime builtin テーブルではなく
コンパイラ側で遅延評価を伴う分岐へ lower する。
`Result::map_err` / `Result::cause` も `Result` 専用の special form であり、第2引数は `Lazy<Error>` 契約で direct `deferror` constructor surface と、`Err(e)` などから既に得た `Error` 値を受け、入力が `Err(...)` のときだけ評価する。
`Result::recover_kind` も surface では special form のままとし、error marker は `Lazy<Error>` 契約で direct `deferror` constructor surface を受ける。compiler は marker から concrete kind 名だけを取り出して hidden builtin `__recover_kind` 呼び出しへ lower し、runtime 側で kind 判定と handler 呼び出しを行う。
`dbg!` も special form とし、各引数を独立に型検査して左から右へ 1 回だけ評価し、`stderr` へ debug 出力したうえで `Unit` を返す。
`dbg!` の docs / `:sig` は `lib/bootstrap.srt` に置かれた intrinsic surface declaration `@intrinsic def dbg!(values: *$A) -> Unit` と `@doc` だけを正本にし、これは通常の callable builtin declaration ではない。
`and` / `or` も宣言型は通常の関数だが、コンパイラ側で short-circuit 分岐へ lower する。
`compare` / `eq` / `neq` / `concat` は builtin テーブルではなく、auto-import された標準 trait method helper の surface として source から提供する。
その concrete impl は `lib/*.srt` に置き、compiler 側はそれと同値な comparison / concat opcode へ lower してよい。

組込み関数と bootstrap 定義のメタデータは共有テーブルまたは事前ロード済み宣言を通して管理し、名前解決・型検査・コード生成・実行が同じ定義を参照する。

## 4. 処理系構成

### 4.1 フェーズチェーン

```text
Source -> Ast -> Resolved -> Typed -> Bytecode -> Execute
```

各フェーズはフェーズ固有のエラー型を返す。

### 4.2 コンパイル単位と source 種別

処理系は compile-unit と source-kind を分けて扱う。

- `CompileUnitKind::Script`
  - 単一 script 実行
- `CompileUnitKind::DefinitionCheck`
  - 単体 definition source の検証
- `CompileUnitKind::Project`
  - project entrypoint を持つ複数 source compile
- `CompileUnitKind::Repl`
  - REPL の増分入力

- `SourceKind::Script`
  - user script source
- `SourceKind::DefinitionSource`
  - user definition source / user extension source
- `SourceKind::StdDefinitionSource`
  - `Bootstrap` / `Kernel` を含む standard definition source
- `SourceKind::ReplChunk`
  - REPL の 1 入力 chunk
  - compile 後は `BytecodeChunk` として Forge から Eldr `InteractiveVm` へ渡される
  - 直近結果は `InteractiveVm` の `last_result` に保持されるが、通常の user binding ではない

構文許可、parser context、top-level expr / `@builtin` 許可、`set_exit_code` 制約は
`sindr::policy::SourcePolicy` から導出する。`Spire::ParseRules` は `SourcePolicy.parse_profile`
を構文解析実装へ写す型、`RuntimeSourcePolicy` は `SourcePolicy.runtime_policy` の runtime-facing
部分として扱う。

- `Script`
  - top-level expr を許可
  - top-level 宣言は `include` / `import` / `const` / top-level `def` / `namespace` / `defstruct` / `defrecord` / `defenum` / `deferror` / `deftrait` / `impl Type` / `impl Trait for Type` を許可
  - `import` / `include` は `Bootstrap` に属する builtin function として文書化されるが、surface では top-level macro syntax として振る舞う
  - `include "<file_path>"`（または `include '<file_path>'`）は script 専用の loader directive として扱う
  - `include` はトップレベル宣言としてのみ許可し、引数は文字列リテラル 1 つに限定する
  - `include` は source file 先頭に連続して現れなければならず、宣言や top-level expr の後には書けない
  - `include` を他の式へ埋め込む（変数バインド、関数引数、戻り値など）は禁止する
  - top-level `def` は暗黙の擬似モジュールに属し、bare 定義 `def name ...` はその擬似モジュール配下へ canonicalize する
  - 同一 script の top-level expr と top-level `def` body では、その擬似モジュール配下 helper への bare call を引き続き許可する
  - `namespace` / `impl` / include module file / 他 module から script top-level `def` を参照するときは、その canonical path を使う
  - script top-level の `defmod` は禁止し、共有 helper は `namespace + defmod` または include module file に置く
  - `namespace` body は top-level expr を持てず、definition source と同じ declaration area として扱う
  - 最初の top-level expr が現れた後は `ExecutionSection` とみなし、それ以降の宣言は parse error とする
  - `set_exit_code` はどこでも許可
  - 既定 entrypoint は `main`
- `Module`
  - top-level expr を禁止
  - top-level 宣言は module 定義と型/trait/impl/import 定義のみ許可
  - 関数本体を持つ宣言は `defmod` / `impl` / `impl Trait for Type` の各 namespace に置く
  - primary module path は source 内の declared `defmod` head から導出し、qualified head と namespace-lowered head を同じ canonicalization 規則で扱う
  - `@builtin` を禁止
  - `set_exit_code` は原則禁止
- `StdModule`
  - top-level expr を禁止
  - top-level 宣言は std module 定義と型/trait/impl/import/`@builtin` 定義のみ許可
  - 関数本体を持つ宣言は `defmod` / `impl` / `impl Trait for Type` の各 namespace に置く
  - primary module path は source 内の declared `defmod` head から導出し、file stem や token 走査を正本にしない
  - `@builtin` を許可
  - `set_exit_code` は原則禁止
- `ReplChunk`
  - top-level expr を許可
  - top-level 宣言は `def` / `import` のみ許可
  - `const` / 型定義 / trait 定義 / `impl` / `defmod` は parse error とする
  - top-level `def` は REPL セッション内の暗黙擬似モジュールに属する
  - `set_exit_code` を禁止

`CompileUnitKind::Project` では、module / std module に対して `set_exit_code` を entrypoint のみ許可する。
この対応表の実装正本は `sindr::policy::SourceKind::policy(...)` とし、Rune / Xldr /
surtr-analysis / Spire / Scar は個別の対応表を持たず、この query から parse / runtime /
typecheck context を導く。

### 4.4 組込み関数の流れ

- `sigil` は組込み名を解決する
- `scar` は共有メタデータから型シグネチャを参照する
- `forge` は `builtin_id` を使って `CallBuiltin` を生成する
- `eldr` は `builtin_id` に対応する実装を呼び出す
- 共有メタデータの正本は `crates/sindr/src/builtin.rs` の `BUILTIN_METAS` とする

### 4.5 標準定義ソースと bootstrap source

- 標準定義ソースの初期ロード順は `Bootstrap -> [SpecialTypes, Function, Kernel, Add, Sub, Mul, Eq, Neq, Compare, Concat, Show, Ordering, Tuple, From, TryFrom, Encode, Decode, Functor, Chainable, PipeApply, Compose, Composable, LiftComposable, KleisliComposable, Int, String, Regex, Boolean, Error, List, Generator, HashMap, Result, Duration, Range, Option, Task, Facet, Float, Json, Config, Project, Random, File, FS, IO, Shell, StyledDoc] -> [Test] -> ユーザ拡張` で固定する
- このロード順と stage 分割の実装正本は [crates/xldr/src/loader.rs](/Users/haruca/work/rust/surtr/crates/xldr/src/loader.rs:137) の `STDLIB_MODULE_SPECS` とする
- Loader はこの順序を保持し、ユーザ拡張を標準定義ソースより前へ入れない
- module stage の可視境界は「前 stage + 同一 stage」とする。同一 stage 内の明示 import / auto import は file 読み込み順に依存せず解決でき、later stage の import は compile error のままとする
- 標準定義ソースも通常 module と同じ stage 可視性規則に従う。標準定義ソース同士は同一 stage 内で相互に明示 import できる
- script 内 `include "<file_path>"` は `Bootstrap` / 標準定義ソース読み込み後に、記述順で追加 module stage を連結する
- `Bootstrap`, `Kernel` は source 上で `@autoimport` が付いた standard `defmod` として auto import 対象にする
- loader / project builder は file discovery と source-kind 配線だけを担当し、standard definition source を含む module identity の決定は source 中の `defmod` head を parse/lowering した canonical path に委ねる
- `Bootstrap` / `Kernel` / user extension module の path 判定は token 走査、コメント位置、空行配置に依存しない
- standard type owner helper surface は source 上で `@autoimport` が付いた `impl Type` を auto import 対象にし、owner 名配下の public helper を unqualified に呼べるようにする
- standard trait 宣言は source 上で `@autoimport` が付いた `deftrait` を auto import 対象とし、trait 名と method helper alias を unqualified に呼べるようにする
- 明示 `import` は同じ file 内の auto-import 名を明示的に shadow してよい
- 明示 `import` 同士で同じ unqualified 関数名が衝突する場合は compile error とする
- auto-import 同士で同じ unqualified 関数名が衝突する場合も compile error とする
- 明示 `import` による shadowing は file 内に書かれた変更だけで完結し、その file 外の名前解決結果を暗黙に書き換えない
- この規則により、project 内で auto import 対象を増やしても、既存 file の呼び先が Ruby のように暗黙的にすり替わることを避ける
- `Bootstrap` / `Kernel` と、`@autoimport` が付いた標準 trait / 標準 `impl Type` owner helper surface 以外の標準定義ソース / trait / type owner helper surface は auto import しない。利用時は明示 `import` または qualified path を使う
- import 検査は file 単位で行い、同一 file 内の同一 module / 同一 member の再 import を禁止する
- `import ModName` は、その module 名前空間の import 可能 member を現在 scope へ unqualified に導入する

- 標準の先行ロード source は `bootstrap.srt`, `kernel.srt`, `styled_doc.srt`, `test.srt`, `lib/traits/operator/*.srt`, `lib/traits/*.srt`, `lib/types/*.srt`、および `lib/facet.srt`, `lib/Config.srt`, `lib/Project.srt`, `lib/Random.srt`, `lib/IO.srt`, `lib/file.srt`, `lib/FileSystem.srt`, `lib/Shell.srt` に分かれる
- `bootstrap.srt` には `@autoimport defmod Bootstrap`、`import` / `include` の `@builtin def` ドキュメント宣言、標準 concrete error (`deferror`) を置く
- `Bootstrap::import` / `Bootstrap::include` は module 所属の builtin function として docs metadata を持つが、surface 構文では引き続き top-level 専用 macro syntax を使い、block 内利用や通常の call-style surface を有効化しない
- `lib/types/special_types.srt` には `Unit`, `TypeRef<$T>`, `Hole`, `Closure`, `MatchArms<$Scrutinee, $Result>`, `CondClauses<$Result>` の canonical builtin type 宣言を置く
- `kernel.srt` には `@autoimport defmod Kernel` 配下の cross-cutting builtin 関数を置く。process / task / duration の内部 helper `__*` はここへ置かず、`Process` は public utility に限定し、process family の lower surface は `Agent` / `GenServer` / `Supervisor` など各 owner module の hidden builtin 宣言として置く
- `@hidden` は builtin 宣言層でのみ使える compiler-internal 属性であり、`@hidden @builtin def ...` / `@hidden @builtin defextractor ...` / `@hidden @builtin type ...` を受理する。hidden builtin は compiler/lowering 専用であり、user code から直接参照・import できない
- `styled_doc.srt` には通常標準定義ソースとして利用可能な `StyledDoc` surface を置く
- `Random.srt` には `RandomGenerator` の canonical builtin type 宣言、`InvalidRandomRange`、および `Random::seed` / `Random::int_until` / `Random::int_range` / `Random::next_int_until` / `Random::next_int_range` surface を置く。`Random` は auto import しない
- `IO.srt` には標準入力固定の `IO::get` / `IO::get_line` surface と `InputError` を置く。`IO` は auto import しない
- `file.srt` には `defmod File`、`FileMode`、`FileHandle` の surface を置く。File v1 の path は実行時の current working directory 基準で解決し、`read` / `write` / `append` / `delete` / `exists` / `with_open` / `read_chunk` / `write_chunk` / `flush` を提供する。`File` は auto import しない
- `FileSystem.srt` には `defmod FS`、`FilePath`、`FileSystemSnapshot`、entry / metadata 型、および path / stat / ls / tree_depth / mkdir / rm / mv / cp の surface を置く。File content I/O は既存 `File` が担い、`FS` は snapshot と filesystem metadata / 最小 mutation を担う。`FS` は auto import しない
- `Shell.srt` には `defmod Shell`、`CommandResult`、`pwd` / `cd` / `exec` の surface を置く。`exec` は起動済み command の非ゼロ終了を `Ok(CommandResult)` として返し、spawn / cwd / host I/O 失敗だけを `Err` とする。`Shell` は auto import しない
- `test.srt` には `surtr test` が消費する `Test` DSL surface を置く。`Test` は `StyledDoc` を明示 import するが、標準定義ソースは同一 stage 可視性を持つため loader では `StyledDoc` と同じ標準 stage に置く
- trait helper surface の auto import は trait ごとに opt-in とし、`@autoimport` が付いた trait だけが unqualified helper alias を file-local prelude へ導入する
- この alias は新しい関数定義ではなく、canonical な `Trait::method` symbol への別名とする
- operator trait のうち pipeline / guard / predicate と相性がよい helper (`eq`, `neq`, `compare`, `concat`) は `@autoimport` 対象にしてよい
- `From::from` / `TryFrom::try_from` は型変換の中枢 surface として `@autoimport` 対象にする。`Encode::encode` / `Decode::decode` は format value owner helper（例: `JsonValue::{encode, decode}`）経由で使うため auto import しない
- `Show::to_string` のような cross-cutting helper trait も、shared helper surface として必要なら `@autoimport` 対象にしてよい
- `Add::add` / `Sub::sub` / `Mul::mul` のように「演算子の別表記」が主目的の helper は既定では auto import しない。利用時は `Add::add(...)` のような qualified call か明示 `import` を使う
- unqualified helper surface (`to_string`, `eq`, `compare`, `concat`, `from`, `try_from`, `encode`, `decode` など) は compiler 固有の名前差し替えではなく、これらの auto-import trait method alias から file-local に導入される
- 標準 primitive/runtime-facing base type の trait impl (`Add`, `Sub`, `Mul`, `Eq`, `Neq`, `Compare`, `Concat`, `Show`) は `lib/traits/**/*.srt` と type module に置き、Rust 実装側はその source 正本に対する lower / 最適化のみを持つ
- type ごとの標準定義ソースは `lib/types/int.srt`, `lib/types/string.srt`, `lib/types/regex.srt`, `lib/types/boolean.srt`, `lib/types/error.srt`, `lib/types/list.srt`, `lib/types/option.srt`, `lib/types/generator.srt`, `lib/types/hash_map.srt`, `lib/types/result.srt`, `lib/types/duration.srt`, `lib/facet.srt`, `lib/types/float.srt`, `lib/types/json.srt` に分ける
- canonical builtin type 宣言は各対応 file のトップレベルに置く
- compiler-special builtin type (`Unit`, `TypeRef<$T>`, `Hole`, `Closure`, `MatchArms<$Scrutinee, $Result>`, `CondClauses<$Result>`) は `lib/types/special_types.srt` に集約する
- `@builtin type` は `defmod` の内側ではなく、標準定義ソース file のトップレベル定義として扱う
- type module 内の member namespace は、通常 `defmod` ではなく対応する `impl Type` を正本とする。標準型も user-defined `impl` と同じ owner 規則に従う
- `list.srt` はトップレベルに canonical builtin type 宣言 `List<$A>` と `ReduceStep<$A>` を持ち、関数 surface は `impl List` に置く
- `impl List` には `cons`, `first`, `last`, `at`, `len`, `append`, `concat`, `reverse`, `reduce`, `reduce_while`, `map`, `flat_map`, `filter`, `find`, `find_map`, `any`, `all`, `count`, `sum`, `max`, `min`, `max_by`, `min_by`, `sort`, `sort_by`, `take`, `drop`, `take_while`, `drop_while`, `span`, `partition`, `dedup`, `group_count`, `zip` を置く
- `result.srt` はトップレベルに canonical builtin type 宣言 `Result<$T>` と `Ok($T)`, `Err(Error)` を持ち、関数 surface は `impl Result` に置く
- `impl Result` には `is_ok`, `is_err`, `map_err`, `cause`, `chain` を置く
- `option.srt` はトップレベルに `defenum Option<$T> { Some($T), None }` を持ち、`impl Option` には `is_some`, `is_none`, `wrap` を置く。`Result` との変換は `impl From<Result<$T>> for Option<$T>` / `impl From<Option<$T>> for Result<$T>` として置く
- `Option` には `impl Functor<$A, $B, Option<$B>> for Option<$A>` と `impl Chainable<$A, Option<$B>> for Option<$A>` を置く
- `Option` は auto import しない
- `hash_map.srt` はトップレベルに canonical builtin type 宣言 `HashMap<$V>` を持ち、関数 surface は `impl HashMap` に置く
- `impl HashMap` には `empty`, `from_entries`, `len`, `contains_key`, `get`, `insert`, `remove`, `keys`, `values` を置く
- `HashMap` は immutable map とし、key は常に `String` とする
- `hash![key => value, ...]` は `HashMap<$V>` literal とし、key は `String` 型を得られる任意の式、value は同一型の式とする
- `hash![]` は空の `HashMap<$V>` literal として扱い、value 型は利用文脈または後続推論で決まる
- `HashMap` の runtime 内部表現は `HashMap<String, Value>` とする
- `HashMap::get` は hit で `Ok(value)`、miss で `Err(NoneError)` を返す
- `HashMap::insert` の duplicate key は値のみ更新する
- `HashMap::keys` / `HashMap::values` / `HashMap::entries` / `inspect(HashMap)` / `to_string(HashMap)` はキー昇順の deterministic order を使う
- `HashMap` の表示は生成可能な literal 形式 `hash!["key" => value, ...]` を使い、空 map は `hash![]` と表示する
- `Generator` の runtime bridge (`gen_make` / `gen_idx` / `gen_items`) は `lib/types/generator.srt` の `impl Generator` 内に `@builtin defp` として置く。これらは標準ライブラリ内部専用であり、利用者向け surface は `unfold` / `iterate` / `range` / `range_step` / `range_char` / `next` / `idx` / `take` / `to_list` などの public helper とする
- `json.srt` はトップレベルに `JsonValue`, `JsonParseError`, `JsonDecodeError`, `JsonEncodeError` を置き、`defmod Json` に `parse`, `stringify`, `decode`, `encode`, `get`, `at`, `kind`, `as_string`, `as_int`, `as_float`, `as_bool`, `as_array`, `as_object` を置く
- `Json` は auto import しない。`Json::parse` / `Json::stringify` は builtin 実装だが、schema-level decode / encode は Surtr source の明示 `impl Decode<T> for JsonValue` / `impl Encode<JsonValue> for T` で書く
- `Random::int_until(end)` は `0 <= n < end` の `Result<Int, InvalidRandomRange>` を返し、`end <= 0` は `Err(InvalidRandomRange(0, end))` を返す
- `Random::int_range(start, end)` は `start <= n < end` の `Result<Int, InvalidRandomRange>` を返し、`start >= end` は `Err(InvalidRandomRange(start, end))` を返す
- `Random::seed(seed)` は opaque な `RandomGenerator` を返し、`Random::next_int_until` / `Random::next_int_range` は `(value, next_rng)` を `Ok` で返す。生成列の厳密なアルゴリズムは surface 契約に含めないが、同じ Surtr version 内では seed から再現可能とする
- `facet.srt` はトップレベルに canonical builtin type 宣言 `Facet<$K, $S, $A, $T, $B>` を持ち、関数 surface は `impl Facet` に置く
- `impl Facet` には `view`, `set`, `over`, `compose` を置く
- `List` は先頭からの逐次処理とパターン分解を中心に扱い、ランダムアクセスや末尾追加は主用途にしない
- Expr 位置の `[head, ..tail]` は list 構築 surface として扱い、Pattern 位置の `[head, ..tail]` は `List` / `String` の sequence 分解 surface として扱う。`String` では `Kernel::uncons(head, tail)` の alias とし、`uncons` を通常の公開関数としては置かない
- Expr 位置の `[start..stop]` は inclusive range literal として扱う。`[Int..Int]` は `List<Int>` を返し、`[String..String]` は `Result<List<String>, Error>` を返す
- range literal の `String` endpoint は `Generator::range_char` と同じく single ASCII char 契約に従い、不正な endpoint は constant literal でも runtime に `InvalidCharRange` として報告する
- constant な `[Int..Int]` は compile-time に `List` literal へ fold し、constant な `[String..String]` は compile-time に `Ok(List literal)` へ fold する
- `[]` は `List` の Nil であり、singleton 構築は `[x]` または `List::cons(x, [])` で表す
- `List::first([])` は `Err(NoneError)` を返す
- `List::last([])` は `Err(NoneError)` を返す
- `List::at(values, index)` は負 index と範囲外 index に対して `Err(IndexOutOfBounds("index #{index} out of bounds for len #{List::len(values)}"))` を返す
- `List::sum([])` は `0` を返す
- `List::max([])` / `List::min([])` は `Err(NoneError)` を返す
- `List::min_max([])` は `Err(NoneError)` を返す
- `List::max_by([])` / `List::min_by([])` は `Err(NoneError)` を返す
- `List::max(values)` / `List::min(values)` は `Compare` を満たす要素について使え、要素型を保った `Result<$A, NoneError>` を返す
- `List::min_max(values)` は `Compare` を満たす要素について使え、`Result<($A, $A), NoneError>` として `(min, max)` を返す
- `List::sort(values)` は `Compare` を満たす list を昇順で並べ替えた新しい list を返す
- `List::sort_by(values, cmp)` は `cmp(left, right)` が `Ordering::Less` を返すときに `left` を先に置く
- 標準ライブラリは tuple arity `2..=8` に対して lexicographic な `Compare` 実装を提供する。arity `9` 以上はユーザ実装または nested tuple で扱う
- `List::count(values, pred)` は `pred` を満たす要素数を返す
- `List::take(values, count)` は `count <= 0` で `[]` を返し、`count > len` では入力全体を返す
- `List::drop(values, count)` は `count <= 0` で入力全体を返し、`count > len` では `[]` を返す
- `List::take_while(values, pred)` は最長 prefix を返す
- `List::drop_while(values, pred)` は最長 prefix を落とした suffix を返す
- `List::span(values, pred)` は `(take_while(values, pred), drop_while(values, pred))` を返す
- `List::partition(values, pred)` は `(matched, rest)` を返し、両側とも元の順序を保つ
- `List::dedup(values)` は最初の出現順を保ちながら重複を除く
- `List::group_count(values)` は `Eq` を満たす要素について `List<(value, count)>` を返し、group の順序は最初の出現順に従う
- `List::sort_by` は任意型に使え、`List::max`, `List::min`, `List::min_max`, `List::sort` は `Compare` 実装型を単一 trait bound で受ける
- `List::zip(left, right)` は短い方の長さで打ち切り、`List<(left_i, right_i)>` を返す
- `List::find`, `List::find_map`, `List::any`, `List::all` の早期終了は `List::reduce_while` と `ReduceStep::Resume` / `ReduceStep::Stop` を基盤にする
- List 構築の推奨スタイルは引き続き `List::cons + List::reverse` とする。公開 surface は逐次処理 helper を中心に広げつつ、比較系 helper として `sort_by` と `Compare` bound の `sort` / `max` / `min` を含める
- `int.srt` のトップレベルには `BitWidth { W8, W16, W32, W64, W128, Any(Int) }` と、`NegativeShiftCount`, `NegativeBitIndex`, `InvalidBitWidth`, `BitIndexOutOfRange` を置く
- `int.srt` の `impl Int` には `safe_div`, `safe_mod`, `bit_and`, `bit_or`, `bit_xor`, `bit_not`, `test_bit`, `set_bit`, `clear_bit`, `toggle_bit`, `width_bits`, `mask`, `wrap_unsigned`, `wrap_signed`, `bit_not_in`, `test_bit_in`, `set_bit_in`, `clear_bit_in`, `toggle_bit_in`, `shl_in`, `shr_logical_in`, `rotl_in`, `rotr_in`, `shl`, `shr`, `abs`, `min`, `max`, `sign`, `is_even`, `is_odd` を置く
- `int.srt` のトップレベルには `impl Add/Sub/Mul/Eq/Neq/Compare/Show for Int` を置く
- `bit_and` / `bit_or` / `bit_xor` / `bit_not` / `shl` / `shr` / `test_bit` / `set_bit` / `clear_bit` / `toggle_bit` の direct call は専用 Opcode に lower する。負 shift count / bit index の検証も opcode 側で行い、surface 互換の `Err(NegativeShiftCount(...))` / `Err(NegativeBitIndex(...))` を返す
- `BitWidth::Any(bits)` は `bits > 0` のときだけ有効とし、fixed-width helper は invalid width を `Err(InvalidBitWidth(...))` として返す
- fixed-width helper の bit index は `0 <= index < width` を満たす必要があり、違反時は `Err(NegativeBitIndex(...))` または `Err(BitIndexOutOfRange(...))` を返す
- `shl` / `shr` と fixed-width shift/rotate helper は負 shift count を `Err(NegativeShiftCount(...))` で返す
- `string.srt` の `defmod String` には `is_empty`, `non_empty`, `len`, `surround`, `join`, `repeat`, `starts_with`, `ends_with`, `strip_prefix`, `strip_suffix`, `split_once`, `contains`, `replace`, `split`, `lines`, `chars`, `from_chars`, `codepoints`, `from_codepoints`, `trim_start`, `trim_end`, `trim` を置く
- `String::repeat` は負 count で `Err(NegativeRepeatCount(...))` を返す
- `String::strip_prefix` / `String::strip_suffix` / `String::split_once` は失敗時に `Err(NoneError)` を返す
- `String::split_once` の成功結果は `StringSplit::Split(before, after)` で表す
- `String::replace(value, "", to)` は `value` をそのまま返す
- `String::split(value, "")` は `List<String>` の文字列分解結果を返す
- `String::lines(value)` は `\n` で分割し、各行末の `\r` を除去し、末尾改行だけで生じる最終空行は落とす
- `String::from_chars` は 1 文字以外の要素を受け取ると `Err(InvalidCharList(...))` を返す
- `String::codepoints` / `String::from_codepoints` は `StringEncoding::{Utf8, Ascii}` を受け取る
- `String::codepoints(value, StringEncoding::Utf8)` は UTF-8 byte 列を `List<Int>` として返す
- `String::codepoints(value, StringEncoding::Ascii)` は ASCII 範囲外文字を含むと `Err(InvalidStringEncoding(...))` を返す
- `String::from_codepoints(values, StringEncoding::Utf8)` は各 `Int` を 0..255 の byte として解釈し、不正な byte 列を `Err(InvalidStringEncoding(...))` とする
- `String::from_codepoints(values, StringEncoding::Ascii)` は各 `Int` が 0..127 を満たすときだけ成功し、違反時は `Err(InvalidStringEncoding(...))` を返す
- `String::trim_start` / `String::trim_end` / `String::trim` は space / newline / tab / carriage return の ASCII whitespace のみを除去対象にする
- `regex.srt` のトップレベルには canonical builtin type 宣言 `Regex`, `RegexCaptures`, `RegexMatch` を置く
- `impl Regex` には `compile`, `is_match`, `captures`, `find`, `find_all`, `split`, `replace`, `replace_all`, `escape`, `group_names` を置く
- `impl RegexCaptures` には `whole`, `capture_count`, `get`, `get_name` を置く
- `impl RegexMatch` には `text`, `start`, `end` を置く
- `Regex::compile` は失敗時に `Err(RegexCompileError(...))` を返す
- `Regex::captures` / `Regex::find` / `RegexCaptures::get` / `RegexCaptures::get_name` は miss を `Err(NoneError)` で返す
- `boolean.srt` の `impl Boolean` には `not`, `xor`, `eqv`, `implies` を置く
- `float.srt` の `impl Float` には `safe_div`, `abs`, `min`, `max`, `floor`, `ceil`, `round`, `trunc`, `pi`, `e` を置く
- `float.srt` のトップレベルには `impl Add/Sub/Mul/Eq/Neq/Compare/Show/From/TryFrom for Float` を置く
- `duration.srt` の `impl Duration` には `new`, `millis`, `sub`, `deconstruct` を置く。`sub(self, rhs)` は負になる場合 `Err(InvalidDuration(...))` を返す
- `duration.srt` のトップレベルには `impl Add/Eq/Neq/Compare/Show/TryFrom<Duration> for Duration/Int` を置く。`Add/Eq/Neq/Compare` は `millis` field を使う Surtr 実装とし、compiler builtin dispatch にはしない。`Sub` trait は戻り値が `Self` 固定のため `Duration` には実装しない
- 標準定義ソースの利用者向け説明は `lib/*.srt` の `@doc` を正本とする
- `Bootstrap` を先に置く理由は、auto-import の起点と loader の固定基準点を確保するためである
- 現行実装のファイル名は `lib/bootstrap.srt`, `lib/kernel.srt` および各 type module file である

### 4.5.1 段階的コンパイル snapshot と semantic aggregate

標準定義、script preload、project preload、REPL live chunk は prefix/suffix を持つ段階的コンパイルとして扱う。
標準定義の stage list と cache key material の実装正本は `xldr::loader::STDLIB_MODULE_SPECS` と
`StdlibModuleSpec` であり、手書き列挙は説明用の要約とする。

Xldr が公開する `StagedCompilationSnapshot` / `CompilationPrefixSnapshot` は、module stages、
declaration index、resolver checkpoint、Scar checkpoint、bytecode、docs/signatures、auto-import
metadata をまとめる上位 aggregate である。`sindr` に置くのは source policy、stage metadata、
cache key schema version など bytecode-independent な情報までとし、Scar / Forge / Eldr 型を含む
checkpoint は上位 crate に残す。

tooling / REPL / LSP が使う symbol 情報は `surtr-analysis::SymbolSemanticInfo` を正本 aggregate とする。
`CompletionSymbol` は UI 投影 DTO であり、identity、capability、visibility、importability、
stage、source location、doc/signature display metadata を推定する正本にしない。
`.eldr` の `DocEntry` / `SignatureEntry` は表示 metadata であり、compile-space の import /
visibility / capability は declaration index と semantic aggregate に由来する。

少なくとも bootstrap source には次の汎用 error が含まれる。

```surtr
deferror NoneError { "None Value." }
deferror ZeroDivisionError { "division by zero" }
```

### 4.6 解決と並列化の不変条件

- 段階的ファイルリードを許可し、まず declaration index を収集する
- declaration index は本体解決なしで構築し、同一 stage の file 読み込み順に依存しない
- 同一 stage / 前 stage の参照は declaration index と各フェーズの predeclare pass で解決する
- later stage 参照、重複宣言、型循環などの失敗は、該当 pass の決定的順序で fail-fast に診断する
- `unique_id` 採番は並列実行順に依存させず、`stage_index -> fq_name` の決定的順序で割り当てる
- user type tag は型 predeclare 順に決定し、並列実行順に依存させない
- 明示的な依存グラフ、再評価用 queue、保留参照集合、固定点 failure 集約は現行 V1 の保証対象外とする
- 失敗診断（主原因/副原因の位置）は実行スケジュールに依らず決定的であること
- step compile では同一入力から同一 bytecode 列を返す
- 将来の並列 compile では、実行意味に影響しない `func_id` 等の差を許容し、bytecode 集合同値を保証対象とする

### 5.1 実行モデル

### 5.2 Value（概念）

- プリミティブ値
- `List`
- `HashMap`

## 12. 診断と source span

- compiler 内部の source span は character offset を正本とする
- human-readable diagnostic と JSON diagnostic の `line` / `column` は character offset 基準で計算する
- JSON diagnostic の `span` は `[char_start, char_end]` を表す
- ariadne など byte range を要求する外部 API には、出力直前に character offset から byte offset へ変換して渡す
- `.eldr` source map と runtime error location も同じ character offset 契約で扱う
- タグ付き値（構造体、レコード、`Result`）
- `Callable`
- `Error`

`inspect` / `to_string` における `Callable` 表示は、bare callable
（`lexical_captures == 0`）かつ runtime metadata から
`module` / `name` / `signature` を復元できる場合、
`FnCapture(module: M, name: f, signature: sig)` を返す。
それ以外の callable は implementation-defined な fallback 表示を使う。

### 5.3 TypeRegistry

- 型タグから型名とフィールド名を逆引きする
- `Ok = 0`, `Err = 1` を予約する
- ユーザ定義型タグは `scar` の型 predeclare 順で決定的に割り当て、並列コンパイル時も同一入力で同じ tag 配置を保証する
- runtime tag は user-visible `Int` とは別の内部 ID として扱う

### 5.4 現行ランタイム表現の暫定方針

- V9 時点では言語機能実装を優先し、プリミティブ値とコレクションの細部挙動は現行 Rust 実装と VM 表現に強く依存してよい
- ここで述べる内容は実装注記であり、将来の最適化や表現変更を妨げる恒久仕様とはしない
- ただし、ユーザに見える挙動へ影響する箇所は本書で明示する

`String` は Rust の UTF-8 文字列として保持する。

- 長さ、走査、部分操作のコストは UTF-8 と実装方式に依存する
- バイト数、Unicode scalar value 数、表示上の文字数は一致しない場合がある
- V9 では `==`, `!=`, `++`, 表示系 builtin を優先し、細粒度の文字列 API は慎重に追加する

`Int` は意味論上 unbounded integer として扱う。

- 現行実装は `BigInt` を用いる
- 算術オーバーフローは `Int` の通常計算では起きない
- `set_exit_code` や bit shift のようにホスト整数へ落とす箇所では、明示的な範囲検査を行う
- source literal は `123`, `0d123`, `0xff`, `0o17`, `0b1101` を受理する
- prefix なし literal は decimal として扱う
- `0x`, `0o`, `0b`, `0d` の digit 欠落と、基数不正 digit は parse phase の compile error とする
- uppercase prefix (`0X`, `0O`, `0B`, `0D`) と `_` 区切り literal は V9 範囲外とする

`Float` は Rust の `f64` 相当として扱う。

- user-visible `Float` value は常に finite value に制限する
- source float literal、builtin constant、VM arithmetic、`safe_div`、JSON bridge は non-finite value を生成しない
- `Float::safe_div(Float, Float)` は divisor が `0.0` のとき `Err(ZeroDivisionError)` を返す
- 標準 helper として `abs`, `min`, `max`, `floor`, `ceil`, `round`, `trunc`, `pi`, `e` を提供する
- 表示は Rust `f64` の通常表示を基礎にし、整数値に見える場合は末尾 `.0` を補う

`UnsignedInt` は V9 範囲外とする。

- 導入時は Rust の対応整数型に準拠して実装してよい
- ビット幅、オーバーフロー、シフト、比較規則は導入時に明文化する
- `Int` と `UnsignedInt` の相互演算規則は未定義のまま先行実装しない

`List` は VM 上で cons cell 表現を前提とする。

- 先頭追加と分解は自然だが、ランダムアクセスや末尾追加は効率的ではない
- リスト操作の性能特性は配列系コンテナとは異なる
- V9 では関数型リストとしての意味論を優先し、高速シーケンス処理は将来別表現または別型で補いうる
