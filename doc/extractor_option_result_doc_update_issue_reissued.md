# Extractor / Option / Result ドキュメント更新イシュー用整理メモ

## 目的

本メモは、Extractor / Option / Result の位置づけと説明方針を、利用者向けドキュメント更新のために整理したものである。
ここで扱うのは主に以下の観点である。

- `Option` を標準に置くかどうか
- `Result` を言語機能の主軸としてどう説明するか
- `Extractor` を「多機能機構」ではなくどう位置づけるか
- `Nomatch` を user-facing な値として扱わない理由
- 変数バインド位置を限定する設計と、マクロ安全性の関係

---

## 1. 結論

### 1.1 Option

- `Option` は標準に用意してよい
- ただし `Result` と同等には扱わない
- `Option` は言語機能サポート対象ではない
  - 関数演算子の文脈で `Result` と同等に扱わない
  - `SafeBind` の対象にしない
- `Option` と `Result` の相互変換はサポートする
- 変換は常に明示的に行う
- 暗黙的なキャストは行わない

### 1.2 標準モジュールの返り値

- 標準モジュールはすべて `Result` 型で返す
- 欠損や失敗を early return / `SafeBind` / 関数演算子に載せたいケースは `Result` を使う
- `Option` は user code 側で必要に応じて選ぶ補助的な標準 enum として扱う

### 1.3 Extractor

- `Extractor` は関数レベルでの値のやり取りを、変数束縛位置で行うための言語機能とする
- `Extractor` は並列合成などの高機能 combinator を持たない
- 複数候補を返したい場合は、`Enum` や構造体、tuple などで明示的に返す
- 複雑な分岐を surface syntax に増やすのではなく、愚直でシンプルなコーディングを推奨する

### 1.4 Nomatch

- `Nomatch` は runtime 制御のための内部概念である
- user-facing な値フローの主役にはしない
- user からは `Err` と同じ扱いしかできない
- user が no-match 相当を明示的に制御したい場合は、`Option` などで返して通常の値として扱う

---

## 2. Option を標準に置くが主軸にしない理由

### 2.1 Option を全面採用しない理由

`Option` を失敗処理の主軸にしない理由は次の通りである。

- `Option` と `Result` を並立させると、利用者が明示的な変換を頻繁に意識する必要がある
- `Result` と同じ制御基盤に載せるくらいなら、最初から `Result` 1 本に寄せた方が単純である
- 暗黙的な変換を入れると、どこで欠損が失敗へ変わったかがコード表面から見えなくなる
- 回復処理は `match` や API による通常分岐で十分に表現できる

したがって、`Option` は「存在してよい標準 enum」ではあるが、Surtr における失敗伝播の中心には置かない。

### 2.2 Option を標準に置く理由

一方で、`Option` を標準に置くこと自体は許容できる。

- user が独自に `Enum` を定義して使うこと自体は自然である
- `Option` もその延長として理解できる
- 欠損を `Option` として表したい user code はありうる

ただし、その場合も `Result` への変換は user が明示的に行う必要がある。

### 2.3 ドキュメントで必須の説明

`Option` を標準に置くなら、少なくとも次は明記が必要である。

- `Option` は `Result` と同等には扱われない
- `Option` は `SafeBind` の対象ではない
- `Option` は `Result` 文脈の関数演算子サポートを受けない
- `Option` と `Result` の変換は明示的に行う
- 暗黙的なキャストは存在しない

この説明がないと、利用者は「標準にあるのに、なぜ `=?` できないのか」「なぜ `Result` と同じように流せないのか」で混乱しやすい。

---

## 3. なぜ標準モジュールはすべて Result を返すのか

標準モジュールを `Result` に統一する理由は、Surtr の制御フローを 2 値に揃えるためである。

- `SafeBind`
- 関数演算子
- early return
- 通常の error 伝播

これらは `Result` を中心にすると一貫して説明できる。

標準モジュールが `Option` と `Result` を混在させると、利用者は

- どこで変換が必要か
- どこで欠損と失敗が分かれているか
- どの API が early return に載るか

を毎回意識しなければならない。

そのため、標準モジュールはすべて `Result` を返す方針とする。

`Option` は user-facing な補助型であり、標準ライブラリの主導線には置かない。

---

## 4. Extractor の位置づけ

### 4.1 Extractor は多機能機構ではない

利用者が現在の説明を読むと、Extractor を多機能な仕組みとして受け取りやすい。

しかし設計意図は逆である。

Extractor の目的は、機能を増やすことではなく、呼び出し側に現れる情報を減らすことにある。

### 4.2 Extractor の役割

Extractor の役割は次である。

- 値の分解
- 前提条件の確認
- 局所的な失敗処理
- 抽出結果の shape の正規化

これらを Extractor 内部へ閉じ込めることで、呼び出し側には主に次だけが現れる。

- Extractor 関数名
- 第一引数である式
- 抽出結果一覧

これにより、分解コード、条件分岐、失敗処理が呼び出し側へ散ることを防げる。

### 4.3 Surtr で Extractor が必要な理由

プログラミング言語では、変数バインドの機能が弱いと次がコード上に散りやすい。

- 値を分解するためのコード
- `if` を伴う局所分岐
- 値検証
- 失敗処理

Surtr ではこれらを Extractor 内部へ閉じ込めることで、呼び出し側では正常系だけを平坦に読みやすくする。

### 4.4 Surtr の Extractor が意識している 3 点

Surtr の Extractor は、特に次の 3 点を意識している。

- `Result` 標準
- 静的型付け
- 変数を扱う位置の限定

Elixir では、パイプの末尾に単純なタプルを返す関数を置くことで似た整理ができる。
Surtr の Extractor も「分解ロジックを呼び出し側から隠し、正常系を前面に出す」という狙いは近い。
ただし Surtr では、`Result` を標準の失敗表現とし、静的型付けで抽出結果を固定し、さらに変数束縛を許可する位置を限定している。
Extractor はこの前提の上で、分解・検証・局所失敗処理を内部へ閉じ込め、呼び出し側には必要最小限の情報だけを見せるための言語機能である。

### 4.5 Extractor の設計上の制約

Extractor は次のような方向へは広げない。

- 並列合成
- parser combinator 的な高機能化
- user-facing な三値制御モデルの公開

複数候補を扱いたい場合は、Extractor 合成を増やすのではなく、Extractor 側で `Enum` や構造体に正規化して返す。

## 5. Nomatch の位置づけ

### 5.1 Nomatch は内部制御である

`Nomatch` は runtime の制御のために存在する概念である。

- `match` では次の arm へ進むための制御
- Extractor 評価系における no-match 表現

この意味で、`Nomatch` は通常の user-facing 値フローに載せるためのものではない。

### 5.2 user からの見え方

user から見た `Nomatch` は、実質的には `Err` と区別できない。

- `Nomatch` を精密にハンドリングする API は持たない
- 関数をまたぐ値フローの主役にはしない
- user が no-match を明示的に操作したい場合は `Option` などを返して通常の分岐で扱う

### 5.3 なぜ user-facing 三値モデルにしないのか

三値を表面へ出すと、次の問題が起きる。

- `Option` 的ネストや回復分岐が LHS に持ち込まれる
- `MatchResult` を明示的に `match` する冗長さが増える
- これまで `Result` ベースで平坦に書けていたコードが崩れる

そのため、`Nomatch` は user-facing な公開制御モデルにはしない。

---

## 6. 変数バインド位置の限定とマクロ安全性

### 6.1 なぜ変数バインド位置を限定するのか

Surtr が変数バインドを限定的に扱うのは、イミュータブル性を強調するためだけではない。

- 束縛と値渡しの発生位置をトークン出現位置で追えるようにする
- どこで新しい名前が導入されるかを surface syntax だけで把握できるようにする
- マクロによる呼び出し側ローカル環境の暗黙的書き換えを禁止する根拠にする

### 6.2 規則

次のような統一規則を置く。

- 新しい束縛は `=` の左辺で起こる
- 値は右辺や引数位置から流れる
- それ以外の位置では、呼び出し側の変数環境は変更されない

### 6.3 マクロ安全性への効果

この規則があることで、たとえ

```surtr
set_var!(num, 10)
```

のような危険そうなマクロがあっても、呼び出し側の `num` が暗黙に再束縛されることはないと説明できる。

マクロは式や構文片を生成できても、呼び出し側の変数束縛を汚染する特権は持たない。

### 6.4 Extractor との関係

Extractor は値分解と検証を内部へ閉じ込めるが、束縛そのものは依然として LHS にしか現れない。
したがって Extractor は「暗黙に変数を増やす機能」ではなく、「束縛位置を固定したまま分解ロジックだけを局所化する機能」として説明できる。

---

## 7. 利用者向け説明方針

ドキュメントでは、Extractor / Option / Result を「できること一覧」で説明するより、何を単純化するかで説明した方が誤解が少ない。

### 7.1 Option

- 標準 enum として存在する
- ただし `Result` と同等には扱われない
- 失敗伝播の主軸ではない
- `Result` への変換は明示的に行う

### 7.2 Result

- 標準モジュールの返り値の基盤
- early return / `SafeBind` / 関数演算子の主軸
- 標準ライブラリの失敗処理は `Result` に統一される

### 7.3 Extractor

- 多機能な仕組みではない
- 分解・検証・局所失敗処理を呼び出し側から隠すための機能
- 呼び出し側には正常系だけを平坦に見せる
- 複雑な候補統合は Extractor 内で `Enum` 等へ正規化して返す

### 7.4 一文で説明するなら

> Extractor は、分解と検証を呼び出し側から隠し、`Result` ベースの早期リターンに乗せたまま正常系を前面に出すための構造化バインド機構である。

---

## 8. ドキュメント更新で明記したいポイント

### 必須

- `Option` は標準に存在するが、`Result` と同等の言語サポートは受けない
- 標準モジュールはすべて `Result` 型で返す
- `Option` と `Result` の変換は明示的に行う
- 暗黙的なキャストは存在しない
- `Nomatch` は runtime 制御のための内部概念であり、user-facing な制御モデルではない
- `Extractor` は並列合成などを持たない
- `Extractor` は複雑な制御を増やすためではなく、呼び出し側の情報を減らすための機能である
- `Extractor` は式として呼べず、MatchBlockないでのみ有効である

### 補足

- 変数バインド位置の限定は、イミュータブル性とマクロ安全性の両方の根拠である
- Extractor はこの規則を壊さずに、値分解だけを強くするための仕組みである

---

## 9. 短いまとめ

Surtr では、失敗伝播の主軸を `Result` に統一する。
`Option` は標準 enum として提供してよいが、言語機能としては特別扱いせず、`Result` との変換も明示に限定する。
`Nomatch` は runtime 制御のための内部概念であり、user-facing な三値制御にはしない。
`Extractor` は高機能化を目指すのではなく、分解・検証・局所失敗処理を内部へ閉じ込め、呼び出し側には正常系だけを平坦に読ませるための言語機能として位置づける。
また、変数束縛位置を限定する設計は、イミュータブル性の強調だけでなく、マクロが呼び出し側のローカル変数を暗黙に汚染しないことを保証する基盤でもある。
