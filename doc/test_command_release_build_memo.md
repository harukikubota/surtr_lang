# リリースビルドの test 改修メモ

作成日: 2026-10-04

状態: 今回の標準テスト再構成PRへ含めない、未設計・未実装の後続課題。本書の現行構成の説明は設計上の制約であり、新しい実装タスクではない。

## 課題の位置付け

リリースビルドの `surtr test --all` は、ユーザプロジェクトを対象とするプロジェクトモードにする。その対象選択、依存収集、コンパイル、キャッシュ、実行、集計の戦略は別課題として1から設計する。

単体の実パス指定と開発用の標準allの入口選択・配置は、[テスト方針](../docs/dev/テスト方針.md)の「標準ライブラリ test script」を正本とする。

debug/releaseのモード分岐、未実装release用allの未対応エラー、プロジェクトモードは引き続き後続設計に残す。標準allの対象ファイル0件を失敗にする新案は、プロジェクト側の対象0件の契約を確定するものではない。リリース用の製品コード・テストは追加していない。

## 現時点で判明していること

### CLIと実行単位

- 現行Runeのtestには開発／リリースの対象選択分岐がない。
- 現行 `--all` はCWDの `lib/tests` を探索し、入口をソートして1スクリプトずつコンパイル・実行する。
- 各スクリプトには独立したVMを作る。全テストを一括して1つのコンパイル単位にまとめる方式ではない。
- `ExecutionEnv::Test` のコンパイル単位は現行では `Script`。プロジェクト用テストの契約とは別に設計する必要がある。

### 依存の収集と重複

- 通常のスクリプトでは、1つの入口ファイルのincludeが依存の指定場所になる。
- 現行の単体・allは、入口のincludeに加えてCWDの `lib` から追加モジュールを自動収集する。この自動収集と明示includeが同じ依存を取り込む可能性がある。
- 異なる入口がそれぞれ同じ依存をincludeすることは、独立したコンパイル単位なら、それだけで衝突しない。
- 現行のソース登録は、同じファイル名・内容・種別・モジュール情報の登録でSourceIdを再利用する。ただしコンパイル対象のステージは残り、後段のモジュール重複判定で拒否されうる。
- 重複includeの許可と、異なるファイルによる同名定義の衝突は区別する必要がある。モジュール重複診断を一律に無効にする設計にはしない。

### 標準環境のキャッシュ

標準環境には、プロセス内で共有するスナップショットとディスクキャッシュがある。スナップショットは標準モジュールのAST、宣言インデックス、名前解決の再開状態、型検査状態、bytecode等を保持する。

テスト用標準環境は `StdlibVariant::TestEnabled` で選ぶ。ユーザプロジェクトのモジュール群は、この標準環境とは別の共有対象になる。

追加モジュールのparseと宣言インデックス構築は、依存キャッシュを確認する前に行われる。ヒット時もこの処理は残る。

また、スクリプト本体にprocess定義がある場合は、現行の追加モジュール向けキャッシュを使わない。通常の `surtr run` もこのキャッシュの対象外で、スクリプト全体のbytecodeキャッシュを利用する。

### 入力収集の再利用とコンパイル結果の再利用は別

CWDの `lib` のソース収集は、同一プロセス内で `OnceLock` により再利用される。これはソースの読み込み結果であり、ユーザモジュール群のコンパイル済み環境を共有する機能ではない。

現行testには、スクリプト全体のbytecodeを `target/surtr-test-cache/eldr` に保存するキャッシュもある。スクリプトと依存が変わらなければ再実行時にコンパイルを省けるが、入口間の共通依存共有とは別の機能である。

### 既存プロジェクトrunner

Xldrには、プロジェクト設定を実行してモジュールの入力ステージを得る処理がある。現時点の調査では、これがリリース用testの実行戦略や共通環境キャッシュを完成させているとは確認していない。

## 次の設計課題

次は未確定事項であり、既存仕様として扱わない。

開発・releaseのモード分岐を設けるか、判定に `cfg(debug_assertions)` を使うか、プロジェクトモード未実装のrelease用allを未対応エラーにするかは、この後続設計で確定する。標準テストの対象選択だけを変更するPRへ未確定の分岐を追加しない。

1. プロジェクトの特定方法、テストの入口の宣言・探索方法、profile等の選択条件。
2. 共通プロジェクトモジュールと各テスト固有のincludeを分ける方法。
3. ディレクトリ収集とincludeで同じ実体を取り込む場合の扱い。実体の同一性、別表記・symlink、異なる内容・種別・定義衝突を区別する。
4. 依存順序とコンパイル単位。入口ごとの順次実行を採るか、一括コンパイルを必要とするか。
5. 共通環境キャッシュのキー、失効条件、保存場所、process定義の扱い。
6. 復元時のSourceId、宣言・関数ID、診断位置の整合。入口に依存する値をキーから除くだけで共有可能と判断しない。
7. コンパイル結果の共有と実行状態の分離。各VMのテストI/Oや実行結果をキャッシュへ混ぜない。
8. テスト0件・対象0件、個別失敗後の継続、終了コード、quietの契約。
9. キャッシュ読み込み・ロック・保存失敗の扱い。現行のCWD取得失敗時の `.` への置換、cacheのrename失敗時のcopyへの切替も整理する。`crates/rune/src/compile.rs`、`crates/rune/src/commands/test.rs`、`crates/xldr/src/lib.rs` に残っている経路を2026-10-04に読み取り確認した。入力エラー・内部契約違反をフォールバックで隠さない。
10. 将来の並列化の単位。再帰探索・コンパイル環境の共有・並列実行を独立して決める。

## 検討の出発点

順次実行でも共通依存の再コンパイルを避けるには、次の構成が候補になる。

```text
標準環境のスナップショット
  → プロジェクト共通モジュールのコンパイル済み環境を共有
    → 各テストの固有includeと本体をコンパイル
      → 独立したVMで実行して結果を集計
```

共通環境のキーを入口スクリプトに依存させず、共有してよい入力とコンパイル状態を先に定義する。同じ依存集合でも収集順序やSourceIdが異なる場合の整合を確認する。

これは設計候補であり、採用済みのプロジェクトテスト仕様ではない。性能要件は、共通モジュールをテストごとに再コンパイルしないことを含めて定め、実装時に実測する。
