# Surtr 大量プロセス性能ベンチ仕様書 v0

## 1. 目的

本書は、Surtr のアクターモデル・プロセス実装に対して、以下を確認するためのベンチ仕様を定義する。

- 大量プロセス生成時のメモリ使用量
- 長時間実行時の CPU 使用傾向
- scheduler / mailbox / timeout / reply 処理の負荷傾向
- 管理プロセス集中時のボトルネック確認
- 実行時間、最大 RSS、メッセージ量などの比較可能な基準作成

本仕様は **コード例ではなく、ベンチシナリオの定義** を目的とする。

---

## 2. シナリオ概要

### 2.1 登場プロセス

- **管理者プロセス**
  - 全ワーカーの状態を管理する
  - ワーカーから採取資源量の報告を受ける
  - 累計必要資源量の達成を監視する
  - ワーカーへ次の目標地点と必要資源量を渡す

- **ワーカープロセス**
  - 管理者から指示を受けて移動・採取・帰還・休憩を行う
  - ループ実行により複数サイクルを継続する

### 2.2 ワーカー1サイクルの挙動

1. 管理者から次の到達地点距離を受け取る
   - ランダム範囲: **10m 〜 100m**
2. 管理者から必要資源量を受け取る
   - ランダム範囲: **100 〜 500**
3. ワーカーは目的地へ移動する
   - **1フレームにつき 1m** 進む
4. 到達地点では採取を行う
   - **5フレーム消費**ごとに資源をランダム入手
   - 1回の入手量は **1 〜 10**
5. 採取量が必要資源量に到達したら初期位置へ戻る
   - 帰路も **1フレームにつき 1m**
6. 管理者へ採取資源量を報告する
7. **10フレーム休憩**する
8. 次サイクルの到達地点と必要資源量を受け取り、再び繰り返す

---

## 3. 入力パラメータ

本ベンチの入力は次の 2 つとする。

- **ワーカー数 `W`**
- **累計必要資源量 `T`**

### 3.1 パラメータの意味

- `W`
  - 初期起動されるワーカープロセス数
  - 大量プロセス性能・メモリ使用量への影響が大きい

- `T`
  - ベンチ全体の終了条件
  - 管理者が受領した累計採取資源量が `T` に到達した時点で終了する

---

## 4. 平均モデル

ベンチ条件の目安を揃えるため、1ワーカー1サイクルの平均値を次のように見積もる。

### 4.1 平均距離

- 往路平均距離: `(10 + 100) / 2 = 55m`
- 復路平均距離: `55m`
- 移動合計: `110フレーム`

### 4.2 平均必要資源量

- `(100 + 500) / 2 = 300`

### 4.3 平均採取量

- 1回あたり平均 `(1 + 10) / 2 = 5.5`
- 必要採取回数の平均 `300 / 5.5 ≒ 54.5回`
- 1回につき 5 フレーム消費
- 採取時間平均 `54.5 * 5 ≒ 273フレーム`

### 4.4 平均サイクル時間

- 往路: 55
- 採取: 約273
- 復路: 55
- 休憩: 10

合計:

```text
約 393 フレーム
```

実運用上は **約 400 フレーム / サイクル** とみなしてよい。

### 4.5 平均持ち帰り量

1サイクルあたりの平均採取量は、必要資源量にほぼ一致するとみなし、

```text
約 300 / サイクル
```

とする。

---

## 5. ベンチ設計式

各ワーカーに平均 `K` サイクル実行させたいとき、累計必要資源量 `T` の目安は次式とする。

```text
T ≒ W * 300 * K
```

ここで:

- `W`: ワーカー数
- `300`: 1サイクルあたり平均採取量
- `K`: 1ワーカーあたり想定平均サイクル数

### 5.1 フレーム数の目安

1ワーカーあたりの平均フレーム数は次で近似できる。

```text
約 400 * K フレーム
```

この式により、

- `W` を増やすと主にメモリ負荷が増える
- `K` を増やすと主に CPU 時間・長時間安定性確認に効く

という使い分けができる。

## 6. 推奨ベンチケース

### 6.1 軽量確認

- `W = 1,000`
- `T = 3,000,000`
- 想定: `K ≒ 10`

用途:

- シナリオの整合性確認
- 終了条件の検証
- メッセージ往復の基本確認
- 初期メモリ傾向の確認

### 6.2 標準ベンチ

- `W = 10,000`
- `T = 30,000,000`
- 想定: `K ≒ 10`

用途:

- scheduler / mailbox / manager 集中の確認
- 最大 RSS の比較
- 実行時間の比較基準作成

### 6.3 重量ベンチ

- `W = 50,000`
- `T = 150,000,000`
- 想定: `K ≒ 10`

用途:

- 大量プロセス時のメモリ圧迫確認
- mailbox / waiting / timeout 管理の粗確認
- 管理者プロセスの集中ボトルネック確認

### 6.4 極端負荷

- `W = 100,000`
- `T = 300,000,000`
- 想定: `K ≒ 10`

用途:

- 上限調査
- process table / mailbox / registry / future / timeout のスケーリング限界調査
- 実装上の O(N) 箇所検出

## 7. 目的別の推奨設定

### 7.1 メモリ使用量の確認

ワーカー数を優先して増やし、サイクル数は抑える。

推奨:

- `K = 3 〜 5`
- `T ≒ W * 300 * 3`

例:

- `W = 10,000`, `T = 9,000,000`
- `W = 50,000`, `T = 45,000,000`
- `W = 100,000`, `T = 90,000,000`

用途:

- 起動後メモリ
- 定常時メモリ
- process instance サイズ影響
- mailbox / timeout slot 数の影響

### 7.2 CPU / scheduler 負荷の確認

ワーカー数は中程度にし、`K` を増やす。

推奨:

- `K = 20 〜 50`

例:

- `W = 5,000`, `T = 30,000,000`
- `W = 10,000`, `T = 60,000,000`

用途:

- scheduler の定常性能
- timeout / reply 処理の累積コスト
- manager hot spot の CPU 使用傾向

### 7.3 長時間安定性確認

推奨:

- `W = 1,000 〜 5,000`
- `K = 100 〜 300`

用途:

- メモリリーク確認
- mailbox 未処理蓄積確認
- timeout / deadline queue の肥大化確認
- 再開処理・resume 処理の安定性確認

## 8. 測定項目

本ベンチでは最低限、次を記録する。

### 8.1 時間系

- 総実行時間
- 総フレーム数
- 1フレームあたり平均処理時間
- 1秒あたり処理フレーム数

### 8.2 メモリ系

- 起動直後 RSS
- 定常時 RSS

- 終了直前 RSS

### 8.3 プロセス系

- 総プロセス数
- ワーカー生存数

- 待機中プロセス数最大値

### 8.4 メッセージング系

- 総送信メッセージ数
- 総返信メッセージ数
- timeout 件数
- 再開回数
- manager 受信件数
- worker 受信件数

### 8.5 シナリオ系

- 累計採取量
- 総サイクル数
- 1ワーカーあたり平均完了サイクル数
- 平均採取距離
- 平均採取完了フレーム数

## 9. 実行条件

測定比較をしやすくするため、以下を固定する。

- 乱数シードは明示的に指定する
- 実行ごとに同一シードで比較可能にする
- ログ出力は最小限にする
- デバッグ表示は無効化する
- timeout policy は明示的に固定する
- worker / manager の spec は実行間で変えない

### 9.1 乱数シード

最低でも以下の 2 パターンで測る。

- **固定 seed**: 再現比較用
- **複数 seed**: 偏り確認用

---

## 10. 終了条件

終了条件は次のとおり。

- 管理者が受領した累計採取資源量が `T` 以上になった時点で終了
- 終了時点で全ワーカーを停止、または run loop を停止する
- 終了後に統計値を出力する

### 10.1 注意

終了直前にワーカーが追加で持ち帰った資源量により、累計採取資源量は `T` を超過してよい。
超過分は誤差として扱う。

---

## 11. ベンチの観測上の注意

### 11.1 管理者プロセスの集中

本シナリオは、worker 性能だけでなく **単一管理者への集中負荷** を意図的に含む。

したがって本ベンチ結果は、以下をまとめて反映する。

- 大量 worker のスケジューリング性能
- manager 受信集中時の mailbox 性能
- reply / report / 次指示の dispatch 性能

これは欠点ではなく、**初期フェーズにおける実装の弱点検出に有効**である。

### 11.2 純粋な大量プロセス性能だけを見たい場合

別途、管理者を shard 化した派生ベンチを用意して比較する。

本書では初期フェーズ用として、まずは **単一管理者モデル** を正本とする。

## 12. 推奨ベンチ実施順

初回は次の順序で行う。

1. 軽量確認
   - `W = 1,000`, `T = 3,000,000`
2. 標準ベンチ
   - `W = 10,000`, `T = 30,000,000`
3. 重量ベンチ
   - `W = 50,000`, `T = 150,000,000`
4. 必要なら極端負荷
   - `W = 100,000`, `T = 300,000,000`

この順で、

- まず整合性
- 次に標準比較
- その後メモリ限界・性能限界

を確認する。

---

## 13. まとめ

本ベンチの基本式は次とする。

```text
T ≒ W * 300 * K
```

推奨基準ケース:

```text
軽量   : W=1,000   T=3,000,000
標準   : W=10,000  T=30,000,000
重量   : W=50,000  T=150,000,000
極端   : W=100,000 T=300,000,000
```

使い分け:

- メモリ確認: `K = 3〜5`
- 標準比較: `K = 10`
- CPU / 長時間安定性: `K = 20〜300`

この仕様により、Surtr の actor process 実装について、
**プロセス数・メッセージ量・待機制御・管理者集中の4軸**を継続的に比較できる。
