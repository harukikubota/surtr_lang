Surtr project_src.rs レビュー
============================

2026-04-08 取り込みメモ
----------------------
- clone ベースの `push_atomic` は今回「即修正」ではなく、作業フロー上の後続最適化課題として残す
- 診断系重複は別タスク化し、今回は数値モデルと runtime ID 分離を優先する
- トップレベル宣言の事前登録ポリシーは `doc/要件定義v9.md` と `doc/open-issues.md` 側で追跡する

対象
----
- 結合ソース: project_src.rs
- 主に設計整合性・失敗時挙動・将来のスケーリング観点で確認
- 単体の大ファイル提出のため、Cargo全体の実ビルド/実行ではなくコード読解ベースのレビュー

総評
----
全体として、
- フロントエンド(spire/sigil/scar) → IR/bytecode(forge/sindr) → VM(eldr)
の層分離はかなり明確です。
- Span を広く保持しており、診断品質を上げる前提もできています。
- Session / Checkpoint / Rollback の考え方も REPL・増分実行に向いています。

一方で、現状は「正しさを優先して clone で成立させる」箇所が複数あり、REPL や長時間セッション、将来の最適化フェーズでボトルネックになりやすいです。
また、診断系の重複と、トップレベル宣言の事前登録ポリシーの不整合は早めに整理したほうがよいです。

重要度: 高
==========

1. push_atomic が VM 全体 clone 前提で、増分実行コストが O(状態全体)
---------------------------------------------------------------
該当:
- crates/eldr/src/vm.rs: 779-785 行付近
- `pub fn push_atomic(&mut self, chunk: BytecodeChunk) -> Result<Value, RuntimeError>`

内容:
- `let mut next = self.clone();` で VM 全体を複製してから chunk を適用しています。
- VM には bytecode, constants, functions, source_map, frames, stack などが入っており、REPL でコードを足すたびに全体コピーになります。
- セッションが長くなるほど push_atomic のコストが線形増加しやすいです。

懸念:
- REPL / LSP 裏の評価 / マクロ展開確認 / bytecode dump 前提だと、この経路はかなり頻繁に通るはずです。
- 現時点では安全ですが、将来的に「遅いが理由が見えづらい」箇所になります。

提案:
- clone ベースは暫定実装として維持しつつ、将来的には以下のどちらかへ寄せるのがよいです。
  1. append 差分だけを記録して失敗時に巻き戻すジャーナル方式
  2. bytecode/constants/functions/source_map を永続データ構造風に分け、chunk 適用時に差分だけ差し替える方式
- 少なくとも `push_atomic` が clone ベースであることを API コメントで明記したほうがよいです。


2. 診断コードが rune / xldr で実質重複している
-----------------------------------------------
該当:
- crates/rune/src/diagnostics.rs: 3597 行以降
- crates/xldr/src/diagnostics.rs: 12485 行以降

内容:
- 差分を見る限り、両者はほぼ同一実装です。
- エラーテンプレート推論や ariadne レポート生成が二重管理になります。

懸念:
- 片方だけ修正してもう片方が古いまま、という事故が起きやすいです。
- 診断ロジックは細かい調整が多く、重複は将来ほぼ確実にメンテ負債になります。

提案:
- `crates/common_diagnostics` のような小さな共通 crate に寄せるか、少なくとも shared module に抽出してください。
- CLI ごとの差分は「入力の渡し方」「出力先」「終了コード」に限定し、診断組み立て自体は一本化したほうがよいです。


3. report_error が出力失敗時に unwrap で panic する
-------------------------------------------------
該当:
- crates/rune/src/diagnostics.rs: 3675-3681 行付近
- crates/xldr/src/diagnostics.rs: 12563-12569 行付近

内容:
- `builder.finish().eprint(...).unwrap();`
- 標準エラー出力や writer 周りで失敗した場合、ユーザー向け診断フェーズで panic になります。

懸念:
- コンパイラ/ランナーの「エラーを表示する処理」が panic すると、元の失敗原因が埋もれます。
- 特にテスト・IDE 連携・パイプ出力時に扱いづらいです。

提案:
- `if let Err(err) = ...` で握って簡易フォールバックを出すほうが安全です。
- 少なくとも panic ではなく、`eprintln!(...)` などへの退避経路を持たせたほうがよいです。


4. トップレベル事前登録が関数系だけで、型/コンストラクタ系と方針が揃っていない
------------------------------------------------------------------
該当:
- crates/sigil/src/resolver.rs: 7787-7849 行付近 (`predeclare_functions`)

内容:
- `Ast::Def` と `Ast::BuiltinDecl` は事前登録されます。
- しかし `Ast::StructDef` / `Ast::RecordDef` / `Ast::DeferrorDef` は重複チェックだけで、事前登録はしていません。

懸念:
- 言語仕様として「トップレベルは前方参照できる」の範囲が関数だけになります。
- 将来的にコンストラクタや型名を値文脈でも扱うなら、かなり分かりにくい差になります。
- 仕様として意図済みなら問題ありませんが、未決定なら早めに固定した方がよいです。

提案:
- 仕様を明文化してください。
  - A. 前方参照は関数だけ許可
  - B. トップレベル宣言は原則すべて事前登録
- 個人的には、値として呼ばれるもの/参照されるものはトップレベルで統一ポリシーに寄せたほうが理解しやすいです。


重要度: 中
==========

5. TypeRegistry getter が clone を返しており、読み取り API としては重い
---------------------------------------------------------------
該当:
- crates/eldr/src/vm.rs: 653-659 行付近
- crates/forge/src/codegen.rs: 2323-2326 行付近

内容:
- `pub fn type_registry(&self) -> TypeRegistry` が clone を返しています。
- display/inspect のような読み取り経路から毎回 clone されます。

懸念:
- 型エントリが増えるほど、診断や表示のたびに不要コピーが発生します。

提案:
- 可能なら `&TypeRegistry` を返す API に寄せる。
- 所有権が必要な箇所だけ明示的に clone する設計のほうが後で効きます。


6. セッション系 API が全体 clone 依存で揃っており、規模拡大時に compile-time / memory cost が増える
----------------------------------------------------------------------------------------
該当例:
- crates/scar/src/checker.rs: 4649-4660 行付近
- crates/forge/src/codegen.rs: 2305-2317, 2329-2346 行付近
- crates/sigil/src/resolver.rs: 7742-7750, 7794-7800 行付近

内容:
- Sigil / Scar / Forge の session/checkpoint/child scope が clone ベースです。
- 実装としては分かりやすいですが、型環境・slot_map・定数表が大きくなるほどコストが見え始めます。

提案:
- 今すぐ全面改修は不要です。
- ただし「clone で正しさを担保する層」と「差分で進めたい層」を整理しておくと後で楽です。
- 特に REPL hot path だけでも差分方式へ寄せる価値があります。


7. Resolver の with_child_scope は next_id だけ親へ反映するため、仕様意図をコメントで強く残したほうがよい
-----------------------------------------------------------------------------------------
該当:
- crates/sigil/src/resolver.rs: 7794-7800 行付近

内容:
- 子スコープで作られた binding 自体は親に戻さず、`next_id` だけを親へ反映しています。
- ブロックスコープ変数を漏らさないための設計としては妥当です。

懸念:
- 将来読む人が「なぜ child の定義が親に戻らないのか」を誤解しやすいです。
- マクロや特殊フォームを増やしたとき、ここを誤って変更すると名前解決の前提が崩れます。

提案:
- 「ブロック内 binding は漏らさないが、unique_id 空間だけは単調増加を維持する」という設計意図をコメントで明文化するとよいです。


8. 一部の整合性チェックが “panic ではないが内部不変条件頼み” になっている
--------------------------------------------------------------------------
該当例:
- crates/sigil/src/resolver.rs: 8292-8296 行付近 `iter.next().expect("checked arg length")`
- crates/spire/src/parser.rs: 11701 行付近 `parsed.into_iter().next().unwrap()`

内容:
- 直前チェックがあるので基本的には安全です。
- ただ、将来の分岐追加で前提が崩れると即 panic 系になります。

提案:
- ここは現状でも大きな問題ではありません。
- ただし「内部不変条件に依存する expect/unwrap」は `debug_assert!` 補助や小さな helper に包んでおくとレビューしやすくなります。


良い点
======
- レイヤ分割が明快
  - parser / resolver / typechecker / codegen / vm の責務境界が比較的見やすいです。
- Span がかなり丁寧に運ばれている
  - 後から診断品質を上げやすいです。
- REPL/増分実行を session/checkpoint で先に意識している
  - 個人開発言語としてはかなり良い投資です。
- builtin metadata と impl 数の const assert
  - 地味ですが破綻防止として効いています。
- runtime error context の追加情報
  - `stack_depth`, `frame_depth`, `locals_len`, `stack_top` などは実運用で役に立ちます。

結論
====
設計の方向性はかなり良いです。特に、
- 静的型付き
- 多段パイプライン
- 増分実行
- 診断改善の余地
を全部同時に見据えている点は強いです。

現状の主要課題は「正しさを優先した clone ベース実装を、どこまで本実装として残すか」です。
ここを REPL hot path と診断共通化から順に詰めれば、かなり安定した基盤になります。
