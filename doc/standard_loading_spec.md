# 標準ソースの任意ロードに関するメモ

状態: include の制約・診断は先行実装済み。標準ソースの任意ロードは未実装の仕様拡張メモ。2026-10-24。

実装済みの include 契約の正本は `docs/dev/diagnostics.md` と `docs/site/standard-library.md` に反映した。
本メモの `optional std` と追加ロード構文は今後の案であり、現在利用できる機能ではない。

## 1. 目的

標準ソースの登録、実行環境での既定ロード、ユーザーによる追加ロードを分けて管理する。
追加の標準ソースをユーザー定義より前にコンパイルする。
実ファイルをユーザー定義として読み込む include と、登録済みの標準ソースを選ぶ任意ロードを別の構文にする。

変更区分は level4。標準ソースの任意ロードの方針と、include 先の宣言が受理できない場合の診断を記録する。
任意ロードの具体的な構文は未確定であり、このメモで実装済みとは扱わない。

## 2. 標準ソースの登録とロード条件

標準ソースの正本は Sindr の `STDLIB_MODULE_SPECS` とする。
標準ソースの登録情報と、実行環境で既定ロードするソースの集合を分けて管理する。
任意ロードの構文は登録済みの識別子を指定し、登録情報にある埋め込みソースを選ぶ。
実ファイルのパスや本文から標準ソースとの同一性を判定せず、任意の実ファイルを標準ソースへ昇格させない。
バイナリに標準ソースの実ファイルパスを保持する必要はない。

現時点で、通常の `run` が既定ロードしない標準モジュールは Test だけである。
`surtr test` は Test も既定ロードする。
今後追加する任意ロードの標準モジュールも、同じ登録とロード条件で扱う。

import と修飾名による参照は、ロード済みのモジュールを対象とする。
通常実行で未ロードの Test を参照・import した場合は、既存の名前解決エラーとする。

`include 'path/to/file'` は常にユーザー定義として読み込む。
コピー元やファイル名によらず、ユーザー定義の規則を満たすファイルは受理し、満たさない宣言や導入済みシンボルとの衝突は拒否する。
現時点の任意ロード候補は Test のみで、その本文には `@builtin` 宣言があるため include では受理しない。

## 3. 任意ロードのコンパイルステージ案（未実装）

ユーザーが任意でロードする標準モジュールの追加に対応し、次の順でコンパイルする。

```text
std → optional std → user defines
```

| 区分 | 入力と責務 |
|---|---|
| `std` | 標準登録と実行環境で既定ロード対象とするソース。現行の `run` では Test 以外、`surtr test` では Test も含む |
| `optional std` | 別構文で指定され、標準登録のロード条件で許可される追加の標準ソース。標準ソースの区分でまとめてコンパイルする |
| `user defines` | include 先を含む、各入口から渡されたユーザー入力のステージ列。先行する標準ソースを参照してコンパイルする |

`std` は既存の Bootstrap と共有標準定義の prefix を含む。
`user defines` は、各入口から渡されたステージ境界と相対順序を保ったまま、標準ソースの後へ接続する。

標準ソースの追加ロード指定とユーザー定義の include を収集してからステージを構成し、指定の列挙順にかかわらず、追加の標準ソースをユーザー定義より前に置く。
参照できる宣言は前ステージと同一ステージに限定し、標準ソースから後続のユーザー定義への参照は拒否する。
`optional std` に入れるソースがなければ、その追加ステージは作らない。

Rune のコンパイル入口、Xldr の REPL preload、解析サービスでは、収集した標準ソースに同じ分類・ステージ構築の規則を適用する。
標準 prefix のキャッシュを使う場合も、追加の標準ソースをユーザー定義より前に配置する。
ロード対象・本文・ソース区分・ステージ構成の異なるコンパイル結果を再利用しない。

## 4. ソース区分と builtin 宣言

ローダーは、標準ソースの追加ロード指定を登録情報に照合し、ロード条件と配置先のステージを決める。
ロードを許可された追加の標準ソースは `optional std` に置き、`StdDefinitionSource` として解析する。
include 先のモジュールは常に `DefinitionSource` として扱う。

標準ソース内の `@builtin` 宣言は標準定義として受理する。
コンパイラが差し込む builtin 宣言も、生成元の情報を保持して受理する。
受理する宣言は、`BUILTIN_METAS` による宣言と署名の整合検査に従う。

ユーザーソースに直接記述された `@builtin` 宣言は拒否する。
モジュール名や宣言名だけで標準・コンパイラ生成の宣言として扱わず、取り込み元の区分と生成由来で判定する。

### include 先の宣言の検査（実装済み）

include 先の字句・構文解析で、`@builtin` や標準専用の `Type` 宣言など、ユーザー定義では許可されない構文を検出する。
検出は既存のソース区分と宣言の許可規則に基づく。文字列・コメント中の同じ語は対象にせず、`Type` の関数型エイリアスや許可された trait 制約など通常の用法は維持する。
ユーザー定義として解析できた宣言は、通常の名前解決で導入済みシンボルとの衝突を検査する。

標準 Test の本文を include して `@builtin` が拒否されること自体は意図した制約である。
include の文脈を伴わずに内部宣言の制約だけを表示していた診断は、include 文を主位置とする診断へ修正済みである。
通常実行と `surtr test`、相対パス・絶対パス・シンボリックリンク・コピーのいずれでも同じユーザー定義の規則を適用する。

## 5. 診断

### include のキャプション（実装済み）

以下の診断の主キャプションと primary location は、読み込み元の `include 'path'` 文全体にする。
include 先の拒否された宣言、衝突する宣言、導入済みの宣言は関連位置として示し、対象ファイル・宣言名・拒否理由を保持する。
案内はキャプションに混ぜず help に置く。

| 条件 | 診断本文 | 案内 |
|---|---|---|
| ユーザー定義では許可されない宣言・構文 | `Cannot include '{path}': {construct} is not allowed in user-defined source.` | `include` はユーザー定義を読み込むことを説明し、該当する宣言・構文を示す |
| 導入済みシンボルとの衝突 | `Cannot include '{path}': symbol '{symbol}' is already defined.` | 衝突元が標準定義なら、既に利用可能な定義を使うため include を削除するよう案内する。ユーザー定義同士なら重複する宣言または include の整理を案内する |

`include 'lib/test.srt'` は、実際に検出した `@builtin` 宣言を理由に拒否する。
標準 Test との同一性判定や Test 専用の拒否経路は設けず、ファイル名だけから Test 用の案内を選ばない。

`include 'lib/types/duration.srt'` は、ユーザー定義として宣言を解析した後、導入済みの `Duration` との衝突として案内する。
標準ソースと同一かどうかを調べる必要はなく、衝突相手の宣言情報から、標準定義が既に導入されていることを示す。

拒否の判定は各フェーズが担当し、ローダーは include 文と取り込み先ソースの対応を保持する。
Spire はユーザー定義の制約違反を識別できる情報を返し、Sigil は衝突する双方の宣言の source identity と span を保持する。
診断は構造化された拒否理由・宣言情報とこの対応から生成し、既存のエラーメッセージの文字列解析で分類しない。
Human / JSON の両方で include の primary location、原因の phase / reason、関連位置を整合させる。
一般の構文・型エラーを、上記二種類の include 診断へ一律に置き換えない。

未ロードのモジュールへの参照・import、標準経路での builtin 宣言と metadata の不一致には、既存の診断を使う。
標準ロード経路で受理した宣言へ、ユーザー定義の制約を誤適用しない。

## 6. 受入条件

- ユーザー定義として有効なモジュールを include できる。標準ソースと同じファイル名でも、その名前だけで拒否しない。
- include 先の `@builtin` と標準専用の型宣言を拒否し、主キャプションを include 文、関連位置を該当宣言にする。
- コメント・文字列中の `@builtin` / `Type` と、ユーザー定義で許可された `Type` の用法を誤検出しない。
- `duration.srt` の include は `Duration` の衝突として診断し、include 文と衝突する双方の宣言位置を示す。
- 相対・絶対パス、別名のシンボリックリンク、別の場所に置いた同じ本文のコピーでも、禁止宣言とシンボル衝突を同じ規則で判定する。
- include 先が複数ある場合、失敗した入力に対応する include 文を示す。
- 通常実行と `surtr test` で include のソース区分と診断規則を共通にする。
- Human / JSON で拒否理由・対象ファイル・include の位置・関連宣言の位置が一致する。
- 標準任意ロードの構文からは登録済みソースだけを選び、実ファイルの同一性判定を要求しない。

include の診断契約は `docs/dev/diagnostics.md` に反映済みで、CLI integration テストで上記の代表例と位置を確認した。
標準任意ロードの具体的な構文を要する検証は、その構文を確定してから追加する。
