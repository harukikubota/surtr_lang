# レビュー観点

このファイルは、今後 `project_src.rs` のような結合ソースを渡してレビューするときに、短時間で前提共有するための観点メモです。

目的は2つです。

1. レビューを毎回ゼロから始めないこと
2. Surtr の設計意図をこちらが誤読しにくくすること

---

## 1. まず見る全体像

Surtr は概ね次の層に分かれている前提で読むと理解しやすいです。

- `spire`: lexer / parser / AST
- `sigil`: 名前解決、スコープ、capture 解決
- `scar`: 型検査、型環境、型推論寄りの責務
- `forge`: IR / bytecode 生成
- `sindr`: 共通 IR / runtime 型 / builtin metadata
- `eldr`: VM 実行
- `rune`, `xldr`: CLI / 診断表示寄り

レビューでは、単体の実装だけでなく、**前段の不変条件を後段がどう仮定しているか** を優先して見る。

---

## 2. このコードベースで特に重視したい観点

### A. 言語仕様と実装のズレ

最優先。

特に以下を確認する。

- トップレベル宣言の前方参照ルール
- ブロックスコープで変数が漏れないか
- shadowing の扱い
- closure capture の境界
- struct / record / deferror / builtin / function で一貫した名前解決規則になっているか
- safe bind / result-like 制御が仕様通りか
- マクロや特殊フォームを追加したときに既存スコープ規則を壊さないか

Surtr は「関数型・静的型付け・データと変換中心」の設計なので、
**評価順序や副作用より、束縛規則・型規則・データ構築規則の一貫性** を強く見る。

---

### B. 不変条件がどこで保証されるか

各層で次を確認する。

- parser が何を保証するか
- resolver が何を保証するか
- checker が何を保証するか
- codegen が何を仮定してよいか
- vm が検証すべきことは何か

特に `expect` / `unwrap` / `panic` が出てきたら、

- ユーザー入力で到達するか
- 直前の層で閉じている不変条件か
- 将来の機能追加で破れやすいか

を確認する。

基準としては、

- **ユーザー入力起因の失敗** は `Result` / 診断に落とす
- **内部不変条件違反** は debug 時に強く検出
- release 時に即 panic させるかは慎重に判断

---

### C. 増分実行 / REPL / LSP でのスケール

Surtr は対話実行や補助ツール強化の方向が強いので、hot path を重視する。

特に見る箇所:

- session / checkpoint / rollback
- scope / env / bytecode / constants の clone コスト
- incremental compile の差分適用
- VM 側の atomic push
- 型環境や registry の getter が clone を返していないか

レビュー時は、単に「clone が多い」で終わらせず、

- 正しさのための clone か
- 一時的実装か
- hot path か
- 将来 persistent / journal 方式へ移すべきか

まで判断する。

---

### D. 診断品質

Surtr は Span をかなり丁寧に持っているため、診断は重要な価値になる。

確認項目:

- Span が途中で失われていないか
- 型エラー時に主原因と周辺情報が出せるか
- runtime error に call site / pc / opcode / stack 情報が付くか
- CLI 間で診断実装が重複していないか
- 診断表示そのものが panic しないか

診断は「あとで良くする」ではなく、**重複削減とフォールバック経路の確保** を早めにやるべき対象。

---

### E. 将来機能を壊しやすい境界

今後入りそうな機能を前提に壊れやすい箇所を見る。

- マクロ
- module attributes 的な仕組み
- アクターモデル / プロセス
- 遅延再開を含む VM 制御
- LSP / REPL / ソケット経由評価
- バイトコードダンプ / 展開表示

このプロジェクトでは、**今正しいだけでなく、後から意味を足せるか** が重要。

---

## 3. 具体的レビュー手順

毎回だいたいこの順で見ると速い。

### 1) 境界を見る

- 各 crate の責務
- 公開 API
- session/checkpoint の流れ
- 型や ID の所有者

### 2) 失敗経路を見る

- `Result` の流れ
- diagnostics
- `unwrap` / `expect` / `panic`
- rollback 失敗時の状態破壊有無

### 3) スコープと型を見る

- bind/safe bind
- closure capture
- top-level predeclare
- pattern と型の整合

### 4) 増分性を見る

- clone-heavy か
- append-only 前提か
- verifier が後段の最後の砦として機能しているか

### 5) 重複を見る

- CLI 間
- diagnostics
- 型表示
- helper の散在

---

## 4. 今後レビューで特に知っておきたい Surtr 固有前提

以下はレビュー時に事前共有されると精度が上がる。

### 共有してほしい仕様

- トップレベル前方参照の方針
- shadowing をどこまで許すか
- constructor を値として扱うか
- closure の capture をどこまで最適化対象にするか
- macro が元スコープへ与えてよい影響範囲
- VM での停止/再開モデル
- `Result` や `Bool` など、コンパイラ特別扱いする型の範囲

### 共有してほしい実装優先度

- 今は正しさ優先か、性能も優先する段階か
- REPL / LSP / CLI のどれが hot path か
- 一時実装として許容している clone / duplicate はどこか

これが分かると、
「問題」なのか「今は保留でよい設計」なのかを切り分けやすい。

---

## 5. レビューコメントの優先度ラベル

今後は次のラベルで返すと短くしやすい。

- **S**: 仕様破綻、誤動作、状態破壊の恐れ
- **A**: 早めに直したい設計負債
- **B**: 中期で効く改善
- **C**: コメント・命名・整理レベル

例:

- `S`: rollback 失敗で state が壊れる
- `A`: diagnostics 実装が二重化
- `B`: getter clone が多く hot path を圧迫
- `C`: 設計意図コメントが薄い

---

## 6. 自分向け理解メモ

このコードベースでは、単純な Rust の書き味だけで判断しない。

重視順は次の通り。

1. 言語仕様の一貫性
2. 各層の不変条件
3. 増分実行の成立性
4. 診断の品質
5. その後で性能・所有権の磨き込み

つまり、`clone` が多いこと自体は即 NG ではない。
ただし、

- REPL/LSP hot path にある clone
- state 全体 clone
- 共有化できる診断/型情報の clone

は優先的に見る。

また、Surtr は今後マクロ・プロセス・REPL 補助が増える前提なので、
**「今の1機能」ではなく「後から意味を足したときに破綻しないか」** を見るのが重要。

---

## 7. 次回レビュー依頼時の最低テンプレ

次回は短縮のため、依頼時に最低でもこれがあると助かる。

```md
今回見てほしい点:
- 仕様確認 / 実装レビュー / 性能観点 / 診断観点 のどれを優先するか

今回の変更で触った層:
- 例: spire + sigil

今回の意図:
- 例: match のブロックスコープを明確化した

既知の妥協点:
- 例: REPL まわりは clone ベースのまま
```

これがあると、レビューの観点をかなり絞れる。
