Surtr List 構文・パターン・型規則
=================================

目的
----
Surtr における List を、
- データ構築
- パターン分解
- 静的型付け
の3点で一貫させる。

本仕様では、List は先頭追加と先頭分解を基本とする不変シーケンスであり、
内部表現は cons cell を前提とする。表面構文は Erlang/Elixir に近いが、
意味論は静的型付き言語として定義する。


1. 基本方針
-----------
1. List は `List<A>` の単相的な値として扱う。
2. 式位置では List は構築される。
3. パターン位置では List は分解される。
4. `uncons` は公開関数としては提供しない。
5. 分解は SafeBind 左辺および match arm 左辺など、パターン位置でのみ有効とする。
6. 空リスト `[]` は表面上は多相的に見えても、型検査後の内部表現では必ず `List<A>` に具体化される。


2. 構文
-------

2.1 式位置の List 構文
~~~~~~~~~~~~~~~~~~~~~~
以下は式として扱う。

- `[]`
- `[x, ..xs]`
- `[a, b, c]`

意味:

- `[]` は空リスト構築
- `[x, ..xs]` は先頭追加による List 構築
- `[a, b, c]` は sugar であり、内部的には `cons(a, cons(b, cons(c, [])))`

例:

    []
    [1, ..xs]
    [1, 2, 3]


2.2 パターン位置の List 構文
~~~~~~~~~~~~~~~~~~~~~~~~~~~
以下はパターンとして扱う。

- `[]`
- `[head, ..tail]`
- `[a, b, c]`

使用可能位置:

- SafeBind 左辺
- `match` arm 左辺
- 将来導入する他の pattern-only 構文位置

意味:

- `[]` は空リストとの一致
- `[head, ..tail]` は非空リストの先頭分解
- `[a, b, c]` は固定長リストパターン sugar

例:

    [head, ..tail] = list

    match list {
      [] => zero
      [head, ..tail] => next
    }


2.3 非公開内部概念としての uncons
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
`uncons` は表面言語の通常関数としては提供しない。

`[head, ..tail]` がパターン位置に現れたとき、その内部意味を
`uncons` 相当の分解操作として扱う。

したがって、以下のような表記は表面コードには現れない。

    uncons(head, tail)


3. 構築規則
-----------

3.1 空リスト
~~~~~~~~~~~~
`[]` は `List<A>` を構築する。
ただし `A` は文脈、注釈、または推論によって確定しなければならない。

例:

    xs: List<Int> = []


3.2 先頭追加
~~~~~~~~~~~~
`[head, ..tail]` が式位置にあるとき、`cons(head, tail)` と同義とする。

型規則:

- `head : A`
- `tail : List<A>`
- 結果 : `List<A>`

`head` と `tail` の要素型が一致しない場合は型エラーとする。


3.3 リストリテラル
~~~~~~~~~~~~~~~~~~
`[a, b, c]` は sugar であり、以下へ展開される。

    [a, ..[b, ..[c, ..[]]]]

あるいは内部的には

    cons(a, cons(b, cons(c, [])))

として扱う。

全要素は同一型でなければならない。


4. 分解規則
-----------

4.1 非空リスト分解
~~~~~~~~~~~~~~~~~~
`[head, ..tail]` がパターン位置にあるとき、値が非空 List の場合に一致する。

束縛:

- `head` は先頭要素
- `tail` は残りの List

型規則:

- 入力値 : `List<A>`
- `head : A`
- `tail : List<A>`

空リストに対しては一致しない。


4.2 空リスト分解
~~~~~~~~~~~~~~~~
`[]` がパターン位置にあるとき、値が空リストの場合にのみ一致する。

型規則:

- 入力値 : `List<A>`
- 一致時に新しい束縛は発生しない


4.3 固定長パターン
~~~~~~~~~~~~~~~~~~
`[a, b, c]` がパターン位置にあるとき、固定長 3 のリストパターン sugar とする。
内部的には以下のようなネストした分解として扱う。

    [a, ..[b, ..[c, ..[]]]]

長さが一致しない場合は一致失敗とする。


5. 型規則
---------

5.1 List 型
~~~~~~~~~~~
List は一種類の要素型のみを持つ。

    List<A>

異種要素の混在は許可しない。

例:

    [1, 2, 3]        : List<Int>
    [true, false]    : List<Bool>
    [1, "x"]         : 型エラー


5.2 空リストの具体化
~~~~~~~~~~~~~~~~~~~~
`[]` は表面上は要素型未確定のように見えるが、型検査後の内部表現では必ず `List<A>` に具体化される。

具体化の方法:

- 型注釈
- 代入先型
- 関数引数/戻り値の期待型
- 周辺式からの型推論

型が決定できない場合は型エラーにしてよい。

例:

    xs: List<Int> = []
    ys = [1, ..[]]           // [] は List<Int> に具体化


5.3 構築位置での型規則
~~~~~~~~~~~~~~~~~~~~~~
式位置の `[head, ..tail]` は以下を満たさなければならない。

- `head : A`
- `tail : List<A>`

結果型は `List<A>` である。


5.4 分解位置での型規則
~~~~~~~~~~~~~~~~~~~~~~
パターン位置の `[head, ..tail]` は、マッチ対象が `List<A>` のときにのみ有効である。

一致時に:

- `head` は `A`
- `tail` は `List<A>`

を束縛する。


5.5 first
~~~~~~~~~
`first` は公開関数として提供してよい。

型:

    first : List<A> -> A?

意味:

- 非空リストなら先頭要素を返す
- 空リストなら `None` / `Nil` / `A?` の空値を返す

`first` は分解構文の代替ではなく、式位置での補助関数として位置づける。


5.6 len
~~~~~~~
`len` は公開関数として提供する。

型:

    len : List<A> -> Int

意味:

- List 長を返す
- 実装上は List handle に保持された長さを返す
- 計算量は O(1)


6. 使用制約
-----------

6.1 パターン専用構文の制約
~~~~~~~~~~~~~~~~~~~~~~~~~~
`[head, ..tail]` を分解として解釈できるのは、pattern-only の位置に限る。

例:

- SafeBind 左辺
- match arm 左辺

それ以外の位置では分解として扱わない。


6.2 式位置との曖昧性解決
~~~~~~~~~~~~~~~~~~~~~~~~~
`[head, ..tail]` は位置によって意味が変わる。

- Expr 位置: 構築
- Pattern 位置: 分解

この判定はパーサまたは構文解析後の文脈情報で行う。


7. 実装方針
-----------

7.1 AST/HIR 分離
~~~~~~~~~~~~~~~~
内部表現では、式とパターンで別ノードを持つことを推奨する。

例:

- `Expr::ListNil`
- `Expr::ListCons { head, tail }`
- `Expr::ListLiteral(Vec<Expr>)`
- `Pattern::ListNil`
- `Pattern::ListCons { head, tail }`
- `Pattern::ListFixed(Vec<Pattern>)`

`uncons` は表面構文ノードにせず、必要なら lowering 後の内部処理概念としてのみ持つ。


7.2 Lowering
~~~~~~~~~~~~
以下のように lowering する。

- Expr の `[a, b, c]` -> nested cons
- Pattern の `[a, b, c]` -> nested pattern cons
- Pattern の `[head, ..tail]` -> non-empty list match


7.3 VM との対応
~~~~~~~~~~~~~~~
VM では List を cons cell ベースで表現する。

- 空リスト
- cons cell
- List handle に長さを保持

表面の `uncons` は存在しないが、pattern lowering 後に以下のような内部操作へ落とせる。

- is_empty check
- head bind
- tail bind


7.4 型安全性
~~~~~~~~~~~~
List 要素型の整合性はコンパイラまたは bytecode verifier が保証する。
VM 実行時に `cons` の要素型を都度ランタイム検査する必要はない。

前提:

- `[]` は IR/bytecode で具体型 `List<A>` に単相化済み
- `cons` は `A x List<A> -> List<A>` として解決済み
- VM には well-typed bytecode のみを渡す


8. 推奨スタイル
---------------

8.1 構築
~~~~~~~~
List の逐次構築は先頭追加を基本とする。

推奨:

    acc = [x, ..acc]
    List::reverse(acc)

非推奨:

    acc = acc ++ [x]

後方連結は左オペランド長に対して線形コストになりやすいため、
ドキュメントおよび将来的な lint で `cons + reverse` を推奨する。


8.2 分解
~~~~~~~~
先頭要素と残りを扱いたい場合は `first` よりもパターン分解を優先する。

推奨:

    match list {
      [] => ...
      [head, ..tail] => ...
    }

`first` は式位置で簡易に先頭取得したい場合の補助APIとする。


9. 仕様上の結論
---------------
1. `uncons` は公開関数ではなく、List パターンの内部意味としてのみ扱う。
2. `[head, ..tail]` は Expr 位置では構築、Pattern 位置では分解である。
3. List は `List<A>` の静的型付き不変シーケンスであり、異種要素混在を許さない。
4. `len` は List handle に保持し O(1) とする。
5. 後方連結は可能でも推奨せず、`cons + reverse` を構築の基本パターンとする。
