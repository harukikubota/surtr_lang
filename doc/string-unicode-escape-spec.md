# 文字列エスケープの入力・引用表示仕様案

2026-10-03。実装入力となる仕様。前版の「表示専用」という制限を置き換え、通常の文字列リテラルと引用表示に同じエスケープ規則を適用する。静的文字列は、ユーザが選択した補間拒否・字面の補間開始の明示的なエスケープに統一する。

level 4：Unicodeエスケープの入力規則、未知エスケープの拒否、文字列補間との境界、Spire内の文字列情報の受け渡しを変更する。式の評価順序、文字列の実データ、型規則、VM命令は変更しない。

## 目的

ESCを含む文字列をREPL・inspectで欠落なく観察し、その引用表示を通常の文字列リテラルとして再入力できるようにする。端末ごとの回避策は設けず、共通の引用処理で制御文字を可視化する。

往復保証はString単体の引用表示について定める。構造体のprivate field省略やError表示など、inspect全体を実行可能なソースへ変換する仕様ではない。

## 調査結果

対象：`/Users/haruca/work/rust/surtr` の現行ソース。

表示経路は Xldr `repl/logic/render.rs::format_result_lines` → Eldr `builtin.rs::inspect_value` → Sindr `runtime.rs::quote_surtr_string_literal`。共通引用処理は `\`、`"`、LF、TAB のみをエスケープし、ESC などをそのまま出力する。CLI の `print_result` は結果を `println!` で書き出す。色なしの presenter は文字列をそのまま複製する。

`cargo run --quiet -- repl --quiet --no-local-config` に stdin pipe で入力し、stdout をバイト列として回収した。終了コード 0、stderr は空。

```surtr

String::codepoints(s, StringEncoding::Utf8)
```

- 連結後：`22 1b 61 22`。
- codepoints の出力：`Ok([27])`、`Ok([27, 97])`。

値の破損や連結の失敗はない。ESC を含む値が、引用符だけを足して端末に渡される。

追加で `SURTR_REPL_COLOR=never` と `always` の両方を実行し、生の ESC が残ることを確認した。`print(inspect(s ++ "a"))` でも同じバイト列が出る。非TTYの stdin は `run_plain_repl` を使い、rustyline の行編集を通らない。色付け前の引用処理も Surtr の自前実装である。今回の原因を外部クレートの欠落処理とする根拠はなく、Surtr の引用表示処理で説明できる。

ESC は一般的な端末制御列の開始文字である。引用符 `0x22` は ESC sequence の intermediate byte の範囲に入り、後続の `a` は final byte の範囲に入る。このため、引用符や後続文字が表示文字ではなく制御列の一部として扱われ得る。画面の欠け方は端末の実装・後続出力によって変わる。iTerm2を実際に操作して端末間の画面比較はしていないが、生のESCが出力される原因は端末に依存しない。

参考：[Ghostty公式の制御列仕様](https://ghostty.org/docs/vt/concepts/sequences)。

## 1. 入力構文

`"..."` と `'...'` は同じエスケープ規則を使う。引用符が文字列を閉じるかどうかは、復号前のソース上で判定する。

| ソース上の表記 | 文字列に入る内容 |
|---|---|
| `\\` | バックスラッシュ |
| `\"` | 二重引用符 |
| `\'` | 単一引用符 |
| `\n` | LF、U+000A |
| `\t` | TAB、U+0009 |
| `\u{HEX}` | 指定したUnicodeスカラー値1文字 |
| `\#{` | 文字としての `#{`。補間を開始しない |

`\#{` は既存の補間抑止表記を正式に列挙したもの。直後が `{` でない `\#` は未知エスケープとして拒否する。

### Unicodeエスケープ

```text
unicode_escape := '\u{' hex_digit{1,6} '}'
hex_digit      := '0'..'9' | 'a'..'f' | 'A'..'F'
```

- 値はU+0000〜U+10FFFFのうち、サロゲートU+D800〜U+DFFFを除く。
- 先頭ゼロと大文字の16進数字を受理する。表示は後述の正規形に揃える。
- 空白、符号、桁区切りの `_`、7桁以上の数字を受理しない。
- Unicode非文字（U+FDD0など）は、有効なスカラー値として受理する。Unicode正規化は行わない。
- `\u{...}` はUnicodeスカラー値であり、UTF-8バイト列を指定する構文ではない。たとえば `\u{80}` のUTF-8バイト列は `[194, 128]`。

既存の `String::codepoints(..., Utf8)` / `from_codepoints(..., Utf8)` は引き続きUTF-8のバイト列を扱う。

成功例（変更後）：

```surtr
String::codepoints("\u{1b}", StringEncoding::Utf8)    # Ok([27])
String::codepoints('\u{001B}a', StringEncoding::Utf8) # Ok([27, 97])
"\u{3042}"                                        # "あ"
"\u{1f600}"                                       # "😀"
"\\u{1b}"                                        # 実データは文字としての \u{1b}
```

追加の短縮形は設けない。CR、NUL、BEL、BS、ESCは、それぞれ `\u{d}`、`\u{0}`、`\u{7}`、`\u{8}`、`\u{1b}` で表現する。

### 拒否する入力と診断

未知エスケープをそのまま文字列に残す旧経路は削除する。復号に失敗した場合は文字列を生成せず、Spireの `LiteralSyntax` エラーにする。診断spanは元ソース上の該当エスケープを指す。

| 入力例 | 拒否理由 |
|---|---|
| `"\q"`、`"\e"`、`"\r"`、`"\0"`、`"\x1b"` | サポートしないエスケープ |
| `"\u1234"`、`"\u{1b"` | 必須の波括弧がない |
| `"\u{}"` | 数字がない |
| `"\u{xyz}"`、`"\u{1_b}"`、`"\u{ 1b}"` | 16進数字以外を含む |
| `"\u{000001b}"` | 7桁以上 |
| `"\u{110000}"` | U+10FFFFを超える |
| `"\u{d800}"`、`"\u{dfff}"` | サロゲート |

診断文は原因を区別する。単なるunknown tokenや無効な文字列への置換で済ませない。

ソース末尾で、さらに入力すれば成立する場合（開いた文字列、末尾の `\`、`\#`、`\u`、`\u{`、有効な桁までの `\u{1b`）は `IncompleteInput` とする。このEOF判定は、物理改行を追加していないソースに対する契約である。Unicodeエスケープ内の空白・改行は受理しないため、REPLのEnterによる行区切りでエスケープの途中を完成させることは保証しない。閉じる引用符などによって不正が確定した入力、無効な桁、桁数超過は追加入力待ちにしない。Unicode値の範囲・サロゲートの判定は、閉じる `}` で値が確定した時点で行う。ただし、追加できる桁を考慮しても有効なスカラー値にできない接頭辞は、その時点でエラーにする。たとえば末尾の `\u{d800` は数字の追加で有効になり得るため未完、末尾の `\u{110000` は6桁で上限を超えているためエラーとする。ファイル入力で未完のまま終了すれば解析失敗になる。

## 2. 補間との境界

補間開始は、元ソース上のエスケープされていない `#{` だけで判定する。エスケープを復号して得た `#`、`{`、`}`、引用符、バックスラッシュを、再び構文として解釈しない。Unicodeエスケープ中の `{...}` も補間の波括弧として数えない。

通常文字列は元ソースを左から処理し、エスケープが消費した文字を補間判定へ戻さない。この規則でバックスラッシュの偶奇も決まる。

| ソース上の内容 | 動作 |
|---|---|
| `#{name}` | 既存どおり `name` の式を補間する |
| `\#{name}` | 文字としての `#{name}` |
| `\\#{name}` | バックスラッシュ1文字に続いて `name` を補間する |
| `\\\#{name}` | バックスラッシュ1文字に続く、文字としての `#{name}` |
| `\u{23}{name}` | 文字としての `#{name}` |
| `#\u{7b}name}` | 文字としての `#{name}` |
| `\u{5c}#{name}` | バックスラッシュ1文字に続いて `name` を補間する |

補間式の中は通常のSurtrソースである。外側の文字列のエスケープ復号を式のソースへ適用しない。式内の文字列リテラルは自身の引用符とエスケープ規則で解析する。既存の式評価順序・Show契約は維持する。

診断spanは、復号後の文字数ではなく元ソース位置で保持する。補間前の `\u{...}` によって、補間式の診断位置がずれないことも契約に含める。

## 3. 他の文字列使用箇所

### 通常の文字列を使う既存surface

通常式、Stringパターン、includeパス、文字列を受け取る宣言引数で、同じエスケープ復号と拒否規則を使う。

補間を評価するsurfaceは通常式とregex sugarに限る。Stringパターン・includeパス・文字列の宣言引数は静的文字列を要求し、元ソースのエスケープされていない `#{...}` を含む文字列を `LiteralSyntax` エラーで拒否する。字面の `#{` は `\#{` と書く。Unicodeエスケープで生成した `#{` も通常の文字なので受理する。未完の補間開始や不正な補間の境界は、通常文字列の構文規則で拒否または未完入力に分類する。

### Regex sugar

`re"..."` / `re'...'` は引き続き通常文字列を `Regex::compile` に渡すsugarである。regexだけのエスケープ復号や未知エスケープの救済は設けない。

- 正規表現の `\d` を渡すソースは `re"\\d"`。
- `re"\d"` はSurtr文字列の未知エスケープとして拒否する。
- `re"\u{1b}"` は実際のESC1文字をRegex::compileに渡す。

正規表現クレート自身の文法は変更しない。通常文字列として成立した後のregex検証は、既存どおりRegex::compileの責務とする。

### Raw triple-quoted文字列・@doc

`"""..."""` と `@doc` の本文は既存のraw文字列・dedent規則を維持し、今回の `\u{...}` 復号と未知エスケープの拒否を適用しない。raw本文の `\u{1b}` はその6文字のままである。

raw文字列式の既存の補間と `\#{` による補間抑止は維持する。`@doc` 内の補間禁止も維持する。通常文字列の復号済みtokenとしてraw本文を処理しない。

## 4. 引用表示の正規形

REPLと `inspect` は、Stringを二重引用符で囲み、次の規則で表示する。

| 実データ | 引用符内の表示 |
|---|---|
| バックスラッシュ | `\\` |
| 二重引用符 | `\"` |
| LF | `\n` |
| TAB | `\t` |
| その他のC0、DEL、C1制御文字 | `\u{...}` |
| 連続する文字としての `#{` | `\#{` |
| その他の文字 | そのまま |

制御文字範囲はU+0000〜U+001F、U+007F〜U+009F。Unicodeエスケープの正規形は小文字16進数・不要な先頭ゼロなしとする。

生のESCを含む値は `"\u{1b}"`、その後に `a` を連結した値は `"\u{1b}a"` と表示する。文字としての `\u{1b}` を含む値は `"\\u{1b}"` と表示し、両者を区別する。

元のStringを `s`、共通の引用処理が返すソース文字列を `q(s)` とすると、通常式として `q(s)` を解析・評価した値は `s` と等しくなければならない。Unicode正規化や制御文字削除は行わない。String単体では任意の有効なUTF-8文字列についてこの往復を保証する。

この引用処理をREPLの束縛・単独評価・履歴値表示、inspectのString、List・Tuple・Result・structの入れ子、HashMapのキーと引用される値に共通適用する。

`to_string(String)` と `print(String)` の生文字列出力は既存の契約を維持する。`eprint(String)` は既存どおりinspect経由で引用表示し、新しい共通引用規則を適用する。HashMapキーなど既存の引用箇所は上記の共通処理を使う。CLI自身の色付けに使うANSI列は維持する。

## 5. 実装境界と移行

Spireは、元ソース上の文字列区間・補間式区間・位置情報を保持してから、文字列区間を一度だけ復号する。tokenは復号済みのPlain文字列と元ソースの補間を含むInterpolated文字列を区別し、static consumerはPlainだけを受理する。字面保存用のvalueと補間partsを二重に保持する旧経路は削除する。以下を必須とする。

- 通常文字列の復号規則を共有し、単一引用符・二重引用符・regex・静的文字列使用箇所で複製しない。
- 復号済みの内容を元ソースとして補間解析しない。
- 未知エスケープを保存する旧経路を残さない。
- 内部表現の違いを隠すための再復号、ダミー文字や特殊なUnicode文字による補間抑止を設けない。
- tolerant parser / LSPも同じ文字列規則と診断原因を使用する。編集中の回復が必要でも、不正なエスケープを有効な文字列値として扱わない。

Sindrの `quote_surtr_string_literal` は上記の正規形を実装する。Eldr・Xldrは既存の共通引用経路を使う。

未知エスケープの拒否と静的使用箇所の補間拒否は意図的な非互換変更である。旧静的文字列の字面 `#{...}` は `\#{...}` に書き換える。従来の `"\q"` は `"\\q"` に書き換える。regexの `\d`、`\s` なども同様に通常文字列のバックスラッシュを明示する。既存fixture・標準ライブラリ・文書例を監査し、必要な拒否テストとして旧入力を残す。互換モード・警告だけの旧経路は設けない。

実装時に更新する正本：

- `docs/site/language-reference.md`：入力エスケープ、Unicode範囲、補間抑止、未知エスケープの拒否。
- `docs/site/regex.md`：Surtr文字列とregex文法の境界。
- `docs/site/kernel.md`、`lib/kernel.srt`：inspectの引用表示とString単体の往復保証。
- `docs/dev/EldrVM_spec.md`、`docs/dev/Xldr_spec.md`：共通引用処理とREPL表示。
- String・HashMapの既存説明と該当する `@doc`：具体例の整合。

入力エスケープの正本はlanguage-referenceとし、実装の受け渡し契約はこの仕様の該当節を開発文書から参照できるようにする。一般的な診断表現に追加が必要な場合だけ `docs/dev/diagnostics.md` を更新する。

## 6. 受入条件

1. 両方の引用符で、既存エスケープ・Unicodeエスケープ・補間抑止を受理する。
2. U+0000、U+001B、U+007F、U+0080、U+D7FF、U+E000、U+10FFFFを受理し、サロゲート、上限超過、書式不正、未知エスケープを原因別に拒否する。
3. 同じUnicodeスカラー値の先頭ゼロ・大文字数字による入力を、同じ値に復号する。
4. エスケープで生成した引用符や `#{` が文字列終端・補間にならない。元ソースの補間開始とバックスラッシュの偶奇は第2節の表どおりになる。
5. 補間式内の文字列は独立して復号し、元ソース上の診断位置を保つ。
6. 静的文字列使用箇所とregex sugarに同じ復号・拒否規則を適用する。静的使用箇所では元ソース上の補間を拒否し、\#{とUnicodeエスケープで生成した字面の#{を受理する。regex検証は既存の境界に保つ。
7. raw triple-quoted文字列と@docの既存契約を保つ。
8. すべてのC0・DEL・C1、引用符、バックスラッシュ、文字としてのUnicodeエスケープ・補間開始、通常のUnicode文字を引用表示して再評価すると、元のStringに戻る。
9. 入れ子・HashMapキー・REPL束縛・単独評価・履歴値の表示に共通規則を適用する。
10. 元データのcodepointsと連結結果は変わらない。色なしCLI出力に値由来の生の制御文字を含めず、色ありでもCLIのANSI列と可視表記が両立する。
11. EOFの未完入力と、追加しても成立しない不正入力を区別する。tolerant parserでも不正入力を正常値にしない。
12. print(String)とto_string(String)の生文字列、およびeprint(String)のinspect経由の引用表示を保つ。

## 7. 実装・検証計画

1. Spireの入力成功・拒否・EOF診断・補間境界のテストを先に追加する。現行の未知エスケープ保存・復号後補間のどちらが契約を破るかを確認してから、共通の文字列処理と関連token consumerを置き換える。tolerant parser、regex sugar、静的文字列使用箇所もこの段階で整合させる。
