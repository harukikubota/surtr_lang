# Surtr 依存整理詳細設計

> 目的: 段階的コンパイル戦略を保ったまま、crate 間依存を `sindr` 中心の共有契約へ寄せ、飛び越え参照と旧 API 受け口を解消する。
> 本書は実装・移行設計を扱う。言語仕様の正本は `doc/要件定義v9.md`、REPL / TUI の外部契約は `doc/Xldr_spec.md` を正本とする。

最終更新日: 2026-04-14

---

## 1. 背景

現状の Surtr workspace はフェーズ分離自体は成立しているが、以下の構造的負債を抱えている。

- `sindr` に置いた builtin 正本を、Scar / Eldr が別表現で再構築している
- `diagnostics` が phase 固有型に依存し、機械向け JSON 契約が人間向け文面へ引きずられている
- `forge` が `scar` だけでなく `sigil` / `spire` の葉型にも依存している
- `xldr` が loader / compile orchestration と REPL / TUI 実装を同居させている
- `Ok = 0`, `Err = 1` などの予約値が複数 crate に散在している

この状態では、あるフェーズの内部表現変更が後段 crate に直接波及しやすく、段階的コンパイル戦略の利点が弱くなる。

本設計の狙いは次の 3 点である。

- `sindr` を「共有契約の正本」に限定し、依存の重心をそこへ寄せる
- 各フェーズ crate は「直前フェーズの公開出力」と `sindr` のみを参照する
- UI / CLI 層を compile core から分離し、REPL/TUI 改修前でも共通基盤を先に安定化する

---

## 2. 設計原則

### 2.1 `sindr` は shared contract crate とする

`sindr` に集約するのは「複数 crate から見える契約」であり、各フェーズの本体ロジックではない。

`sindr` に置くもの:

- source / span / module path / source kind などの共通基盤型
- `builtin_id`, `tag`, `fun_idx` などの内部識別子 newtype と予約定数
- builtin catalog と canonical signature
- bytecode / runtime value / type registry / `.eldr` schema
- 診断 DTO と JSON schema
- 後段フェーズでも再利用される葉型

`sindr` に置かないもの:

- parser の AST 構築ロジック
- resolver の名前探索アルゴリズム
- type checker の推論・単一化ロジック
- codegen の lowering 規則
- VM の実行ロジック
- REPL / TUI / CLI の入出力制御

### 2.2 フェーズは predecessor + `sindr` だけを見る

各フェーズ crate の依存は原則として次に固定する。

```text
sindr
spire        -> sindr
sigil        -> spire + sindr
scar         -> sigil + sindr
forge        -> scar + sindr
eldr         -> sindr
diagnostics  -> sindr
xldr-core    -> spire + sigil + scar + forge + eldr + diagnostics + sindr
xldr-ui      -> xldr-core + diagnostics + sindr + ratatui/crossterm/rustyline
rune         -> diagnostics + eldr + sindr + xldr-core (+ xldr-ui は対話機能の暫定依存)
```

本書では UI 側 crate を論理名として `xldr-ui` と呼ぶ。実装上は当面、既存 package `xldr` をその役割へ縮小する方針とする。

禁止する依存:

- `forge -> sigil`
- `forge -> spire`
- `diagnostics -> scar`
- `diagnostics -> spire`
- `eldr -> scar | sigil | spire`
- `xldr-core -> xldr-ui`

### 2.3 フェーズ出力型はその crate が所有する

入出力境界は引き続き各 crate の `pub` 型で表現する。

```rust
fn parse(src: &str)                   -> Result<Vec<Ast>, ParseError>
fn resolve(ast: Vec<Ast>)             -> Result<Vec<Resolved>, ResolveError>
fn typecheck(resolved: Vec<Resolved>) -> Result<Vec<TypedNode>, TypeError>
fn codegen(typed: Vec<TypedNode>)     -> Result<Bytecode, CodegenError>
fn execute(bytecode: Bytecode)        -> Result<(), RuntimeError>
```

ただし、境界型の内部で再利用する葉型は `sindr` から借りてよい。重要なのは「後段が前段 crate の内部型を掘りに行かないこと」である。

## 3. 目標アーキテクチャ

### 3.1 責務境界

| crate | 主責務 | 許可依存 | 公開してよい主要型 |
|---|---|---|---|
| `sindr` | 共有契約、runtime schema、builtin 正本、diagnostic DTO | 外部 crate のみ | `Bytecode`, `Value`, `BuiltinMeta`, `DiagnosticData`, `SourceRegistry` |
| `spire` | 字句解析・構文解析 | `sindr` | `Ast`, `ParseError` |
| `sigil` | 名前解決、import 解決、前方参照管理 | `spire`, `sindr` | `Resolved`, `ResolveError` |
| `scar` | 型検査、型注釈解決、field index 解決 | `sigil`, `sindr` | `TypedNode`, `TypeError` |
| `forge` | bytecode 生成、定数表・型表生成 | `scar`, `sindr` | `CodegenError` |
| `eldr` | VM 実行、builtin 実装、display | `sindr` | `RuntimeError`, `Vm` |
| `diagnostics` | human renderer / JSON serializer | `sindr` | `render_*` 関数群 |
| `xldr-core` | compile orchestration、module load、session rollback | `spire`, `sigil`, `scar`, `forge`, `eldr`, `diagnostics`, `sindr` | compile session API |
| `xldr-ui` | REPL/TUI 実装 | `xldr-core`, `diagnostics`, `sindr` | REPL/TUI entry |
| `rune` | CLI entry / subcommand dispatch | `diagnostics`, `eldr`, `sindr`, `xldr-core`, `xldr-ui` | CLI binary only |

### 3.2 段階的コンパイルと依存方向

本設計で守るべき invariant は次のとおり。

- parse 段は AST を返すが、Sigil 以降は AST の詳細構造を再解釈しない
- resolve 段は `Resolved` を返し、Scar は `Resolved` のみを入力とする
- typecheck 段は `TypedNode` を返し、Forge は `TypedNode` のみを入力とする
- Eldr は bytecode と runtime metadata のみを入力とする
- UI / CLI は compile core を呼ぶが、compile core から UI 実装は参照しない

## 4. `sindr` に集約する共有契約

### 4.1 module 再編方針

`sindr` を次の責務単位へ再編する。

| module | 役割 |
|---|---|
| `source.rs` | `SourceId`, `SourceKind`, `Span`, `SourceRegistry`, `ModulePath` |
| `ids.rs` | `BuiltinId`, `TypeTag`, `FunIdx`, `TypeId`, `DefId` などの内部識別子 |
| `builtin.rs` | `BuiltinMeta`, `BuiltinSignature`, catalog lookup, reserved builtin helpers |
| `surface.rs` | `Visibility`, `BinOp`, `Literal`, `SymbolName` などの共有葉型 |
| `diagnostic.rs` | `DiagnosticData`, `DiagnosticLabel`, `DiagnosticCode`, `JsonDiagnostic` |
| `runtime.rs` | runtime value, registry, reserved tags |
| `bytecode.rs` | `Bytecode`, opcode, chunk schema |

`surface.rs` は AST 本体ではなく「複数フェーズで意味を共有する葉型」のみを持つ。

### 4.2 識別子の newtype 化

内部識別子は user-visible `Int` と分離し、数値の生値比較を禁止する。

```rust
pub struct BuiltinId(pub u16);
pub struct TypeTag(pub u32);
pub struct FunIdx(pub u32);
pub struct DefId(pub u32);
```

予約値は `sindr::ids` または `sindr::runtime` に定数として集約する。

```rust
pub const RESULT_OK_TAG: TypeTag = TypeTag(0);
pub const RESULT_ERR_TAG: TypeTag = TypeTag(1);
```

受け入れ条件:

- `0`, `1`, `2` などの予約値が phase crate に直書きされない
- runtime ID と surface `Int` の API が型で分離される

### 4.3 builtin contract の正本化

現在の `sig_str: &'static str` だけでは Scar / Eldr / docs の三者で再解釈が発生する。これを構造化表現へ置き換える。

```rust
pub struct BuiltinMeta {
    pub name: &'static str,
    pub builtin_id: BuiltinId,
    pub arity: u8,
    pub signature: BuiltinSignature,
    pub effect: BuiltinEffect,
    pub docs_key: &'static str,
}

pub struct BuiltinSignature {
    pub type_params: &'static [BuiltinTyParam],
    pub params: &'static [BuiltinTypeExpr],
    pub ret: BuiltinTypeExpr,
}
```

`BuiltinTypeExpr` は `Int`, `Float`, `String`, `Boolean`, `Unit`, `Error`, `List<T>`, `Result<T>`, function, tuple を表現できる最小構造とする。

この catalog から派生するもの:

- Scar の builtin 型
- `@@builtin def` 検証
- Forge の builtin call metadata
- Eldr の dispatch table
- std module の canonical doc 整合性検証

禁止事項:

- `meta.name` による手書き `match` で型を再構築すること
- `builtin_id as usize` で実装配列を引くこと
- 未知 builtin を `Unit -> Unit` で握りつぶすこと

### 4.4 diagnostic DTO の正本化

machine-readable diagnostics は文面の再パースではなく、構造化データから生成する。

```rust
pub struct DiagnosticData {
    pub phase: DiagnosticPhase,
    pub code: DiagnosticCode,
    pub message: String,
    pub primary_span: Option<Span>,
    pub labels: Vec<DiagnosticLabel>,
    pub notes: Vec<String>,
    pub structured: Option<StructuredDiagnosticData>,
}
```

`StructuredDiagnosticData` は当面次を持つ。

- `TypeMismatch { expected, got }`
- `UndefinedName { name }`
- `ArityMismatch { expected, got }`
- `NonExhaustiveMatch { missing_patterns }`
- `ImportConflict { name }`

各 phase error は自身の crate で `impl From<&PhaseError> for DiagnosticData` あるいは `to_diagnostic()` を持つ。

`diagnostics` crate は次だけを担う。

- `DiagnosticData -> ariadne`
- `DiagnosticData -> JSON`
- `Vec<DiagnosticData>` の formatter

## 5. フェーズ境界の self-contained 化

### 5.1 `spire`

`Ast` 自体は `spire` が所有し続ける。ただし `Span`, `Visibility`, `Literal`, `BinOp`, `ModulePath` などの葉型は `sindr` へ移してよい。

移行後の原則:

- `spire::Ast` は `sindr::surface::*` を使ってよい
- 後段 crate は `spire::Ast` を直接保持しない

### 5.2 `sigil`

`Resolved` は resolver 出力として self-contained にする。

現状の問題:

- `Resolved` が `spire::AstTy` や `spire::Lit` をそのまま持っている
- 後段が parser 由来の表現差分に引きずられる

変更方針:

- `ResolvedTy` を `sigil` 内の独立型として定義する
- `ResolvedExpr` / `ResolvedPat` が必要とする literal / operator / visibility は `sindr::surface` を参照する
- `ResolvedId`, `DefKind`, `ImportBinding` など resolver 固有識別子は `sigil` に残す

結果:

- `scar` は `sigil::Resolved` だけを見ればよい
- parser の型注釈 AST 変更がそのまま Scar に波及しない

### 5.3 `scar`

`TypedNode` は codegen 入力として self-contained にする。

現状の問題:

- `TypedNode` が `sigil::ResolvedId` と `spire` 由来の葉型を直接参照している
- `forge` が `scar` 以外にも依存する理由になっている

変更方針:

- `TypedType`, `TypedPattern`, `TypedLiteral`, `TypedVisibility` を `scar` で定義する
- `TypedNode` が必要な symbol reference は `scar::typed::SymbolRef` のような codegen 向け形へ変換して保持する
- field access は現行方針どおり Scar で index 解決済みとする

結果:

- `forge` の direct dependency は `scar` + `sindr` に縮退する
- resolver ID 変更がそのまま codegen へ漏れない

### 5.4 `forge`

`forge` は `TypedNode` 以外の前段知識を持たない。

`forge` に残してよい責務:

- `TypedNode -> Bytecode` lowering
- constant table / label table / type registry 生成
- reserved tag / builtin id の使用

`forge` が持ってはいけない責務:

- resolver の `ResolvedId` 再解釈
- parser literal の再解釈
- builtin signature の独自推定

## 6. crate 別詳細設計

### 6.1 `diagnostics` を renderer crate に縮小

#### 目的

- `diagnostics` から phase 固有依存を取り除く
- JSON 契約を人間向け文面から分離する

#### 変更内容

- `SourceRegistry`, `Span`, diagnostic DTO を `sindr` へ移す
- `diagnostics` は `render_human`, `render_json`, `format_diagnostic_bundle` のみ公開する
- `rune` / `xldr-core` は phase error から `DiagnosticData` を作って renderer に渡す

#### API 変更案

```rust
pub trait ToDiagnostic {
    fn to_diagnostic(&self) -> DiagnosticData;
}

pub fn emit_human<W: std::io::Write>(
    writer: W,
    registry: &SourceRegistry,
    diagnostics: &[DiagnosticData],
) -> std::io::Result<()>;
```

#### 移行メモ

- まず adapter を各 crate に追加し、旧 API からも新 DTO を返せるようにする
- 旧 `serializable_diagnostic_by_id` 系は DTO ベース実装に差し替えてから削除する

### 6.2 builtin 系の一本化

#### 目的

- `BUILTIN_METAS` を本当に唯一の正本にする
- Scar / Eldr / std module のずれを禁止する

#### 変更内容

- `BuiltinMeta.signature` を構造化
- `sindr::builtin::catalog()` に lookup helper を追加する
- `scar` は signature から内部 `Ty` を構築する
- `eldr` は `match BuiltinId` または `(BuiltinId, fn(...))` map で dispatch する

#### 推奨 API

```rust
pub fn builtin_by_id(id: BuiltinId) -> Option<&'static BuiltinMeta>;
pub fn builtin_by_name(name: &str) -> Option<&'static BuiltinMeta>;
pub fn all_builtins() -> &'static [BuiltinMeta];
```

#### 受け入れ条件

- builtin 追加時の修正起点が `crates/sindr/src/builtin.rs` のみで済む
- builtin 署名不整合が compile time または unit test で検出される

### 6.3 reserved tag / ID の集約

#### 目的

- runtime 内部識別子の責務を `sindr` に集約する

#### 変更内容

- `scar::env` の `next_tag: 2` を `RESULT_ERR_TAG.next_user_tag()` 相当の helper に置き換える
- `forge` の `Constant::Tag(0/1)` を予約定数へ置換する
- `runtime display` 側も予約定数で判定する

#### 追加 helper 例

```rust
pub const FIRST_USER_TAG: TypeTag = TypeTag(2);

pub fn is_reserved_result_tag(tag: TypeTag) -> bool;
pub fn next_user_tag_from_reserved() -> TypeTag;
```

### 6.4 `xldr` の core / UI 分離

#### 目的

- 共通 compile orchestration を UI 依存から切り離す
- 将来の TUI 大改修前に core を安定化する

#### crate 構成

```text
crates/xldr-core
  src/lib.rs
  src/loader.rs
  src/session.rs
  src/compile.rs
  src/checkpoint.rs

crates/xldr
  src/lib.rs
  src/repl/**
  src/tui/**
```

現時点では package rename を強制せず、既存 `xldr` を UI crate として縮小する。`doc/Xldr_spec.md` の外部契約は維持する。

#### `xldr-core` に移すもの

- std module 収集
- source load / source kind 判定
- `parse -> resolve -> typecheck -> codegen -> execute` orchestration
- checkpoint / rollback
- compile session state

#### `xldr` に残すもの

- `rustyline` ベース REPL loop
- TUI state / widgets
- REPL command parser
- input editing / display

#### 依存規則

- `xldr-core` は `ratatui`, `crossterm`, `rustyline` を持たない
- `xldr` は `xldr-core` を呼ぶだけで、compile pipeline 実装を持たない
- `rune run/build/dump/test` は `xldr-core` を使い、`repl` だけが `xldr` を使う暫定構成を許可する

### 6.5 std module loader の決定性強化

#### 目的

- `lib/` 構成変更に強い loader にする

#### 変更内容

- `lib/**.srt` を再帰収集する
- default std module は basename ではなく canonical module path で一致判定する
- `lib/tests/**` は引き続き除外する

#### canonical key

`lib/trait/numeric.srt` は `trait/numeric.srt` をファイルキーとし、必要なら module path (`Numeric`) を別保持する。

#### 受け入れ条件

- サブディレクトリ追加で default std module 判定が壊れない
- ロード順は `Bootstrap -> default std modules -> discovered extra std modules -> user inputs` で固定される

内容:

- 本書を追加する

### M2. builtin catalog を構造化し、Scar / Eldr を差し替える

対象:

- `crates/sindr/src/builtin.rs`
- `crates/scar/src/checker/**`
- `crates/eldr/src/builtin.rs`

作業:

- `sig_str` 主体から `BuiltinSignature` 主体へ移行
- Scar の手書き `match` を削除

- builtin 定義は catalog のみを修正すれば各フェーズで反映される

### M3. `Resolved` を self-contained 化

対象:

- `crates/sigil/src/resolved.rs`
- `crates/sigil/src/lib.rs`

作業:

- `ResolvedTy` 等の独立型導入

完了条件:

- `sigil` の公開型から `spire::AstTy` が消える

### M4. `TypedNode` を self-contained 化し、Forge の飛び越え依存を除去

対象:

- `crates/scar/src/typed.rs`
- `crates/forge/src/**`
- `crates/forge/Cargo.toml`

作業:

- `TypedNode` が codegen に必要な情報をすべて自身で持つように再編
- `forge` の `sigil` / `spire` 依存を削除

完了条件:

- `forge/Cargo.toml` が `scar` + `sindr` のみになる

### M5. `xldr-core` 新設と loader / session 抽出

対象:

- `crates/xldr-core/**` 新設
- `crates/xldr/**` 縮小

作業:

- loader / compile orchestration / rollback を抽出
- `run/build/dump/test` の batch 系は `xldr-core` 経由に寄せる

完了条件:

- `xldr-core` が UI 依存を持たない
- REPL/TUI を触らずに compile core の修正ができる

### M6. 不要依存と旧 API を削除

対象:

- 古い adapter, fallback, reexport

作業:

- deprecated helper を削除
- `cargo deny` 相当の依存チェックが不要でも、workspace grep で禁止依存を検証する

完了条件:

- 本書 3.1 の依存表と実コードが一致する

- `unit/sindr`
  - builtin catalog lookup
  - reserved tag / id helpers

- `forge` が `sigil` / `spire` 非依存で build できること
- `diagnostics` が `scar` / `spire` 非依存で build できること

## 9. 受け入れ条件

本改修の受け入れ条件は次に固定する。

- `sindr` が shared contract crate として責務分離されている
- `forge` の飛び越え依存が除去される
- `diagnostics` が phase 固有型に依存しない
- builtin の正本が `sindr` の構造化 catalog へ一本化される
- 予約 tag / builtin ID / fun index の生値散在が解消される
- `xldr-core` が UI 依存を持たず、batch compile 経路から利用できる
- `cargo nextest run --workspace` が通る

---

## 10. 非目標

本設計では次を直接の対象外とする。

- REPL / TUI の UX 改修
- trait system の拡張
- macro 段階の導入
- runtime の大規模最適化
- surface syntax の追加

これらは依存整理後の土台の上で別設計として扱う。

## 11. 実装順の推奨

最小リスク順は次のとおり。

1. `sindr` に diagnostic DTO / IDs / reserved constants を追加する
2. `diagnostics` を renderer crate に縮める
3. builtin catalog を構造化し、Scar / Eldr の旧受け口を除去する
